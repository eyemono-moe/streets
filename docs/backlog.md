## Vite+ (`vp`) への移行

`vp` は Vite・Vitest・Oxlint・Oxfmt・Rolldown・tsdown をタスクランナーとキャッシュごと1つのバイナリに束ねた統合ツールチェーン。2026-03-13 に alpha、2026-05-13 の v0.1.21 で alpha が外れた。

### このリポジトリで実際に置き換わるもの

| 現在 | vp 後 |
|---|---|
| Vite 6.1（Rollup） | Vite + Rolldown |
| Vitest 3.0.5 | 同梱 |
| **Biome**（lint + format） | **Oxlint + Oxfmt** |
| pnpm | vp のパッケージマネージャ管理下に入りうる |

### 着手前に確認すること

- **Biome → Oxlint/Oxfmt が最大の変更点。** ルールセットが一致しないため、`biome.json` の設定を移す作業と、フォーマット差分による大量の変更が発生する。`pnpm check` / `pnpm fix` は CI と本リポジトリの全スクリプトが依存しており、`scripts/check-read-layer-deps.mjs` もこの経路に乗っている。
- **モノレポ向けの利点は効かない。** vp の売りであるタスクランナーのキャッシュとモノレポ対応は、単一パッケージの本リポジトリでは価値が薄い。得られるのは主にビルドと lint の速度。
- **バージョンが 0.1.x である。** 移行時点の安定度を確認すること。
- SolidJS プラグイン、`vite-plugin-pwa`、UnoCSS が Rolldown ベースの Vite で動くかを先に検証する。

## knip による旧実装の削除

[実装計画の後続 #8](./superpowers/archive/plans/2026-07-31-read-layer-single-relay.md)（旧実装の削除）を、手書きのリストではなく **knip** で機械的に行う。

現在 `check-unused` が `@line/ts-remove-unused` を使っているが、これは未使用エクスポートの検出が中心。knip は**未使用のファイル・エクスポート・依存パッケージ**をまとめて検出できるため、「どのファイルが孤立したか」を人間が覚えておく必要がなくなる。

### なぜこれが効くか

計画 #8 の削除対象は現在 1 ファイル単位で列挙されている。新旧のコードが `src/core/solid/` と `src/core/nostr/` に同居しているためディレクトリ単位で消せず、列挙が必要だった。**列挙は次に新しいファイルが増えたときに腐る。**

同じ問題に対して `scripts/check-read-layer-deps.mjs` は「覚えておく」を「CI が落ちる」に置き換えた。knip はその削除側の対応物になる — 旧実装への最後の import が消えた瞬間、そのファイルが孤立したことを検出できる。

### 着手前に確認すること

- `@line/ts-remove-unused` を置き換えるのか併用するのか。
- Vite+ 移行との順序。vp は lint を Oxlint に替えるが knip はカバー範囲が違うので競合しないはず。ただし両方を同時にやらないこと。
- SolidJS のルート定義は `src/router.tsx` の `lazy(() => import(...))` 経由なので、動的 import を knip が追えるか確認する。追えないとルートコンポーネントが全て未使用に見える。

## seed データの NIPs 準拠検証と循環参照テスト

`e2e/fixtures/seed.ts` が生成するイベントについて、**NIPs に準拠しているかを網羅的に検証**できるようにする。あわせて各 kind について、**引用やリプライを含む循環参照のケース**をテストデータとして用意する。

### なぜ循環参照が重要か

[ADR-0017](./adr/0017-declarative-renderer-needs.md) の波状解決は、レンダラが宣言した `needs` を波ごとに 1 クエリで解決し、**収束するか深さ上限（引用の入れ子は 2 階層）に達したら停止する**。

**循環参照はこの深さ上限が機能することを証明する唯一のケースである。** イベント A が B を引用し、B が A を引用していれば、上限がなければ波は永遠に続く。上限があれば 2 波で止まる。

波状解決はまだ実装されていない（[後続計画 #2](./superpowers/archive/plans/2026-07-31-read-layer-single-relay.md)）。**そのため、このテストデータは計画 #2 の着手前に用意されているべきである。** 実装してからテストを足すと、上限が本当に効いているのかを確かめないまま進むことになる。

用意すべき循環の形:

- A が B を引用、B が A を引用（2 サイクル）
- A → B → C → A（3 サイクル）
- 自己引用（A が A を引用）
- リプライの循環（`e` タグで親子が閉じる）
- 引用の入れ子が 3 階層以上（上限で打ち切られることの確認）

### なぜ NIPs 準拠の検証が要るか

seed データはテストの土台であり、**ここが NIPs から外れていると、テストが通っても実際のリレーで動く保証にならない**。逆に seed が仕様に厳密であれば、`isNostrEvent` と `verifyEvent` の検証がテストデータを弾いてしまう場合にどちらが誤っているかを切り分けられる。

### 着手前に確認すること

- **`e2e/fixtures/seed.ts` は現在 `nostr-tools` に依存している。** [ADR-0020](./adr/0020-no-nostr-library-noble-primitives-only.md) で本体からは依存を落としたが、テスト用共有インフラとして残している。seed を NIPs 準拠の基準にするなら、**基準側が本体と同じ実装であってはならない**（同じバグを共有すると検証にならない）。`nostr-tools` を残すことがむしろ独立した第二実装として機能する、という見方もできる。ここは意図して決めること。
- **seed の決定性は 2026-08-01 に修正された。** それ以前は `dev:relay:reset` が Docker のボリューム名を取り違えて DB を消せておらず、過去の実行のイベントが残り続けていた。準拠検証は決定的なシードを前提とする。
- 検証をどこで走らせるか。ユニットテスト（seed が生成したイベントを直接検証）か、リレーへ投入した後の e2e か。前者のほうが速く、リレーの受理／拒否と切り分けられる。
