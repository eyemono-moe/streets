## 外部レビュー（2026-08-04）— 着手順を横から縦へ変える

外部レビューを受け、**次は読み取り層の続きではなく縦断スライスを作る**と決めた。

> 個々の判断は論理的だが、プロダクトを完成させる設計というより「理想的な Nostr 読み取り基盤を作る研究開発」に寄りすぎている。実装が設計を検証しているのではなく、設計を維持するために実装している状態へ近づいている。

**数字が裏づける**（2026-08-04 時点）。v1 は main から 201 コミット先行、読み取り層 3,056 行・テスト 6,142 行・`docs/` 12,240 行に対し、**使っている画面は `/debug/v1-section` 1 本だけ。** 要件が使用によって検証されていない部品に厳密さを注いでいた。

**[ADR-0002](../adr/0002-v0-parity-before-cutover.md) は覆さない。** ADR-0002 が決めるのは「未完成の v1 を本番に出さない」という本番切替の話であり、読み取り層を作り切ってから UI を載せるかという開発順序は要求していない。`/v1-preview` のような内部ルートで縦断スライスを動かすことは両立する —— ADR-0002 自身が「切替までフィードバックが得られず、設計の誤りが長期間露見しないリスクを負う」と記録しており、そのリスクが今回顕在化した。

**レビューの指摘のうち、参照コードが古く既に閉じているもの**（再提起しないこと）: 受信イベントのローカルフィルタ再照合、500 件バースト時の全ソート・全通知（いずれも下記「解消済み」参照）。

**反映しないと決めたもの:**

- **`Source` を Nostr イベント列と非イベント（NIP-11 等）の 2 層に割る** —— 分岐が増えてから割る。今割ると使われない抽象を足すだけになる。
- **接続予算のコストモデル化**（`hardLimit`/`interactiveReserve`/`backgroundLimit`、リレーごとの重み付け）—— 30 は実測に基づく（[research](../research/2026-08-01-outbox-connection-budget.md): 需要 378〜1251 本に対し貪欲選択で 96〜98% 被覆）。環境適応は実際に苦しんでから。
- **高水準 Nostr ライブラリの排除を再検討する** —— [ADR-0020](../adr/0020-no-nostr-library-noble-primitives-only.md) の決定であり、覆すなら独立した議論が要る。今の停滞の原因ではない。
- **全性能予算を Playwright で測る方針の見直し**（構造予算/ベンチマーク予算/ブラウザ E2E 予算の 3 階層化）—— 方向は正しく `scripts/research/measure-section-reader-burst.mjs` が中間層に相当するが、ADR-0011 の書き換えを伴うので測れない指標に実際にぶつかってから。

## v1 縦断スライス（2026-08-05）— 仕様 10 節の答え

動くもの（NIP-07 ログイン・3 カラム・kind:0 コアレッサ・投稿・リロード復元、`/v1-preview`）は検証済み。以下は実際に動かして初めて答えられた 5 問だけを、推測を除いて書く。

### 問い1 —— `{ items, status, loadMore }` で足りたか

**足りた。** 実装者は `items`/`status().phase`/`status().incomplete` を過不足なく使え、`loadMore` は仕様どおりページネーション対象外で未使用（型に存在すること自体は邪魔にならなかった）。

摩擦は `Section` の形ではなく**一段上**で起きた —— 「pubkey から `warmUpRouting` を呼び `NostrSource` を組み立てる」約 15 行のパターンを `debug/v1-section.tsx` と `v1-preview.tsx` の両方で手で複製している。「2 箇所目では時期尚早、3 箇所目が出たら共通化する」と判断し、この時点でも呼び出し箇所はこの 2 つのままで、**共通化の着手条件はまだ満たされていない。**

N+1 の実物計測: **50 件のノート・10 人の著者に対し、kind:0 の REQ は 200ms のまとめ窓のもとでちょうど 1 本。** プロフィールのコアレッサが `{ items, status, loadMore }` の外側の薄いレイヤー（`profile-requests.ts`）として無理なく載ったこと自体も、この 3 点セットが土台として足りていた傍証になる。

### 問い2 —— 30 接続予算は 3 カラム + プロフィール + 投稿で成立したか

**成立した。** ローカル docker relay での計測は `connections: 4`（予算 30 に対し桁違いで何も試せていない）。答えたのは実鍵・実リレーでの検証（2026-08-05）—— 3 カラム + プロフィールのコアレッサ + 実フォローリストで**接続数は 3〜9、ピーク 10。** ローカル計測の約 2.5 倍の接続を使いながらまだ予算の 1/3 で、予算 30 の妥当性を裏づける最初の実地データになった。

### 問い3 —— 楽観的挿入は 100ms 予算に収まったか

**アプリの制御が及ぶ範囲では収まった。** 初回計測（クリック→テキスト可視化を Playwright の `toBeVisible()` で測る手法）は 72〜920ms とばらついたが、これは計測窓に `signer.signEvent()`（`page.exposeFunction` 越しの Node 呼び出しという実運用に無い IPC ホップ）と Playwright のポーリング間隔が混ざっていたためで、**ノイズであり答えではない。**

修正後（`store.put()` から `setOptimisticEvents()` の signal 書き込み完了までを `performance.now()` で挟み、`signEvent` を計測窓の外に出す）は **0.9〜12.9ms、定常状態では 1ms 未満** —— 100ms 予算に対して 2 桁小さい。`data-testid="optimistic-insert-ms"` に常設し、実鍵でも確認できる。

**未測定**: 本物の NIP-07 拡張機能の署名確認 UI が出てからユーザーが反応するまでの時間（計測手段が無い）、`publisher.publish()` の往復時間（`publish-result` の表示タイミングを計測すれば分かるが未実施）。

### 問い4 —— `status.incomplete` の生の数値は、作った本人が見て意味が分かったか

**分かった部分と分からなかった部分がある。** 実装者は「`unreachableRelays` は読めば分かるが、`unroutableAuthors` と `uncoveredAuthors` はフィールド名だけでは区別できず、`SectionPlan` のドキュメントコメントを読んで初めて区別できた」と報告 —— **画面だけでは意味が分からず、ソースコードを開いて初めて分かった。**

**訂正: この問いはそもそも答えられる状態になかった。** `incomplete` の 3 つの数値は単一カラムでは出ていたが、`DeckColumn` へ書き直した際に描画が落ち、`/v1-preview` に出ていなかった。仕様 7 節が「既存の `status.incomplete` の生の数値をそのまま見せる」と明記していたにもかかわらず見落とされ、発見は人間の実機確認中の問い返しによる。**この要求は spec の別の節（エラー処理の表）にあり、受け入れ確認はカラム数・リロード・localStorage に向いていた** —— 受け入れ確認が spec の一部しか写さないとき、写されなかった部分は誰の担当でもなくなる。

描画は復旧させた（`data-testid="deck-column-incomplete"`）。**問い4 は依然として未取得** —— 一次情報は上の実装者自身の体験のみで、実際に画面で見た人間の判断はまだ無い。

### 問い5 —— fetch-once をどこまで一般化する必要が見えたか

「新しい意味論を発明せず、`bootstrap.ts` の `collect()` が既に持っていたものを公開面へ出す」という仕様 5 節の方針どおり、`collect()` を `src/core/read/collect.ts` に切り出し `bootstrap.ts` と `SubscriptionManager.fetchOnce()` で共有した。プロフィールのコアレッサはこの `fetchOnce` にそのまま乗り、追加の一般化は要求しなかった。**「一度引いて閉じる」という単一の意味論で、このスライスが必要としたものは全部足りた。**

**一般化の要否は手つかず。** 仕様 5 節が明記するとおり購読には「時間を遡って取り切る」ものと「これから来るものを受け続ける」ものがあり、rx-nostr の backward/forward strategy と合わせて設計すべき領域だが、本スライスはページネーションに触れておらず材料は増えていない。次にページネーションが要るタスクが、この整理に取り組む最初の機会になる。

## A-1 デッキとカラム（2026-08-07）— 仕様 12 節の答え

仕様 12 節が定める 6 問への回答。**問 3・4・5 は実装した内容から、問 1・2・6 は人間による実鍵・実リレーでの確認（2026-08-07）から答えた。** 上の「v1 縦断スライス」節と同じ規律で書く —— 実測に基づかない推測は書かない。

### 問い1 —— 30 接続予算は 5〜10 カラムで成立するか

**成立した。8 カラムで `connections: 9` / `peakConnections: 10`**（人間による実鍵での確認、2026-08-07）。予算 30 に対して 1/3 で、上限には近づいていない。

**注目すべきは 3 カラムのときと同じ値だったこと。** 縦断スライス（2026-08-05）の 3 カラムでもピークは 10 だった。**カラムを 2.7 倍にしても接続数が増えていない** —— Outbox の貪欲選択（[ADR-0025](../adr/0025-greedy-relay-selection-under-a-global-budget.md)）が著者の重なりを畳んでいることの、最初の直接的な証拠である。接続数を決めているのはカラム数ではなく**著者集合の広がり**であり、同じフォローリストから作ったカラムを何本並べても新しいリレーはほとんど要らない。

**したがって「カラム数 × 接続数」という見積もりは棄却してよい。** 予算 30 を脅かすのは、カラムを増やすことではなく、**互いに素な著者集合を持つカラム**（別の人のフォローリスト、まったく別のハッシュタグ）を増やすことである。次に予算を測るときはそちらを狙うこと。

### 問い2 —— `createSection` に画面外カラムの休止・優先度・破棄が要るか

**今は要らない。8 カラムで体感の重さは無かった**（同上）。followups の「縦断スライスを動かしてから決めるもの」節が保留していた API 判断は、**当面この形（休止も優先度も持たない）のままでよい**という実地の答えを得た。

**ただし別の遅さが観測された** —— 下の「初回描画が約 3 秒」を参照。これは画面外カラムの問題ではなく初回表示の問題であり、`createSection` のライフサイクル API では解けない。

### 問い3 —— `warmUpRouting` → `NostrSource` パターンの 3 箇所目は出たか

**出なかった。** 呼び出し箇所は `src/routes/v1.tsx` と `src/routes/debug/v1-section.tsx` の 2 箇所のみで、A-1 でも増えていない。`/v1-preview` が `/v1` へ移設された際もこのパターンをそのまま引き継いだだけで新しい呼び出し箇所は生まれていない。**「3 箇所目が出たら共通化する」の着手条件は依然として満たされていない。**

### 問い4 —— 派生ソースは `followees` だけで足りたか

**足りた。** `ColumnSource` の判別共用体は `{ kind: "literal" }` と `{ kind: "followees", kinds }` の 2 種のままで、4 種別（ホーム/ユーザー/ハッシュタグ/グローバル）を実装しても 2 つ目の派生 `kind` は要らなかった。`followees` が要ったのはホームだけで、他は `literal` で表現できた。

### 問い5 —— 4 種別のどれかが 2 本目のセクションを欲しがったか

**欲しがらなかった。** `DeckColumn.tsx` は `createSection` を 1 回だけ呼び、4 種別いずれも 1 本の時系列リストに収まった。ただし「A-1 の範囲では反証が出なかった」以上は主張できない —— 仕様 5 節が明記する反証条件（ユーザー詳細カラム）はまだ作っていない。詳細は [ADR-0003](../adr/0003-open-column-abstraction.md)「実装の段階」の A-1 の項。

### 問い6 —— ハッシュタグ（`authors` の無いフィルタ）は実際にどこへ繋いだか

**実鍵で動いた**（2026-08-07 確認）。自動テストは無いので**回帰を止めるものはまだ無い**。

経路: ハッシュタグ列の `ColumnSource` は `relays` を持たない `{ kind: "literal", filters: [{ kinds: [1], "#t": [tag] }] }`（仕様 4 節）。`resolveSource` はこれを `relays` キーの無い `NostrSource` に変換し、`SubscriptionManager.subscribe()` は `fallbackRelays ?? FALLBACK_RELAYS` を使う。`planQuery` は `authors` の無いフィルタを「誰でもいい」として `fallbackRelays` 全体へ同報し `unroutableAuthors` にカウントしない。`#replanOnce` が `fallbackRelays` を無条件に `pinned` へ足すため、この 3 本（`yabu.me`/`nos.lol`/`relay.damus.io`）は接続予算の貪欲選択で落とされない。

### 仕様が問うていなかったが実測で出たもの —— 初回描画が約 3 秒

**実鍵確認（2026-08-07）でタイムラインの初回描画は約 3 秒。** [ADR-0011](../adr/0011-performance-budget.md) の予算「初回イベント表示 2 秒」を超過している。

カラム数を増やしても接続数は変わらない（問い1）ので**A-1 が持ち込んだ劣化ではない。** 原因候補は 3 つ、どれがどれだけ効くかは未測定: ① ブートストラップの往復（`kind:3`→`kind:10002` の 2 往復無しにルーティング表が引けない）、② schnorr 検証（初回バーストで数百件を同時検証）、③ 接続確立そのもの（10 本ぶんのハンドシェイク）。

**測る手段が無いことが本当の問題である。** 初回イベント表示 2 秒は ADR-0011 の 7 指標のうち未測定の 5 つに含まれる（下記「満たしていない要件」）。**この指標を E2E で測れるようにすることを性能作業の最初に置くこと**、原因特定はその後でよい。

### 検索カラムは別に設計が要る（2026-08-07）

ハッシュタグ列で「フィルタで表現できる検索」の道は通ったが、**v0 の検索カラムはこの延長線上には無い。** 足す前に決める必要があるもの:

- **どのリレーへ問い合わせるか。** NIP-50 の `search` は対応リレーが限られ、Outbox（著者から引く）は使えない —— 検索は著者が未知だからこそ検索である。専用リレー集合を持つか、NIP-11 `supported_nips` で選別するか、`fallbackRelays` に委ねるかは `ColumnSource` に 3 つ目の `kind` が要るかの判断でもある
- **クエリ構文をどう扱うか。** v0 の `from:@...`/`since:` はローカルフィルタ（`authors`/`since`）とリレー全文検索（`search`）が混在する。どこまでローカルに翻訳しどこからリレーに委ねるかを決めないと、リレーごとに結果が変わる

旧実装（`src/features/Search/`）は[この v1 では無視してよい](../../CONTEXT.md)が、**この 2 点は v0 の実装が調査対象として役に立つ。**

## A-2 レンダラと関連イベント（2026-08-07）— 仕様 11 節の答え

**5 問とも「未取得」**（この節を書いている時点で実鍵確認が未実施）。以下は何を読めば・何をすれば答えが得られるかだけを書く。

### 問い5 —— `e`/`q` タグの pubkey は実際に入っているか

**未取得。** `event-refs.ts` の `replyTarget`/`quoteTargets` は pubkey を読める実装として存在し、あれば `Note.tsx` が `<Profile>` を即座に描く。ただしこれは**実装が使えることの確認**であり、**実在するクライアントがどれだけ pubkey を書いているか**は別問いで誰も観測していない。e2e フィクスチャは pubkey を明示的に書いて作ったもので実地の割合を示さない。**答え方:** 実鍵のタイムラインで、返信が「@name への返信」を親イベント到着より先に出す割合を多数の投稿で観察する（`e` タグに pubkey が無いクライアントの投稿では親が届くまで著者名が出ない）。

## 初回描画の分解（2026-08-10、実鍵）

開発者モードの読み取り値。8 カラム、実フォローリスト。

| 値 | 実測 |
|---|---|
| `firstRenderMs` | 369.50 ms |
| `warmUpMs` | 3577.70 ms |
| `verifyMs` | 4713.00 ms / 9470 件（0.498 ms/件） |
| `eventBatch` | 11（最大 30） |
| `profileBatch` | 1（最大 194） |
| `connections` / `peakConnections` | 9 / 10 |

**3 秒の正体はウォームアップだった。** `warmUpMs` 単独で ADR-0011 の「初回イベント表示 2 秒」を超えている —— schnorr 検証でも接続確立でもない。`warmUpRouting` は 2 相（インデクサ 4 本から `kind:3` → 全員分の `kind:10002`）あり、どちらも `collect()` で全リレーの EOSE/CLOSED/タイムアウトを待つため、最遅の 1 本が所要時間を決める。**`firstRenderMs` は測りたいものを測っていない**——370ms は「いずれかのカラムに最初のノートが出るまで」で、実際に出ているのは `mine`/`global` で**どちらもウォームアップを待たない**。人が見るホーム列はフォローリストが要るので 3.6 秒待ち、指標としては予算内なのに体感は 3 秒という食い違いはここから来る。

**検証コストは水和の設計を確定させた。** 0.498ms/件は 9470 件で 4.7 秒になる。IndexedDB キャッシュを `put()` で流し込めば起動時にこれを丸ごと払うため、[ADR-0018](../adr/0018-indexeddb-event-cache.md) の水和は信用済み挿入なしには成立しない。**バッチ分割は急がない**——最大でイベント 30 件・プロフィール 194 件、NIP-11 `max_message_length` の上限（最も厳しい `nos.lol` で約 1,950 件）に対して 1.5%/9.9% でしかない。

### C1 — 窓が末尾から追い出されると崩壊するバグ

窓の実装が当初「描画済み末尾アイテムの id」を境界として持っていたところ、`SortedEvents`（上限超過時に末尾＝最古を `pop()`）と組み合わさると、新着が先頭へ入って上限に達したセクションで境界アイテム＝末尾アイテム＝次に捨てられるアイテムになり、次の 1 件で境界ごと消えて件数が初期値（40 件）へ一気に崩壊した。描画済み 200 件が一斉にアンマウントされ `scrollHeight` が縮んでブラウザが `scrollTop` をクランプし、読んでいた位置が飛ぶ——「今すでに正しいので壊してはいけない」挙動を壊していた。

直し方は境界を**末尾ではなく先頭**に打つこと。末尾からの追い出しは先頭の添字に影響しないため崩壊が構造的に起きなくなる。実装は `render-window.ts`。

**仕様 8 節の残り 2 問は未取得**——初期 40 件・増分 40 件の妥当性、上限 200 件で足りるかは、いずれも実鍵で `/v1` を操作して体感で判断する必要がある（合成データでは答えが出ない）。

**jsdom の `ResizeObserver` スタブが実物と違っていたこともこの変更で露見した。** 実際の `ResizeObserver` は `observe()` 時の初回観測を必ず配信するが、`vitest.setup.ts` のスタブは何も撃たない no-op だった。`createElementSize` が同期的に `getBoundingClientRect()` を読んでいたため今まで表面化しなかった。製品コードから同期読み（ノートごとの強制リフロー）を外して初めてスタブの契約違反がテスト失敗として出た。スタブを実物に合わせた。

## アカウント境界とキャッシュの scope（2026-08-14）— 仕様 9 節の答え

決定は [ADR-0027](../adr/0027-account-boundary-and-cache-scope.md)。`CachePolicy` に「誰が見てよいか」(`scope: "public" | "account" | "session"`) を保持方針 (`retention`) とは独立した軸として足した。**既定は `"session"`（ディスクへ書かない）。** 名乗り忘れが「書かれない」に倒れるようにし、共有 IndexedDB に一度書かれたものは後からアカウント別に引き剥がせないという取り返しのつかなさを避けた。

### C1 — 本番の書き込み経路が `scope` を見ていなかった

永続化の実装は 2 つ（`createMemoryPersistence`/`createIndexedDbPersistence` → `selectForPersistence`）、本番(`/v1`)は後者を使う。`shouldPersist`（`cache-policy.ts`）を「分類の choke point」としたが、これを呼ぶのはデバッグルート専用の `createMemoryPersistence` だけで、本番の `selectForPersistence` は `retention.type` だけを見る独自の `switch` を持ち `scope` を一度も参照していなかった。**同じ規則を 2 箇所に別々に書いたことがそのまま食い違いを生んだ**——ミュート（kind:10000）に `scope: "account"` と正しく書いても本番は共有 DB へ書いてしまう。落ちるテストは 1 件も無かった。

直し方は `selectForPersistence` のループ先頭で `persistableScope(policy)` を門番にし、両経路が同じ判定を通るようにしたこと。ディスク境界のテストも足した（修正前に戻すと落ちることを確認済み）。

**今日、scope 判定を通る入力は 1 つも無い。** 登録済み 3 kind（0/3/10002）は全て `scope: "public"`、未知 kind は既定で `scope: "session"` かつ永続化しない。C1 が本番に残っていた期間も実害（別アカウントの漏洩）は起きていない。判定が効くのは `"account"` または永続化する `"session"` の kind が方針表へ載ったとき。

**繰り越し:** `"account"` の置き場は未実装（該当 kind が無いためメモリのみ、安全側）。アカウント切替の機構も未実装——ADR-0027 の「アカウントが変わったら read layer を捨てて作り直す」規則をコードにする前に固定した。

**仕様 9 節の 2 問は未取得**——切替実装後の読み取り層作り直しの体感、`"account"` 置き場が最初に必要になる kind（ADR-0027 はミュート #207 が最有力）は、いずれも実装に着手してから分かる。

## 書き込みの土台（2026-08-22）— 仕様の答え

イベントビルダ・`Writer` seam・置換可能イベントの read-modify-write・`Signer` への NIP-44 追加・compose の配線を実装した。残タスクは [v1-feature-inventory.md](./v1-feature-inventory.md) 1 節を参照 —— ここには**理由**だけを書く。

### `EventStore.remove()` は置換可能イベントの索引を張り直さないと「巻き戻したら全部消えた」になる

`#replaceable` は `kind:pubkey` を単一の id へ写す索引。素朴に `remove(id)` で `#events`/`#byTag` からだけ id を外すと、削除した版が直前に索引を上書きしていた場合、直前の版は `#events` に残っているのに `#replaceable` からは指されなくなり `latestReplaceable()` から永久に見えなくなる。フォローリストの楽観挿入を巻き戻すと、既存のフォロー全員が画面から消える形で症状が出る。`remove()` は削除した id が索引先だった場合、`#replaceable` からそのキーを消してから `#events` を走査し直前の版を再索引する（O(n) だが `remove()` は巻き戻しと明示的削除でしか呼ばれない）。

### `fetchLatest` は `identifier` を渡すと throw する

`EventStore.#indexReplaceable` は `kind:pubkey` でしか索引しておらず `d` タグを持たない。**kind:30078（デッキ）を保存する前に、この索引へ `d` を足す設計が要る。** また `fetchLatest` は `kind` に任意の数値を受け取れるが `#indexReplaceable` が実際に索引するのは kind 0/3/10000-19999 だけなので、`identifier` を渡さず kind:30000 番台で呼ぶと throw せず `latestReplaceable` が構造的に常に `undefined` を返す——「取得できなかった」ではなく「最初から索引されていないので常に無い」という別の失敗モードで、`d` を足す設計はこの違いも埋める必要がある。

### IndexedDB: 「削除ループを書き込みループの後に回す」では同一 flush 内の削除は勝てない

同一 flush に「保存」と「巻き戻し (delete)」が来たとき、削除ループを後に置けば削除が勝つと想定していたが実際は逆転する——retained（保存対象）の `put()` は非同期のカーソルコールバックから発行されるため、同期的な `delete()` より**後**に IndexedDB へ届き削除を上書きしてしまう。削除対象の id を retained の書き込みループから最初に除外する形に変えた（`indexeddb-persistence.ts` の `removalSet`）。IndexedDB の往復を検査するテスト基盤が無かったので `fake-indexeddb` を devDependency に追加した（[ADR-0020](../adr/0020-no-nostr-library-noble-primitives-only.md) の射程は Nostr 用ライブラリだけでテスト用フェイクは対象外）。同じ調査で `flush()` の早期 return ガードが `removals` の有無を見ておらず削除だけの flush が丸ごと飛ぶバグも見つけて直した。

### 楽観挿入の巻き戻しは「実際に自分が入れた分」しか消してはいけない

Nostr のイベント id は `pubkey, created_at, kind, tags, content` のハッシュで `sig` を含まない。compose は常に `tags: []` を送るため**同一秒内に同じ本文を 2 回投稿すると id が一致する**。1 回目の `put()` は `"inserted"` で publish も成功、2 回目は `"duplicate"` を返すが、2 回目の publish が全滅すると無条件の巻き戻しは `store.remove(id)` を呼び**1 回目の、実際にリレーへ届いた投稿を消してしまう**（表示だけでなく実データの損失）。`verifyOptimisticInsert` が verdict（`"inserted" | "duplicate"`）を返すようにし、`writer.ts` は `putResult === "inserted"` のときだけ `store.remove()` する。テストは同一 signer/draft/秒で実際に 2 回 publish して id を衝突させる形で書いた。

### `optimisticInsertMs` は `store.put()` の前から測らないと schnorr 検証が計測から抜ける

`onOptimisticInsert` フックは `store.put()` の**後**に発火するため、フック内で `performance.now()` を取ると `put()` 自体（schnorr 検証、ADR-0011 の 100ms 予算が本来見ている部分）が計測区間から抜け落ちる。`store.put()` 直前に取った `startedAt` を受け取る形にした。**この値を testid で見ている e2e は無く**、`writer.test.ts` のユニットテスト 1 本だけが正しさを支えている。

### くり返し踏んだ罠: フィクスチャの既定値が期待値と一致していると、その変異をテストが捕まえない

3 回、独立に発生した——`k` タグの値（`reaction.test.ts`/`deletion.test.ts` は既定 `kind: 1`、期待値も `["k", "1"]` なのでハードコード変異が緑のまま通る）、`buildReply` の `kind` アサーション（同型）、`removeFollow` の「該当する `p` だけを落とす」（フィクスチャの先頭がたまたま削除対象で単体では red にならない、隣接テストが救っている）。**フィクスチャの既定値を期待値と同じにすると、そのアサーションは実は何も検証していない。** フィクスチャの当該フィールドを期待値と異なる値にするか、変異させて red になるか確認する必要がある。**この一般則を書いた後、同じ defect が独立にもう1回起きた**——`src/core/nostr/build/` 配下 9 ファイルの `evt` テストフィクスチャが `kind: 1` を既定値として重複していた。**足りていないのは一般則の周知ではなく強制である。** 9 ファイルを共有フィクスチャに集約し、既定値を `kind: 1` 以外にする（または `kind` を必須パラメータにする）ことを次にビルダを 1 つ足す前にやること。

### 繰延事項（実行: [#301](https://github.com/eyemono-moe/streets/issues/301)/[#302](https://github.com/eyemono-moe/streets/issues/302)/[#303](https://github.com/eyemono-moe/streets/issues/303)）

- **`Mutation` は合成できない。** `type Mutation = (current: NostrEvent | undefined) => EventDraft` は `NostrEvent` を受け `EventDraft` を返すため `m2(m1(current))` が型検査を通らない。仕様が選んだ署名デバウンス戦略（「束ねる側が `mutate` の中で複数の変更を適用する」）をそのまま塞いでいる。直し方は `replaceTags`/`Mutation` の入力型を `{ tags: string[][]; content: string } | undefined` へ広げること——`NostrEvent`/`EventDraft` ともこの形を満たすので既存の呼び出し側は変更不要になる。合成結果の `kind` は後から適用した側のものになるが組み合わせる対象は同じ kind どうしだけなので問題はなく、実際に危険なのは**型が異なる kind の変更の合成を止められない**こと——`addFollow` と `addMute` を重ねると kind:10000 のイベントにフォロー用 `p` タグが混入した無意味なものが型検査を通ったまま出来上がる。
- **`evt` テストフィクスチャの重複（9 ファイル）**——「くり返し踏んだ罠」節を参照。
- **レビュー番号・タスク ID を運ぶコメントが repo 全体で 100 箇所を超えて残っている。** [コメントは非自明な WHY だけ](../../CONTEXT.md) の規則に反するが、新規に書かれたコメントはこの規則を守れている——違反は過去の持ち越しであり規則自体は機能している。

### 小さいもの（実行: [#304](https://github.com/eyemono-moe/streets/issues/304)〜[#310](https://github.com/eyemono-moe/streets/issues/310)）

## スレッド（2026-08-22）— 仕様の答え

根への 1 購読・`threadSpine`・`threadRoot()`・カラム内ナビゲーションスタック・押して開く導線・`Order` から `"thread-tree"` を削ることを実装した。残タスクは [v1-feature-inventory.md](./v1-feature-inventory.md) 2.2 節を参照——ここには**理由**だけを書く。

### `Order` の `"thread-tree"` は答えではなかった

背骨は**並べ替えではなく計算**である。祖先の連鎖を根まで辿り、選択したイベントを挟み、直接の返信だけを並べる——この形は `SectionReader` の「保持順を決める全順序」では表せない。順序関数はイベント 2 件を比べる形しか取れず「focus からの距離」という文脈依存の値を持てないので、`Order` に値を足す発想そのものが筋違いだった。実装したのは `threadSpine`（独立した純関数）で、`Order` からは `"thread-tree"` を削った。

### スレッドのソースは根の id でメモ化しないと、1 段進むたびに購読が張り直される

`createSection` は `source()` を読んで `SectionReader` を作り直すため、素朴に返す関数だと内容が同じでも呼ぶたびに新しいオブジェクトになり、返信を押して1段進むだけで購読が張り直され `items` が空から積み直しになる。`DeckColumn.tsx` は `threadRootId` を `createMemo` で根の id だけに絞り、フィルタ生成もさらに `createMemo` で包む。フィルタが `{ ids: [root] }` と `{ kinds: [1], "#e": [root] }` の 2 本で固定されるので、祖先を辿っても返信を辿っても購読は同じまま保たれる。

### キーボードではスレッドを開けない（実行: [#289](https://github.com/eyemono-moe/streets/issues/289)）

`useOpenThreadOnClick` はポインタ操作しか見ておらず `<article>` に `biome-ignore lint/a11y/useKeyWithClickEvents` で抑制している。直し方は自明ではない——`<article>` 自体を focusable にすると1カラム最大200件のノートが全部タブ順に入る。本来の答えは記事内に実体を持つ focusable な要素（タイムスタンプへのリンク、返信数ボタン等）を置くことだが、これは「押せる面をどこに置くか」という設計そのものの変更になるため決めずに残した。

### リアクションチップはクリック除外セレクタに入っていない（実行: [#290](https://github.com/eyemono-moe/streets/issues/290)）

`useOpenThreadOnClick` は `target.closest("a, button, [role='button'], input, textarea, [data-part='trigger']")` で対話要素上のクリックを除外している（`[data-part='trigger']` は `Avatar`/`ProfileHover` の `asChild` トリガーが role を持たないためアイコン押下でスレッドが開いてしまう不具合の修正で追加した）。リアクションのチップ（`data-testid="reaction-group"`）はただの `<div>` でこのセレクタに掛からない。今はクリックハンドラが無いので実害は無いが、「同じ絵文字のチップを押して同じリアクションを送る」が実装された瞬間、チップを押すとスレッドも開いてしまう。

### `threadSpine` の返信フィルタは focus 自身を除外していない（実行: [#291](https://github.com/eyemono-moe/streets/issues/291)）

祖先を辿る側は訪問済み集合 (`seen`) で自己参照を止めているが、直接の返信を集める側（`replyTarget(event)?.id === focusId` で絞るだけ）には同じガードが無い。実際には起こらない——Nostr の id はタグを含めたハッシュなので、これが起きるには id とタグの中身が一致するハッシュの不動点が要り現実的な攻撃経路ではない。ただし祖先側だけに対称なガードがある非対称は、次に触る人のために書いておく価値がある。

### 同じ `chevron-left-rounded` が 2 つの意味を持つ（実行: [#292](https://github.com/eyemono-moe/streets/issues/292)）

カラムのヘッダー左端は通常「カラムを左へ移動」、スレッドを開いている間は「戻る」に差し替わり、どちらも同じアイコンを使う。1 カラムの中では排他なので混乱しないが、複数カラムを並べたデッキではあるカラムの「戻る」が隣のカラムの「左へ移動」と横に並ぶ。

### `thread-spine.ts` は変異テストの対象に含めなかった（実行: [#293](https://github.com/eyemono-moe/streets/issues/293)）

純関数でテストも速く ADR-0029 と同じ扱いに値するが、ADR-0029 を書いた直後であり、まず今の範囲での運用感を見てから対象を広げるべきだと判断した。

### 繰延事項（実行: [#294](https://github.com/eyemono-moe/streets/issues/294)/[#295](https://github.com/eyemono-moe/streets/issues/295)）

- **`#e` 購読は Outbox ルーティングできない。** `threadSection` はカラムの明示リレーと、フォーカスしたイベント自身の `e` タグが運ぶリレーヒントを合わせて送るが、どちらも無ければ `planQuery` の fallback（`FALLBACK_RELAYS` への同報）に委ねるしかない。これは直せる余地が無い残余——`#e` フィルタは「誰が返信するか」を事前に知りようがなく Outbox ルーティングが構造的に効かない。
- **`MAX_ITEMS_PER_SECTION`（200）が背骨から落とすのは深さではなく幅。** `SortedEvents` は保持順の全順序で上限超過分を末尾から追い出すため、スレッドの根・祖先（会話の中で最も古い部類）は**深さではなく幅（返信の総数）が増えるほど先に追い出される。** 200 件を超える返信を持つスレッドは Nostr で珍しくない。根・祖先が追い出されても `ThreadView` は settled まで待ってから「取得できていません」を出すので**隠れない劣化**として届く。focus 自身は `useRender().store.get(focusId)` から直接補うため上限の影響を受けない（クリックした時点で画面に描かれていたイベントは必ず `EventStore` に入っている）。**残る本物の隙は返信側**——`threadSpine.replies` は 200 件上限で古い返信が落ちてもそれを示す手段を持たず、一部の返信が黙って欠けたまま表示され得る。
- **spec 6.2 節の深さドットは意図して落とした。** 深さを redesign のボードに合わせてドットで示す要求は不要と裁定し、仕様側もこの節から要求を削って実装と一致させた。

## 未着手のまま残っている設計上の課題

**タスクとしては [GitHub Issues](https://github.com/eyemono-moe/streets/issues) に登録済み。** ここに残すのは Issue の本文に収まらない背景である。

### `EventStore` が呼び出し側から渡される公開オプションになっている

[ADR-0018](../adr/0018-indexeddb-event-cache.md) は `EventStore` の seam 資格を取り消し `EventPersistence` を seam としたが、現状は `SectionReader` と `createSection` の両方でオプションとして露出しており**共有するかどうかを呼び出し側が決められる**。最初期の Critical はここから生まれた（共有 store で `put` が `"duplicate"` を返す経路）。IndexedDB 水和が入れば store は読み取り層のシングルトンになるほかない。

**着手は永続化の計画（後続 #4）の冒頭で行う。** 早く直すべきという当初案は誤りだった——(1) 呼び出し箇所は #4 までは増えない（デバッグルートのみで、増えるのはデッキとカラムを作る後続 #7）。(2) 今やると合成ルート（`EventStore`+ルーティング表#1+接続プール#3+`EventPersistence`#4）の形を、中身が1つしか分かっていない段階で決めることになり、残り3つを積んだ後に作り直すことになる。`SectionReader` 側のオプションは内部 seam（テストの `PassThroughStore` 注入用）として残してよく、外に出すべきでないのは `createSection` の公開インターフェースのほう。**同じ計画で水和経路の検証も決める**——`put()` は挿入のたびに schnorr 検証するため、IndexedDB キャッシュを起動時に流し込むと全件再検証で ADR-0011 の「初回イベント表示 2 秒」が埋まる。信用済み挿入の経路を足すかは `put()` のシグネチャの話であり永続化 #4 で決着させる。

### ~~`seenRelays` の帰属が検証されていない~~ — 修正済み

`"duplicate"` 経路がペイロード照合前に `seenRelays` へリレーを記録していたため、悪意あるリレーが既知の ID を送るだけで自分が配信していないイベントの提供者として記録された。Outbox（後続 #1）が `seenRelays` をリレーヒントとして読み始める直前に修正した——`"duplicate"` 経路の push を `isNostrEvent(event) && computeEventId(unsigned) === event.id` で門番する。イベント ID は署名対象フィールドの sha256 なので**ID の再計算がそのままペイロードの照合になり**、schnorr を伴わないため重複ごとの検証コストは発生しない。`put` の戻り値は照合が失敗しても `"duplicate"` のまま——ここで `"rejected"` を返すと既に保持している正規のイベントをセクションが取りこぼす。

### `reserved`（ブートストラップの予算迂回）が ADR-0025 の記述と食い違っている

[ADR-0025](../adr/0025-greedy-relay-selection-under-a-global-budget.md) はブートストラップのインデクサ（4 本）を `pinned`（予算を消費するが決して落とされない）として扱うと書いていたが、実装（`{ reserved: true }`）は `selectRelays` の `pinned` を経由せず `ConnectionPool.subscribe()` の予算チェックそのものを丸ごと迂回する**バイパス**である。ADR-0025 の該当段落は誤りとして訂正した。帰結は2つ——(1) ピーク同時接続数は `30 + |indexers|` = 34 になりうる（今日は到達しないが、未知の著者に遭遇して再ウォームアップする経路が入れば重なる。次の計画がこの経路を作るなら34という数を先に踏まえること）。(2) `pinned` と `reserved` という意味の違う2つの仕組みが同じ「30接続」という数字を別々に主張しており1つの数値に統一されていない。**裁定**: 統合スライスがこのコードにどのみち触れるため、今回はドキュメントを実装に合わせて訂正し `ConnectionPool` に `reservedSize` アクセサを追加するところまでで止める。予算の再構成は次の計画が1つの数値に対して行うこと。

### ~~死んだままのリレーが枠を永久に食いつぶす~~ — 修正済み

**実地で観測済み（実鍵検証、2026-08-05）。** `/v1-preview` を本物のアカウントで公開リレー網に対して動かしたところ `.onion` アドレス等 3 本が繰り返し接続に失敗し、恒久的に暗転する著者の枠を占有し続ける挙動を実演した。`#onConnectionDied` はソケットの枠を解放するだけでマネージャ側の状態には触れず、URL は `entry.opened`/`currentSet` に残り続け、`selectRelays` は「到達可能かどうか」の概念を持たないため `replan()` のたびに同じ死んだ URL を選び直していた。**リレーが恒久停止すると、そのリレーが担当していた著者は永久に暗転し、空いたはずの枠は誰にも使われない。**

これは「隠れた劣化」ではない——`unreachableRelays` として正直に報告され続ける。[ADR-0021](../adr/0021-reconnection-policy.md) が「死亡・復帰は再選択の契機にしない」と決めたのは瞬断のたびに churn を起こさないためで瞬断には正しいが、恒久喪失には対処していなかった。

**`selectRelays` に `degraded?: readonly RelayUrl[]` を追加して解決した。** `ConnectionPool.degradedRelays`（連続失敗が `DEGRADED_AFTER_FAILURES` に達した URL）を `SubscriptionManager.replan()` から渡し、候補集合の構築段階でこれに含まれる URL を完全に除外する——「最後の手段として残す」設計は採らなかった。到達不能なリレーに割り当てても被覆は増えず枠だけが無駄になるためである。degraded な URL しか宣言していない著者は `uncovered` に落ちる（[ADR-0011](../adr/0011-performance-budget.md) の「劣化を隠さない」に適う意図した挙動）。`pinned`（ユーザー明示指定・fallback・ブートストラップのインデクサ）はこの除外の対象外——黙って落とすと経路そのものが壊れる。復帰経路は `DEGRADED_COOLDOWN_MS`（300 秒）のクールダウンで確保した。

**訂正: 上の「解決した」は不完全だった。** `selectRelays` の純関数側は正しく実装されていたが、それを呼び直す `SubscriptionManager.#runReplan()` の内部呼び出し元は `subscribe()` と `#close()` の 2 つだけで、接続が死んで `degradedRelays` に積み上がっても、アプリのどの経路もそれを受けて `replan()` を呼び返していなかった。`.onion` が 4 回失敗して `degradedRelays` に入っても次にセクションが追加・削除されるまで選択結果には反映されず、原因だけ変えて（除外ロジックの欠落ではなく再選択の契機の欠落として）同じ症状を再現していた。

**`ConnectionPool.onDegradedChanged(listener)`（degraded への遷移を通知する新しいフック）と `SubscriptionManager` 側のバッチ配線（`#scheduleDegradedReplan()`、窓 200ms）を足して自動化し、初めて実際に閉じた。** 遷移の瞬間だけ通知し以後の失敗では再発火しないので、単発のブリップを再選択の契機にしないという ADR-0021 の方針は保たれる。バッチ窓は複数のリレーが同時に degraded へ遷移した場合（ネットワーク断など）に replan を 1 本へまとめるためのもの。**復帰側も同じ配線で閉じた**（`onDegradedChanged` は遷移両方向で通知し、`#clearFailures` を通る 3 経路が既存のバッチ窓に相乗りする）。詳細は [ADR-0021](../adr/0021-reconnection-policy.md) の「諦めない」と「再選択の候補から外す」は別の問い節を参照。

### ~~指数バックオフが実際には指数になっていない~~ — 修正済み

**実地で観測済み（実鍵検証、2026-08-05）。** 上記の到達不能な 3 本はいずれも単発の切断ではなく**およそ 3 秒間隔で失敗を繰り返し続けた**——コードを確認すると、これはバックオフの欠陥が予測する症状そのものだった。`#reconnect` は `connect()` の戻り値だけを見て `attempts` を 0 に戻すが、`connectRelay` は `new WebSocket(url)` を構築して即座に返るだけでソケットが開いたかどうかは見ていない。したがって恒久的に到達不能なリレーでも `connect()` は毎回「成功」扱いになり指数は 2⁰ から一度も伸びず、間隔は `RECONNECT_BASE_MS × (0.5 + random)` = 500〜1500ms のまま張り付く。観測された「約 3 秒」はこの一定間隔に DNS/TCP/TLS の失敗時間が乗ったもの。

[ADR-0021](../adr/0021-reconnection-policy.md) は「初回 1 秒からの指数バックオフ、上限 60 秒」と決めているが実装は食い違っていた。**帰結**: 30 本が同時に落ちた場合、ADR-0021 が防ごうとした「復帰時のバースト」ではなく「切断中ずっと毎秒 30 本のソケット構築が走り続ける」という、より高頻度な負荷になっていた。隠れた劣化ではない（`unreachableRelays` は正直に立ち続ける）。

**`RelayConnection` に `onOpen` の seam を足し、`attempts` のリセットを `connect()` の戻りではなく実際に接続が開いた時点に移して解決した**（`pooled.offOpen = connection.onOpen(() => this.#clearFailures(url))`）。失敗回数の記録も `ConnectionPool` 自身が持つ寿命に移り、`DEGRADED_AFTER_FAILURES`/`DEGRADED_COOLDOWN_MS` として結実した。

### CI が Playwright (e2e) を一度も実行していない

`.github/workflows/ci.yaml` には `check`/`test`（vitest）/`build` の 3 ジョブしかなく、`pnpm exec playwright test` を呼ぶジョブが無い。e2e 群はローカルで走らせれば本物のガードとして機能する（下記「満たしていない要件」参照）が、push のたびに自動で検査する仕組みが無いので e2e が守るはずの退行は CI では止まらない。

単純にジョブを足すだけでは済まない——(1) e2e は `nostr-rs-relay`/`nostr-rs-relay-2`（`postgres` 依存）を必要とし、CI ワーカーでの起動とシード手順が要る。(2) `e2e/console-warning.spec.ts` は旧実装の `/` を対象にしており現在の状態では失敗するので、素朴に配線すると初日から赤くなる——直す・対象を切り替える・除外するかを先に決める必要がある。**CI 配線は独立した作業として範囲外に置く。**

## 通知（2026-08-25 に繰延）

### 通知カラムの警告が 2 件同時に出ると、片方が嘘になる（実行: [#296](https://github.com/eyemono-moe/streets/issues/296)）

`column-alerts.ts` の「あなたの設定した read リレーに接続できません」は `source.kind === "notifications" && unreachable > 0` だけで出て**`viewerRelayListMissing` が真のときを除いていない**。自分の kind:10002 が引けず `FALLBACK_RELAYS` の 3 本も到達不能な状態では、正しい警告（「既定のリレーで待っています」）と嘘の警告（「あなたの設定した read リレーに接続できません」——実際に不通なのはアプリ組み込みの fallback で、ユーザーが設定した read リレーは存在しない）が同時に出る。`action`（「kind:10002 の read リレーを確認してください」）も存在しない設定の確認を促してしまう。直し方は条件に `&& !viewerRelayListMissing` を足すだけ。

### 通知に kind:16（汎用リポスト）を含めること（実行: [#297](https://github.com/eyemono-moe/streets/issues/297)）

**表示は既にできる。** `Repost.tsx` は kind:16 で `defaultRenderers` に登録済みなので `NOTIFICATION_KINDS` に `16` を足せばそれだけで通知に並ぶ。含めなかったのは「動作を確かめられないから」であって混ぜたくないからではない——kind:16 の対象は kind:1 以外（長文記事等）で v1 はまだ作れず、届くのは「他人が v1 の外で作った自分のコンテンツへの汎用リポスト」だけになり e2e のフィクスチャも組めない。**入れる条件**: v1 が長文を作れるようになるか、kind:16 を e2e で再現できるフィクスチャが組めるようになったとき。

### 通知カラムの read リレーが 30 接続予算を無制限に食う（実行: [#298](https://github.com/eyemono-moe/streets/issues/298)）

`resolveSource` が返す `relays` は `explicitRelays` として扱われ、`selectRelays` の結果に左右されず全 URL 必ず開こうとする（「ユーザーが名指ししたリレーを予算都合で落とさない」ため）。これまで `explicitRelays` はユーザーが自分で打った URL か `FALLBACK_RELAYS`（3 本）だけで件数はユーザーの手の内にあったが、通知カラムは初めて外部が決めた無制限のリスト（自分の kind:10002 の read 全部）を流し込む。**具体的な壊れ方**: read リレーを 18 本宣言している利用者が通知カラムを足すと `MAX_CONNECTIONS = 30` のうち 18 本が先に押さえられ、残り 12 本で全フォロイーの outbox を被覆することになり、溢れた分は診断値の裏に落ちてホーム列から著者が静かに消える。**上限を設けなかった理由**: 「どの N 本を残すか」の基準が要るが NIP-65 は `r` タグに順序の意味を与えていない。恣意的に切ると通知が実際に届いているリレーを落としうるので、予算を食うことより届く場所を黙って捨てることのほうが悪いと判断した。基準は人間の判断が要る。

### settle 前に fallback の実在リレーへ一瞬購読する（実行: [#299](https://github.com/eyemono-moe/streets/issues/299)）

`readRelays` は `warmUp()` に依存するため settle までは必ず `[]` を返し `FALLBACK_RELAYS` が載る。通知カラムは起動のたびに fallback 3 本へ投げ、settle 後に破棄して read リレーへ張り直す——read リレーを持っている利用者でも毎回起こる。害は接続の無駄と一瞬の内容差し替えで数秒で自己修正する。直すには `ResolveContext` に settle 済みかどうかを足す必要がある（上の「30 接続予算」の項と重なる）。

### `readRelays` は warmUp の 1 回きりに固定される（実行: [#300](https://github.com/eyemono-moe/streets/issues/300)）

`readRelaysFor` はシグナルではなく依存は `warmUp()` だけなので、warmUp 後に自分の kind:10002 が届く経路は事実上ない。warmUp 時に取れなければそのセッションの間ずっと fallback のまま・警告も出っぱなしになる。`followees` と同じ制約で新規の欠陥ではないが、通知では「一生届かない」という結果になる点が重い。

## NIP-46 bunkerログイン（2026-08-25）— 実装で確定した境界

最初の経路は `bunker://` だけに絞った。client/remote signer/user の 3 鍵を分け、client session key だけを versioned な localStorage へ保存する。user key は公開鍵しか受け取らない。NIP-07 と NIP-46 の切替は `ActiveSigner` へ集約し、画面の pubkey と `Writer` の署名器が別 session になる経路を作らない。

transport の NIP-44 は remote signer へ委譲できないため `@noble/ciphers` を直接依存に加え公式 vector で固定した。平文上限は 65,535 bytes とした（ブラウザで理論上限 4GiB を確保しないため。NIP-46 RPC の JSON には十分で、現行 NIP-44 が許す platform-specific な DoS 上限にあたる）。

kind:24133 の購読・publish は既存 `ConnectionPool` を共有する。bunker URI と `switch_relays` の返却値は 5 本を上限とし、切替先を 1 本も確保できなければ旧 relay を維持する。署名要求の自動 retry は重複承認と idempotency 未規定のため行わない。

**後続へ残るもの:** `nostrconnect://` と QR/deep link、NIP-46 の `nip44_encrypt/decrypt` を `Signer.nip44` へ公開する権限拡張、reaction/repost/follow/mute/kind:30078 追加時の再認可導線、client key を WebCrypto の non-extractable key として保持できるかの検証、`switch_relays` を合理的な間隔で再取得する運用。

## 他クライアントの実装調査で見つかった差分（2026-08-29）

rx-nostr/NDK/applesauce/welshman と nostter/Jumble/noStrudel/Coracle/Damustr/Primal を読み、streets に無い仕組みだけを残す。**どれも「壊れている」ではなく「まだ持っていない」である。**

### 購読数に上限が無い

`pool.subscribe()` はセクションごと・リレーごとに呼ばれる。同一リレー向けの REQ マージ（下記「同一リレー向けの REQ マージ」）が未実装なので、カラム 5 本×担当リレー 10 本なら 1 リレーに 50 本の REQ が向かいうる。**接続数の予算 30（[ADR-0011](../adr/0011-performance-budget.md)）は守れていても購読数は無防備である。** NIP-11 の `limitation.max_subscriptions` は既にパース済みだが `RelayInfoRegistry` は `max_limit` しか公開していない。nostter は宣言が無ければ 20 とみなす方式を採る——上限超過時にリレーが古い購読を黙って切ると、こちらからは EOSE 済みの正常な購読と区別が付かない。マージ実装時は NDK の制約（`limit` を持つフィルタは束ねない——`limit:200` の 2 本を 1 本に畳むとどちらも 200 件受け取れなくなる）も引き継ぐことになる。

### 「引いたが無かった」に有効期限が無い

`profile-requests.request(pubkey)` は `replaceableFetchedAt` が `undefined` なら必ず要求するため、kind:0 を持たない著者は**画面に出るたびに 200ms 窓の REQ へ載り続ける。** `event-requests` の `settled` も `request()` のたびに削除されるため同様に再要求が続く。Damustr は負のキャッシュ（`null` は 10 秒で捨てて再取得）を持つ。streets には `CachePolicy` があるので `missTtlMs` を足す形が素直。

### 水和したイベントがカラムに出てこない

`EventStore.hydrate()` は IndexedDB から本体を戻すが `SectionReader` は配達された id しか見ないため、**起動直後のカラムはリレーが同じイベントを再配送するまで空のまま**で、水和した本体はその間使われない。Jumble は id と `created_at` の組をキャッシュし復帰時に先に画面へ返して差分だけ取りに行く。**これは ADR-0024 と矛盾しない**——メンバーシップが経路依存であることと、経路がたどった結果を保存して復元することは別であり、保存するのは id と表示順だけなので本体を共有する形も崩れない。

### リレーヒントを読んでいるのに使っていない

`event-requests.ts` は `relayHint` を受け取るが使わない。nostter は二段階（既定リレーへ投げ、5 秒後も store に現れなければヒント先だけへ投げ直す）にしている——最初から使わないのはヒント先が接続を 1 本増やすため。**streets は接続予算 30 を持つのでこの「後から、見つからなかったものだけ」がむしろ噛み合う。**

### 署名検証がメインスレッドで同期

`EventStore.put()` は `verifyEvent()` を同期に呼ぶ。`verifyMs`/`verifyCount` は計測済みだが**その値を読んで判断したことがまだ無い。** nostter は Web Worker へ、Jumble/noStrudel は `nostr-wasm` を使うが**後者は ADR-0020 に反するので採れない**（Worker 化なら noble のままなので触れない）。ただし Worker 化は `put()` を非同期にしセクションへの配達順を変えるため、先に `verifyMs` の実測値を見てから判断すること。

### 完了判定に閾値が無い

`SectionReader.status` の `allSettled` は到達不能を除いた全リレーの `complete` を要求するため、生きているが遅いリレーが 1 本あるとカラムは `settled` にならない。welshman/Jumble/NDK はいずれも割合や打ち切りで解決する。**入れるなら打ち切ったことを `incomplete` に出さねばならない**——さもないと「待つのをやめた」が「全部見た」に化け [ADR-0015](../adr/0015-section-status-excludes-renderer-fetches.md) の区別が崩れる。優先度は低く、まず実際の待ち時間を測るのが先。

### 判断を保留したもの

- `hydrate()` が同期の全件ループ。nostter は `chunk` 合間に譲る。streets の水和件数は [ADR-0019](../adr/0019-two-bucket-cache-policy.md) の保持方針次第なので件数が分かってから判断する。
- negentropy（NIP-77）。コールドスタートの転送量は理論上最小になるが対応リレーが限られ ADR-0020 の下では自前実装になる。

### ADR-0024 の理由づけが強すぎる

[ADR-0024](../adr/0024-shared-bodies-per-section-membership.md) の「どのライブラリでも同じ理由で破れる」という一文は強すぎる。決定（本体は共有、メンバーシップはセクションが持つ）自体は正しいが、`EventStore` は既に `seenRelays` を持っており、ADR-0024 が挙げた 4 つの理由のうち 3 つ（取得先の違い、ページネーション位置、要求していないイベント）は式で表現できてしまう。再現できないまま残るのは `limit` の裁量だけで、実害は「別のセクションが何を取ったかでこのセクションの中身が変わる」こと。決定を支える本当の根拠は 3 つ——**ADR を直すならこれに差し替える**: (1) 網羅性を式が言えない（`filter(store)` は取り切ったかを言わない）。(2) 欠落の理由を返り値に置けない（`unreachableRelays` 等は取得の試みの属性で届いたデータの属性ではない）。(3) 破棄が成り立たなくなる（メンバーシップを毎回 store から計算するなら何も捨てられない。id の列として持てば列自体が参照カウントになる——9 節の「メモリ側の破棄戦略が未決」はこれと同じ問題を別の側から見ている）。3 つ目は交換条件であり、クエリとして計算する設計は何も捨てられない store と引き換えにしか成り立たない。

### `EventStore.subscribe()` が全体ストリームなので、通知コストが画面のアイテム数に比例する

`EventStore` は全変更を 1 本のストリームとして配り、購読者は毎回自分で関係の有無を判定する。`ReactionList.tsx` と `EventActionBar.tsx` はアイテムごとに購読しタグを走査するため、**1 イベント挿入あたりのコストが `O(描画中のアイテム数×そのイベントのタグ数)` になる**——描画 40 件で購読者 80 個、バーストで毎秒数百件流れると毎秒数万回のタグ走査がメインスレッドで回る。`EventStore` は `eventsByTag` 索引を既に持っているが**通知がその索引を使っていない。** 鍵つきの購読（`watch(key, listener)`、`WatchKey` は event/replaceable/tag の 3 種）に変えれば関係する購読者にだけ配られ、内部は `Map<string, Set<listener>>` 1 つで済み、`put()` は影響する鍵だけを計算して配ればよい。`onReplaceableChanged` は既に鍵つきに近い形（`account-settings.tsx`/`mute-list.tsx` が使用）なのでこれを一般化する形になる。`section-reader.ts`/`projected-writer.ts` の購読は全体ストリームのままでよく、**アイテムごとの購読者 2 つだけが問題である。**

## コードコメントから移した判断

コメントを新規参加者向けに整理した際、コードを読む上では要らないが、失うと同じ検討を招く判断をここへ移した。

### `fetchOnce` は接続予算を迂回しない

`collect()` が `pool.subscribe(..., { reserved: true })` を使うため `fetchOnce` にも同じ迂回を持たせたくなるが、**持たせていないのは意図的である。** 予算の外側にもう 1 系統の取得経路ができると 30 接続の上限が数字として意味を失う。迂回してよいのはブートストラップのインデクサだけで、ルーティングを解決できなければ何も始まらないためである。

### `PUBLISH_TIMEOUT_MS` は他のタイムアウトと同じ 10 秒

`bootstrap.ts` と `subscription-manager.ts` に揃えてある。10 秒という値自体に根拠があるのではなく**揃っていること**に意味がある。片方だけ動かすと、どのタイムアウトで落ちたかを症状から切り分けられなくなる。

### デッキの保存キーを pubkey だけに留めた範囲

`DECK_STORAGE_KEY_PREFIX` はアカウント境界を pubkey で切るだけの最小実装で、セッション・グローバルを含む三分類は範囲外として保留した。[ADR-0019](../adr/0019-two-bucket-cache-policy.md) の保持方針と揃える必要があるので、片方だけ先に決めない。

### `notification-filter` を UI から切り出している理由

判定をブラウザ無しで固定するため。`column-presets.ts` も同じ理由で切り出してある。

## 直さないと決めたもの（理由つき）

### `publish()` だけが触った新規 URL の接続失敗を degraded に数えること

`publish()` が誰も購読していない新しい URL へ接続しようとして `connect()` が同期的に例外を投げた場合、その失敗は `#failures` に記録されない。**数えない**理由は 3 つ——`degradedRelays` は `selectRelays` の入力であり読み取り側の関心事（[ADR-0025](../adr/0025-greedy-relay-selection-under-a-global-budget.md)）。publish は購読を残さないので除外→購読ゼロ→履歴消滅→再選択という振動はそもそも起こりえない。失敗自体は `publisher.ts` が `PublishResult.rejected` として表に出すので ADR-0011 の「劣化を隠さない」は満たされている。なおこの経路は同期的 throw に限られ、`connect()` がソケットを返した後に `PUBLISH_TIMEOUT_MS` 以内で死んだ場合は `#onConnectionDied`→`#scheduleReconnect` を通って数えられる。

### `EventStore.put` で検証を重複判定より前に移すこと

Critical（既知 ID を再利用した偽造イベント）を塞ぐ別解だが、重複のたびに schnorr 検証が走ることになる。Outbox では同一イベントが複数リレーから届くため 500 件×3 リレーで約 1,500 回の追加検証となり、ADR-0011 の「初回イベント表示 2 秒」を削る。**採用しない。**

### `websocket-relay-connection.ts` の `subId`/`eventId` の `typeof` ガード 4 箇所

「`Map<string, _>` のキー意味論により到達不能なデッドコード」という判定は誤りだった。`Array.isArray(message)` が `message` を `any[]` に絞るため、これらのガードは信用できないリレーと `NostrEvent` の間に存在する唯一の検証である。**削除しないこと。**

### ~~アンカー購読が「接続を握る」手段として REQ を悪用している~~ — 修正済み

`warmUpRouting` はフェーズ①②間で接続が落ちないよう、インデクサごとに絶対にマッチしない filter の購読を張っていた。一部のリレーがこれを `blocked: filters must specify at least one kind` で拒否して CLOSED を返すことが分かった。機能自体は壊れていなかった——接続を生かしていたのは REQ ではなく `ConnectionPool` のエントリで、アンカーの `onClosed` は no-op なのでエントリは残ったが、**それは偶然に寄りかかっていた**。欲しかったのは「接続の参照を 1 つ握る」ことだけで、REQ はそれを表現する API が他に無いから送っていたにすぎない。**`ConnectionPool.hold(url, options?): PooledHold | undefined` で解決した**——`hold()` は接続を確保し保持カウントを立てるだけで `subscribe()` を呼ばない。予算は `subscribe()` と同じに数える（生きたソケットを 1 本占有するため）。`NEVER_MATCHING_ID` 定数とアンカー宛イベントの会計は消えた。

## 後続 #3（接続プール）で扱うと決まったもの

### 同一リレー向けの REQ マージ

NIP-01 は 1 つの `REQ` に複数フィルタを載せることを認めており（複数フィルタは OR）、同一リレーへ向かう複数カラムのフィルタを 1 購読にまとめられる。**購読数はカラム数に比例しない。** 代償は 2 つ——EOSE は購読単位なのでまとめると [ADR-0015](../adr/0015-section-status-excludes-renderer-fetches.md) の `phase` をセクションごとに解決できなくなる。同じ `subscription_id` への REQ は置換なので 1 カラムを閉じるとグループ全体が張り直しになる。両立させる形は**初回取得中はカラムごとに購読を分け、settled 後は 1 本にまとめて張り替える**——定常状態の購読数はリレーあたり約 1 本に落ちる。これにより `max_subscriptions` はリレーの除外基準ではなく初回取得の並列度を決めるスケジューリングの入力になる（実測では 8〜300 と大きく開きがある。詳細は [research/2026-08-01-nip65-relay-selection.md](../research/2026-08-01-nip65-relay-selection.md) 5.4 節）。

**マージ自体は後続 #5 へ回った。** 再照合はマージの付随作業ではなく前提条件だと判定して切り出した結果、本スライス（後続 #4）が用意したのはその前提条件のほうである——マージすると 1 つの `subscription_id` に複数セクションのフィルタが相乗りするが、`EVENT` メッセージは `subscription_id` しか持たないため、届いたイベントをどのセクションへ配るか決める手段はフィルタ照合しかない。その照合器を `src/core/read/filter-match.ts` として用意し配線した（下記「解消済み」）。

## 解消済み

- **性能 — 1 イベントごとの全ソートと全再描画** — 解消。`section-reader.ts` の `#onEvent` が 1 件ごとに配列を 2 回ソートし 3 回コピーしていたのをやめ、保持順を `SortedEvents` に一本化した。保持順は `compareEvents`（`created_at` 降順、同値は `id` 昇順）で決まる全順序で固定し、挿入は二分探索、上限超過時は末尾を 1 件 `pop` するだけで済む。通知は `Scheduler` 経由でバッチする（`NOTIFY_BATCH_MS = 16`）——最初の変化でタイマーを 1 本張り以後の変化は既存のタイマーに相乗りする（デバウンスではない）。`items` と `status` は同期的に正しいまま保たれ遅れるのは通知だけである（[ADR-0015](../adr/0015-section-status-excludes-renderer-fetches.md)）。計測は `scripts/research/measure-section-reader-burst.mjs` に記録した（2,000 件で旧実装の約 157 倍高速、壁時計は環境依存で揺れるためこれは回帰を防ぐガードではない）。E2E は `e2e/section-cap.spec.ts` が測る。

  **当初の対処案「`#notify` をマイクロタスクで合流させ」は誤りだった。** NIP-01 のリレーは `["EVENT", subid, event]` を 1 イベント 1 メッセージで送り、ブラウザはメッセージごとに別タスクを回すため、マイクロタスクは次のメッセージが届く前に flush されて合流しない（500 イベント=500 タスク）。メッセージをまたいで合流するにはマクロタスク境界が要り、それが `Scheduler.setTimeout` によるバッチである。
- **ルーティング表の永続化** — 撤回。`EventStore` 内の `kind:10002` から導出する形にしたため専用の保存先も TTL も不要になった。永続化は [ADR-0019](../adr/0019-two-bucket-cache-policy.md) の「参照データ」バケットが `kind:10002` を保持すれば自動的に得られる。
- **生きているセクションを張り直す手段が存在しない** — 解消、ただし引き金は後続 #4（ローカルフィルタ照合）で変わった。再計画の機構（`replan()` が `#runReplan()` を回し変化したエントリにだけ `onPlanChanged` を配る per-section diff、`SectionDelivery.onRelayRestarted(relay)` 通知）は生きていて正しく動く。接続自体は張り直さない（同一プール接続で close+subscribe）ので [ADR-0016](../adr/0016-routing-bootstrap.md) の「解決後に張り直す」が指す再購読と接続の張り直しを混同していない。**ただし `kind:10002` の到着を検知して自動でこれを起動する経路は無い。** 当初あったデバウンス再計画の引き金は、ローカルフィルタ照合が `matchesAnyFilter` を導入した際に削除された——`kind:10002` はセクションが要求していない限り store へ届かないため。生きているのは公開 `replan()` と `scheduler` オプションのみで、**今この機構を動かすのは明示的な `replan()` 呼び出しだけ**である。水和や再ウォームアップなど「ルーティングを変えうる入口」を実装する側が、その入口から `replan()` を呼ぶ責任を持つ。
- **`RelayConnection` に接続単位のライフサイクル通知がない** — 解消。`onClose(listener): () => void` を追加し購読単位の `onClosed` とは別にソケットそのものの死を通知する。`ConnectionPool` はこれで「ソケットの死」と「レート制限による個別 CLOSED」を区別できるようになり、死んだ接続を即座に予算とレジストリから外す。再接続（[ADR-0021](../adr/0021-reconnection-policy.md)）もこの通知を起点に組まれている。
- **接続数はフォロー人数に比例して無制限に増える** — 解消。`ConnectionPool` が唯一の接続開設点になり `MAX_CONNECTIONS = 30`（[ADR-0011](../adr/0011-performance-budget.md)）を全経路で強制する。著者ごとの先頭 N 本方式は `selectRelays` による貪欲被覆選択（[ADR-0025](../adr/0025-greedy-relay-selection-under-a-global-budget.md)）へ置き換わった。予算超過で被覆できない著者は `incomplete.uncoveredAuthors` として黙らず報告する。
- **リレーが配信したイベントをフィルタに再照合していない** — 解消。`SubscriptionManager.#handlersFor` が組み立てる `onEvent` は `store.put` より前に `matchesAnyFilter` で判定し、`bootstrap.ts` の `collect()` にも同じ判定を入れて信頼境界を揃えた。捨てた件数は `unrequestedEventsByRelay`/`WarmUpResult.unrequested` に現れる。`e2e/relay-lies.spec.ts` が悪意あるリレーを再現し、要求していないイベントが `items` に出ないこと・カウンタが動くこと・正当なイベントは従来どおり届くことを主張する。
- **`tsconfig.e2e.json` がルートのビルドグラフに載っておらず `pnpm typecheck` が `e2e/` を検査しない** — 解消。`tsconfig.json` の `references` に `tsconfig.e2e.json` と新設の `tsconfig.test.json` を追加した。相対 import に `.js` 拡張子を足す機械的な修正が必要だった（`NodeNext` の規約）。この配線自体が既存の型エラーを 7 ファイル分表面化させた（対応は `tsconfig.test.json` の `exclude` で除外、報告のみ）。

## 満たしていない要件

[ADR-0011](../adr/0011-performance-budget.md) は性能予算が**E2E で測定可能でなければならない**と定めている（測定できない予算は要件ではなく願望である）。7 指標のうち 30 接続上限と 1 セクションの保持件数上限（当初 500 件、現在 200 件）が測定済みで、残る 5 指標は未測定。

**「E2E が存在しゲートする」と「CI がその E2E を実行している」は別の主張である。** ~~CI は Playwright を一度も実行していない。~~ **これは解消済み**——`ci.yaml` には `e2e` ジョブがあり、ローカルリレーを立てて実行する（この誤った記述を信じて別文書に同じ誤りが生まれたため取り消し線で残す）。ただし push のたびに自動で検査する仕組みは依然として無く、CI 配線自体は別の follow-up。

- **30 接続上限** — 解消済み。`e2e/connection-budget.spec.ts` が予算超過なし・貪欲被覆・落とした著者の報告を測る。実ソケットが死んで実リレーが復帰することは `e2e/relay-recovery.spec.ts` で測る。
- **200 件上限**（当初 500 件から変更） — 解消済み。`e2e/section-cap.spec.ts` が 600 件 seed し `phase: settled` 到達時点で `items` がちょうど 200 で止まることを主張する。
- 残る 5 指標（カラム数、初回表示 2 秒、操作反映 100ms、メモリ等）は未測定。**「初回イベント表示 2 秒」は実地で超過が報告された**（約 3 秒、上の「初回描画が約 3 秒」節）——測定手段が無いまま超過だけが分かっている状態で、5 つのうちこれを最初に測れるようにすること。**「カラム数」は実地で 8 カラムまで確認できた**（`peakConnections: 10`、体感の重さ無し）が E2E では未測定。
