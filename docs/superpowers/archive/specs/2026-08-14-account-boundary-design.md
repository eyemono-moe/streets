# アカウント境界と機密情報の分類 — 設計

## 0. このスライスは何のためにあるか

`EventStore` と IndexedDB は今どのアカウントのものでもない。デッキは pubkey ごとに分かれている（`streets.v1.deck.<pubkey>`）が、イベントの置き場は 1 つである。

**今この瞬間に漏れているものは無い。** 永続化されているのは kind:0（プロフィール）と kind:10002（リレーリスト）だけで、どちらも公開・著者キーのイベントである。kind:3 は `retention: none` で書いていない。

**危ないのはこれからである。** ミュート（kind:10000）や既読、NIP-44 の復号結果を足すとき、`cache-policy.ts` へ 1 行足すだけで無分別に書けてしまう。分類を強制する仕組みが無い。**混ざった後に引き剥がすのは非常に高くつく。**

前提知識は [CONTEXT.md](../../../../CONTEXT.md)、決定は [docs/adr/](../../../adr/)、スライスの記録は [read-layer-followups.md](../../../design/read-layer-followups.md)。残タスクは [GitHub Issues](https://github.com/eyemono-moe/streets/issues)。

## 1. 何が本当にアカウント単位なのか

**Nostr の性質上、`EventStore` に入るものはすべてリレーから来た署名済みの公開イベントである。** 「公開イベント本体は共有してよい」は EventStore のほぼ全体を指す。本当にアカウント単位にすべきものは、イベントそのものではなくその周辺にある。

| もの | 例 | 性質 |
|---|---|---|
| 署名済みイベントの本体 | kind:0 / 1 / 6 / 10002 | 誰が見ても同じ。共有してよい |
| 閲覧者の鍵で導いた派生物 | NIP-44 の復号結果、kind:10000 の暗号化 content の中身 | **イベントではない。** 鍵を持つ人にしか作れない |
| 閲覧者に紐づくローカル状態 | 既読、UI 状態 | イベントではない。EventStore の外 |

**実際に起きる害は「別アカウントの DB を覗かれること」ではない。** 同一オリジンなので、どちらにせよページの JS からは両方読める。**害は誤って画面に出ることである** —— A のミュートが B に効く、A しか取っていないイベントが B のタイムラインに出る。この設計が防ぐのはそちらである。

## 2. 決めること

**3 つの分類を `CachePolicy` の必須フィールドにし、既定を fail-closed にする。**

| `scope` | 意味 | 置き場 |
|---|---|---|
| `"public"` | 誰が見ても同じ署名済みイベント | 共有 DB（`streets.v1`） |
| `"account"` | その閲覧者にしか意味がない | そのアカウント専用の置き場 |
| `"session"` | ディスクへ書かない | メモリのみ |

**既定は `"session"`。** 分類を名乗らない kind は共有もされず永続化もされない。永続化したい kind は `"public"` を明示的に名乗るしかない。

### 2.1 なぜ既定を `"session"` にするか

`shouldPersist` は今 `retention.type !== "none"` で決めており、既定の `retention` が `none` なので**結果として** fail-closed になっている。しかしそれは「保持方針」という別の軸がたまたまそう働いているだけで、「アカウントをまたいで見せてよいか」を誰も表明していない。

`scope` を別の軸として立て、既定を `"session"` にすることで、**永続化したい人は「これは誰が見ても同じイベントだ」と名乗る**ことになる。名乗り忘れは「書かれない」に倒れる。

### 2.2 `"account"` の置き場は今回作らない

**該当する kind が 1 つも無い。** 作るのは、最初にアカウント単位で永続化したいものが現れたときでよい。

後から DB を足すのは安い。**高くつくのは共有 DB に混ざった後に引き剥がすこと**で、それは既定 `"session"` が構造的に防ぐ。`"account"` を名乗った kind は、置き場が用意されるまでは単に永続化されない（メモリのみ）—— 安全側であり、機能としても「リロードで消える」だけである。

## 3. メモリ側の境界

**アカウントが変わったら read layer を捨てて作り直す。** in-memory の `EventStore` ごと破棄する。

理由は 1 節の「害は誤って画面に出ること」である。`"public"` なイベントまで一緒に捨てることになるが、それらは共有 DB から水和し直せる。`"account"`/`"session"` のものだけを選んで捨てる仕組みを作るより、全部捨てるほうが**取りこぼしが構造的に起きない**。

**この規則は今回コードにしない。** アカウント切替の経路が 1 つも無いので、`createReadLayer` にアカウントを渡しても誰も使わない引数が増えるだけになる。**今回やるのは規則を ADR に固定することだけ**で、機構は切替を作る人が作る —— そのとき `createReadLayer` の呼び出し元（`v1.tsx`）が dispose して作り直せばよく、`createReadLayer` 自身は変えなくてよい。

**分類（2 節）と違って、これを先に作る必要は無い。** 混ざって困るのは**ディスクに書かれたもの**であり、メモリは切替を作る瞬間に一度考えれば済む。ディスクのほうは、分類を忘れた 1 行が入った時点で取り返しがつかない。

## 4. ログイン前の水和を壊さない

`createReadLayer` は今**ログイン前**に作られ、その場で水和を始めている。拡張機能の `getPublicKey()` 応答待ちと並行させるためで、実測で `firstRenderMs` 356→112.9ms、相② 1497→651ms の効果があった（[read-layer-followups.md](../../../design/read-layer-followups.md)）。

**この並行を保つ。** 共有 DB（`"public"`）はアカウントに依らないので、ログイン前から水和できる。アカウント専用の置き場ができたときも、そちらの水和だけがログイン後になる。

**これが案「DB をアカウントごとに完全に分ける」を採らなかった理由である。** 分類の取り違えは起こらなくなるが、ログイン前に水和を始められなくなり、実測で得た並行の利得を手放すことになる。

## 5. 範囲

**含む。** `CachePolicy` に `scope` を必須フィールドとして足し、既定を `"session"` にする。既存 3 kind（0 / 3 / 10002）の分類。`shouldPersist` が `scope` を見るようにする。決定（3 分類・fail-closed・切替時にメモリを捨てる規則）を ADR にする。

**含まない。** `"account"` の置き場の実装（2.2）。アカウント切替の UI と、切替時にメモリを捨てる機構（3 節）。NIP-44 の復号そのもの。既読状態。ミュート機能（#207）。`createReadLayer` の引数は変えない。

## 6. 既存 3 kind の分類

| kind | `scope` | 理由 |
|---|---|---|
| 0（プロフィール） | `"public"` | 誰が見ても同じ |
| 10002（リレーリスト） | `"public"` | 同上 |
| 3（フォローリスト） | `"public"` | **イベント自体は公開である。** 永続化しないのは `retention: none` という別の理由（古いメンバーシップで購読すると外した著者を画面から消せない）であって、アカウント境界の問題ではない |

kind:3 を `"public"` としつつ `retention: none` のままにするのは、**2 つの軸が独立していることをそのまま表す**ためである。混ぜて 1 つのフラグにすると、後から「共有してよいが保持はしたくない」を表現できなくなる。

## 7. エラー処理

| 起きること | 扱い |
|---|---|
| 分類の無い kind を永続化しようとする | 書かない（既定 `"session"`）。**例外は投げない** —— 1 件の未分類 kind でカラムを落とさない |
| `"account"` の kind を永続化しようとする | 置き場がまだ無いので書かない。メモリには載る |
| アカウントが未確定（ログイン前） | 共有 DB だけを水和する。`"account"` は対象外 |

## 8. テスト

**ユニット（vitest）**

- 分類の無い kind は `shouldPersist` が false（**既定が fail-closed であること** —— 2.1 の核心）
- `"public"` かつ `retention` が `none` でない kind だけが true
- `"public"` でも `retention: none` なら false（kind:3。2 つの軸が独立していること）
- `"account"` は今は false（置き場が無い）
- `"session"` は false

**構造**

- **`POLICIES` の全エントリが `scope` を明示していること。** 型で必須にするので普通は書き忘れられないが、`as` などで抜ける余地を塞ぐ

2. **`"account"` の置き場が最初に必要になるのはどの kind か。** ミュート（#207）が最有力だが、実際に作るときまで分からない
