# NIP-09 削除依頼の表示反映 — 設計

## 1. 目的

`EventStore` は kind:5 の `e` タグを対象 id だけの tombstone として永続化し、
次回の水和で対象を除外している。しかし、生きているセクションから対象を消す経路は
無く、削除依頼者と対象著者が一致するかも検証できない。

このスライスでは、NIP-09 の削除依頼を到着順にかかわらず現在の表示へ反映し、
ローカルで楽観挿入した削除依頼の publish が全滅した場合は元の表示へ戻す。
対象 id だけを保存する現在の永続化も、検証に必要な削除依頼イベントを保存する形へ
置き換える。

## 2. NIP-09 と採る表示方針

現在の NIP-09 は kind:5 の `e` と `a` を削除対象とする。クライアントが `e` の対象を
隠す前には、削除依頼と対象イベントの `pubkey` が同じことを必ず検証する。
`a` は座標に含まれる pubkey が削除依頼者と一致する場合だけ受け付け、削除依頼の
`created_at` 以下の版を対象にする。削除依頼を対象にした削除依頼は無視する。

streets は有効な削除対象を完全に隠す。削除理由への置き換えや「削除済み」カードは
このスライスでは出さない。ユーザーが操作できない診断表示を通常画面へ増やさず、
カラムの保持件数にも削除済みイベントを数えないためである。

`e` だけを実装して `a` を後回しにはしない。どちらも削除依頼の真正性と由来を保持する
同じ永続スキーマを必要とし、ここで bare id のスキーマをもう一度延命すると次の変更で
再び破棄移行が必要になる。

## 3. 責務の境界

### `EventStore` — 可視性の唯一の判定者

kind:5 の意味を持つのは `EventStore` とする。署名検証済みイベント本体、置換可能
イベントの版、タグ索引を既に所有しており、削除依頼と対象著者を同じ信頼境界内で
比較できる唯一の場所だからである。

`EventStore` は次を持つ。

- 削除依頼 id から検証済み kind:5 への索引
- `e` の対象 id から削除依頼 id への索引
- 正規化した `a` 座標から削除依頼 id への索引
- 削除で隠れている本体。公開の `get()`、`eventsByTag()`、置換可能索引からは外す

対象を物理削除しない。publish 全滅で kind:5 を巻き戻したときに本文と取得元を復元
できなくなるためである。隠した本体はセッション中だけ内部に保持し、別の有効な
削除依頼が残っていなければ元の索引へ戻す。

### `SectionReader` — 経路依存のメンバーシップを維持

どのセクションが対象を受け取ったかは `SectionReader` だけが知る（ADR-0024）。
`EventStore` が全セクションを走査したり、store 全体からフィルタを再評価したりしない。

`EventStoreChange` に可視性の `hide` / `show` を追加し、`SectionReader` は start 中だけ
store を購読する。`hide` では `SortedEvents` から対象を外して「このセクションの
非表示メンバー」として id を覚え、`show` ではその id だけを戻す。通常の物理
`remove` は復元候補にしない。`stop()` は store 購読と非表示メンバーも破棄する。

削除依頼が対象より先に届いた場合、`EventStore.put()` は後着の対象を非表示本体へ
入れて `"hidden"` を返す。`SubscriptionManager` は `"rejected"` と違ってその id を
セクションへ配り、`SectionReader` は本文を表示せず非表示メンバーだけを記録する。
これにより、その削除依頼がローカル publish の巻き戻しで消えた場合も元の
メンバーシップへ戻せる。

### `ProjectedWriter` — 楽観表示も同じ可視性へ従う

`SectionReader` と別に保持している直近の楽観イベントも削除対象になりうる。
`ProjectedWriter` は store の `hide` / `show` を購読し、対象 entry を削除せず
非表示にする。kind:5 の publish 全滅で `show` が来れば再び投影する。

## 4. 削除の状態遷移

### 対象が先にある

1. kind:5 の署名と id を通常どおり検証する
2. 削除依頼を store と削除索引へ入れ、永続層へ渡す
3. `e` の対象、または `a` の該当版を探す
4. 対象が kind:5 でなく、著者が一致する場合だけ可視索引から内部の非表示領域へ移す
5. `hide` を通知し、各セクションと楽観一覧から消す

### 削除依頼が先にある

1. kind:5 を削除索引と永続層へ保存する
2. 後から対象が `put()` された時点で、該当する削除依頼を著者込みで照合する
3. 一致すれば公開索引へ入れず非表示領域へ置き、`"hidden"` を返す
4. セクションは配信された id を非表示メンバーとしてだけ保持する

### 削除依頼の巻き戻し

`Writer` が楽観挿入した kind:5 の publish が全滅すると、既存どおり
`EventStore.remove(deletion.id)` を呼ぶ。store はその削除依頼だけを索引と永続層から
外し、影響した対象を再判定する。別の有効な削除依頼が残る対象は隠したまま、
一つも残らない対象だけを可視索引へ戻して `show` を通知する。

同じ対象に複数の削除依頼がある場合も、削除依頼 id ごとに由来を保持するため、
一件の巻き戻しが他の tombstone を消さない。

## 5. `EventPersistence` と IndexedDB

`deletedIds: string[]`、`saveDeletions(ids)`、`deleteDeletions(ids)` は廃止する。
代わりに、署名検証済みの kind:5 イベント自体を専用領域へ保存する。

```ts
type EventPersistence = {
  load(): Promise<{
    events: PersistedEvent[];
    deletionRequests: NostrEvent[];
  }>;
  saveDeletionRequest(event: NostrEvent): void;
  deleteDeletionRequest(id: string): void;
  // 既存の save / delete / dispose
};
```

起動時は削除依頼を先に索引し、その後に通常イベントを水和する。削除依頼の pubkey、
`created_at`、対象種別、依頼 id が残るため、後着の対象にも真正性と時刻条件を適用できる。

IndexedDB は version 2 とし、既存方針どおり upgrade 時に `events` と `deletions` を
破棄して再作成する。`deletions` の key は削除依頼イベントの id とする。version 1 の
bare target id は著者を検証できず安全に移行できない。通常イベントの cache も同時に
破棄されるため、旧 tombstone だけを失って cache 上の対象が復活する中間状態は作らない。
リレーは削除依頼を保持・配信すべきという NIP-09 の前提に従って再取得する。

## 6. `PutResult` と書き込み境界

`PutResult` に `"hidden"` を追加する。これは署名不正の `"rejected"` ではなく、正当な
イベントだが既存の削除依頼により表示しない状態である。

読み取り側の `SubscriptionManager` は `"hidden"` でも id をセクションへ配送する。
書き込み側の `verifyOptimisticInsert` は `"hidden"` を楽観表示・publishへ進めない。
一度削除した同一 id の再送で表示を復活させず、ユーザーには内容か時刻を変えた新しい
イベントとして投稿し直す必要があることをエラーとして返す。

## 7. `a` タグの扱い

`a` は `<kind>:<pubkey>:<identifier>` を自前で解析する。kind は addressable event の
範囲、pubkey は64桁hex、identifier は空文字を含め残り全部とする。座標の pubkey が
削除依頼者と一致しないもの、不正な座標、対象が kind:5 のものは無視する。

同じ座標のうち削除依頼の `created_at` 以下だけを隠す。それより新しい版は、著者が
削除後に公開した新しい内容なので表示する。削除依頼を巻き戻した場合は、他の削除依頼に
覆われていない版を戻し、置換可能索引は可視な版の中から通常の全順序で最新版を選び直す。

## 8. 今回含めないもの

- 削除ボタンや確認ダイアログ。kind:5 builder と Writer の接続は別の UI スライス
- 通常カラムへ kind:5 を自動で追加取得する購読。全 kind:5 の無制限購読ではなく、
  表示対象の `e` id / `a` 座標をリレーごとに束ねる設計が別途必要。このスライスは
  kind:5 が読み取り層へ到着した後の適用を担当する（[#333](https://github.com/eyemono-moe/streets/issues/333)）
- 削除理由の表示、「削除済み」カード、削除が完全ではない旨の警告
- リレーからイベントを実際に消すことの保証
- kind:5 以外のモデレーション、ミュート、NIP-62 Request to Vanish
- 非表示本体の長期的なメモリ破棄。共有 store 全体の破棄戦略と同じ未決事項であり、
  このスライスだけで別の LRU を作らない

## 9. 検証

ユニットテストは少なくとも次を固定する。

- `e`: 対象先着 / 削除依頼先着、著者一致 / 不一致、削除依頼自身を対象にした場合
- `a`: 同じ座標の削除時刻以前だけを隠し、新版は残す
- 同一対象への複数依頼と、一件だけの巻き戻し
- kind:5 の publish 全滅で SectionReader と ProjectedWriter の表示が戻る
- `SortedEvents.remove()` が id 集合と配列を同時に更新する
- Memory / IndexedDB の両実装が削除依頼イベントを往復し、同一バッチの保存より
  巻き戻しを優先する
- version 2 が旧スキーマを破棄して同じ二つの store を再作成する
- `"hidden"` を読み取り側は配送し、書き込み側は publish しない

ブラウザ E2E は、kind:5 を明示取得する専用カラムで対象先着と削除依頼先着を一つの
spec で通し、別著者による削除依頼では対象が残ることも対照として確認する。ローカルの楽観巻き戻しはリレー応答を人工的に
全滅させる必要があり、決定的に作れるユニットテストを担当とする。

「捕まえる変異」を書いたテストは、対象の行を実際に変えて赤を確認してから戻す。
`src/core/write/**` の変更には `pnpm mutation`、ブラウザを含む最終入口には
`pnpm verify:all` を使う。
