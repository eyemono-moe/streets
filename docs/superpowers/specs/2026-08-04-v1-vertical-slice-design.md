# v1 縦断スライス — 初めて人が触れる形にする

読み取り層の続きではなく、**ログインから投稿までを縦に貫く最小の動くもの**を作る。

**この spec は意図的に短い。** 直前に「ドキュメントが実装の 4 倍あり、維持コストが負の収益になっている」と判定した（[followups](../../design/read-layer-followups.md) の外部レビュー節）。コードから復元できない判断だけを書く。

## 0. なぜこれを次にやるか

[followups の「外部レビュー（2026-08-04）」](../../design/read-layer-followups.md)に全文がある。要点だけ: v1 は main から 201 コミット先行し、読み取り層 3,056 行・そのテスト 6,142 行・docs 12,240 行を積んだが、**それを使っている画面はデバッグルート 1 本だけ**だった。要件が使用によって検証されていない部品に厳密さを注いでいた。

[ADR-0002](../../adr/0002-v0-parity-before-cutover.md) は本番切替の戦略を決めているだけで、**開発の順序を規定していない**。内部ルート `/v1-preview` で縦断スライスを動かすことは ADR-0002 と両立する。

## 1. 範囲

**入れる**: NIP-07 ログイン / 3 カラム（ホーム = フォロー相手の kind:1・単一著者・明示リレー）/ kind:0 プロフィール表示 / 投稿（楽観的挿入つき）/ リロード復元。

**入れない**: NIP-78 デッキ保存（[ADR-0013](../../adr/0013-deck-persisted-to-nip78.md)、今回は localStorage）/ レンダラ登録機構（[ADR-0003](../../adr/0003-open-column-abstraction.md)）/ 宣言的 `needs` の一般形（[ADR-0017](../../adr/0017-declarative-renderer-needs.md)）/ IndexedDB 永続化 / モバイル対応（[ADR-0009](../../adr/0009-mobile-single-column-view-only-editing.md)）/ REQ マージ。

**3 本目（明示リレーカラム）は最後に置き、時間が押したら落とす。** 必須ではない。

**このスライスは直近のどれより大きい。** 新規要素が 4 つあり、そのうち署名器・書き込み経路・デッキ・UI は v1 側にコードが 1 行も無い。**それでも分割しない** —— 縦に貫くことがこのスライスの目的そのものであり、横に切ると元の失敗に戻る。代わりに各要素を 2 節のとおり薄く保つことで大きさを抑える。

## 2. 「薄く作る」の意味

承認済み ADR を実装しないのではなく、**まだ実装しない**。タイムラインを一度も見ないまま要件を推測するのが、今回正そうとしている失敗だからである。

| 要素 | 薄い版 | 一般形はどこへ |
|---|---|---|
| カラム描画 | kind:1 用コンポーネント 1 つを直に書く | ADR-0003 |
| プロフィール | プロフィール要求のコアレッサ（4 節） | ADR-0017 |
| デッキ保存 | localStorage + `version` フィールド | ADR-0013 |
| 書き込み先 | 自分の kind:10002 write リレー、無ければハードコード | UX 調査は実装時 |

**このスライスの成果物は「動くもの」ではなく「押し返し」である。** 薄く作れば、`createSection` の `{ items, status, loadMore }` で足りない箇所が実物として出る。足りなければ、それが一般形の**根拠つき要件**になる。

## 3. 新しく作るもの

**`src/core/signer/`** — [ADR-0008](../../adr/0008-signer-only-key-handling.md)（秘密鍵を保持しない）を型で強制する seam。

```ts
export type Signer = {
  getPublicKey(): Promise<string>;
  signEvent(template: UnsignedEvent): Promise<NostrEvent>;
};
```

NIP-07 実装と fake（`fake-relay-connection.ts` と同じ位置づけ）。**`secretKey` という語がこの層のどこにも現れないこと**が ADR-0008 の実装上の意味である。

**`src/core/write/publisher.ts`** — `publish(event): Promise<{ accepted: RelayUrl[]; rejected: { relay; reason }[] }>`。送信先は自分の kind:10002 の write リレー。

**デッキ** — `{ version: 1; columns: ColumnDef[] }` を localStorage へ。`version` を最初から持たせるのは、NIP-78 へ移すときの移行の足場が要るため。**スキーマの形を実地で確かめてから** NIP-78 に載せられるのが、この順序の利点である。

**`/v1-preview`** — ログイン、カラム、投稿フォーム。

## 4. プロフィールは要求のコアレッサで取る

```
<Note>  kind:1 を描画
  └ <Profile pubkey={x} />   マウント時に x の 1 件を要求
                                  ↓
                        コアレッサ
                        ・EventStore にあれば即返す
                        ・無ければ pending へ入れ、短い窓でまとめる
                          （窓は既存の `Scheduler` seam で刻む。
                            読み取り層が実タイマーを直接掴まない規約に従う）
                        ・{ kinds: [0], authors: [まとめた分] } を 1 本の REQ に
```

**初版の設計は違う形で、そちらは誤りだった（記録として残す）。** 当初は「全カラムの `items` から著者集合を導き、その集合を購読する専用セクション」を提案した。これは 2 つの意味で悪い。

1. **churn を自分で作る。** `items` が変わるたびに派生集合の識別子が変わり、`createSection` の `createEffect` が購読を張り直す。中身が同じでも張り直す。500 件のバーストなら最大 500 回で、通知をバッチした効果が相殺される。
2. **ADR-0017 より筋が悪い。** ADR-0017 は `needs: (event) => ({ profiles: [event.pubkey] })` と**イベント単位で宣言**し、読み取り層が波状にまとめる形を定めている。集合を外で計算するのは、そのプロジェクト自身の決定から遠ざかる方向だった。

コアレッサはこの波状解決を、宣言的レンダラ登録機構なしで、**プロフィール 1 種類に限って**実装したものである。ADR-0017 を入れるときの前身になる。

## 5. 読み取り層への押し返し —— fetch-once

コアレッサを書くと、読み取り層に無い能力が要る。

プロフィール取得は「一度引いて閉じる」性質である（kind:0 は replaceable で、EOSE 後に張り続ける意味が薄い）。ところが現在の `SectionReader` は購読を張りっぱなしにする形しか持たず、**一度きりの取得は `bootstrap.ts` の module-local な `collect()` に閉じ込められていて外から使えない**。

**このスライスでは、必要な最小限だけを公開能力にする。** 具体的には「フィルタを渡すと、全リレーが EOSE か CLOSED を報告した時点（またはタイムアウト）で解決し、購読を閉じる」1 つだけ。`bootstrap.ts` の `collect()` が既にこの意味論を持っているので、**新しい意味論を発明するのではなく、既にあるものを公開面へ出す**形にする。ページネーション（`until` / カーソル）は含めない。

**ただし、これは一般的な整理を必要とする領域であり、今回それをやらない。** 購読には少なくとも「時間を遡って取り切る」ものと「これから来るものを受け続ける」ものがあり、rx-nostr はこれを **backward / forward strategy** として整理している（<https://speakerdeck.com/penpenpng/rx-de-req-suru-nostr> の 30 枚目付近。**このスライドは本 spec 執筆時点で LLM から読める形になっていない** —— 実際にこの整理を設計するときは人が読んで持ち込むこと）。ページネーション（後続）と合わせて設計すべきで、**今ここで場当たりに一般形を発明しない。** 今回足すのは「EOSE で閉じる 1 回きりの取得」だけであり、その事実を followups に記録する。

## 6. 投稿

**楽観的挿入は署名の後・publish の前に行う。** この順序だと、ユーザーが署名を拒否した場合に**巻き戻す状態が存在しない**。[ADR-0011](../../adr/0011-performance-budget.md) の「操作の画面反映 100ms（楽観的更新、リレー応答を待たない）」を初めて実測できる。

**自分をフォローしているのが一般的**なので、publish した投稿はリレー経由でも戻ってくる。**重複処理が自然に検証される** —— `EventStore.put` が `"duplicate"` を返し、`SortedEvents.add` が `false` を返す経路。

**publish の接続は 30 接続予算の中に入れる。** 現在 `ConnectionPool.subscribe()` が**ソケットを開く唯一の場所**であり、それが [ADR-0011](../../adr/0011-performance-budget.md) を実際に強制している一点である。publish がプールを通らなければ、予算の外にもう 1 系統ソケットができる —— `reserved`（ブートストラップの予算迂回）が既に開けている穴と同じ形になる。**プールに publish 経路を足す。**

## 7. エラー処理

| 起きること | 扱い |
|---|---|
| NIP-07 拡張が無い | ログイン画面で明示。クラッシュさせない |
| ユーザーが署名を拒否 | 投稿を中止。巻き戻す状態は無い（6 節） |
| publish が全リレーで失敗 | `rejected` を出す。ノートは `EventStore` に残る |
| 自分の kind:10002 が引けない | ハードコードのフォールバックへ publish し、**そう明示する** |
| リレー到達不能 | 既存の `status.incomplete` の生の数値をそのまま見せる。ユーザー向け翻訳は繰延（followups に記録済み） |

## 8. テスト方針の較正

これまでのやり方を捨てるのではなく、**リスクに応じて配分を変える**。

**現在の厳密さを維持する（純粋ロジック）** —— デッキの直列化と `version` 移行、write リレーの選択、コアレッサのまとめ規則。入力と出力が閉じており、変異を明記でき、期待値を計算できる。

**軽くする（UI 配線）** —— カラム描画、ログイン画面、投稿フォーム。**動かして見るほうが速く、多くを教える。** per-task レビューは残すが、UI タスクでは変異証明を求めない。

**e2e は 1 本、縦に貫くものだけ** —— ログイン → カラム表示 → 投稿 → リロード復元。NIP-07 のスタブは `e2e/console-warning.spec.ts` が既に `page.addInitScript` でやっている手法をそのまま使える（署名は fixture の秘密鍵で本物を作れる）。

**維持する** —— SDD の骨格と ledger。compaction を生き延びる仕組みなので外さない。

## 9. 影響を受ける ADR

- **[ADR-0002](../../adr/0002-v0-parity-before-cutover.md)** —— 変更なし。0 節の区別（本番切替の戦略 ≠ 開発の順序）を追記する。
- **[ADR-0011](../../adr/0011-performance-budget.md)** —— 変更なし。publish を予算内に入れることは既存の決定の実装である。
- **[ADR-0003](../../adr/0003-open-column-abstraction.md) / [ADR-0013](../../adr/0013-deck-persisted-to-nip78.md) / [ADR-0017](../../adr/0017-declarative-renderer-needs.md)** —— いずれも**まだ実装しない**ことを「実装の段階」に記録する。撤回ではない。

新しい ADR は起こさない。このスライスが出す押し返しは followups に集め、**一般形を決めるときに ADR にする。**

## 10. このスライスが答えるべき問い

実装が終わった時点で、以下に実物で答えられること。答えは followups に書く。

1. `{ items, status, loadMore }` で足りたか。足りなければ何が要ったか。
2. 30 接続予算は 3 カラム + プロフィール + 投稿で成立したか。
3. 楽観的挿入は 100ms 予算に収まったか。
4. `status.incomplete` の生の数値は、作った本人が見て意味が分かったか。
5. fetch-once をどこまで一般化する必要が見えたか。
