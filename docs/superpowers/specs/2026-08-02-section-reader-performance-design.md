# セクションの保持と通知 — 1 イベントごとの全ソートと全再描画をやめる

読み取り層の後続 #6。[ADR-0011](../../adr/0011-performance-budget.md) の予算に直接効く 1 点だけを扱う。

> **採番について。** 本仕様の「後続 #n」は [ADR-0023](../../adr/0023-centralized-subscription-manager.md)「実装の段階」の系列（#1 Outbox ルーティング、#3 接続プール、#4 ローカルフィルタ照合、#5 REQ マージ、#6 本仕様）を指す。[read-layer-followups.md](../../design/read-layer-followups.md) には**別系列の古い採番**が残っており、そちらの「#4」は永続化を指す（同ファイル冒頭の採番表を参照）。**本仕様では永続化に番号を振らず、名前で呼ぶ。**

用語は [CONTEXT.md](../../../CONTEXT.md)、決定は [docs/adr/](../../adr/)、全体像は [architecture.md](../../design/architecture.md)。

## 0. なぜ REQ マージより先にこれをやるか

[read-layer-followups.md](../../design/read-layer-followups.md) の順では REQ マージ（後続 #5）が次だった。**着手順を入れ替えた。** 理由は 3 つある。

1. **REQ マージは今日、観測可能な効果を持たない。** セクションを作っているのは `/debug/v1-section` の 1 つだけである。マージ対象が 1 本しかない状態では恒等変換にしかならない。効果が出るのは**デッキとカラムのスライス**が載って以降である。
2. **[ADR-0023](../../adr/0023-centralized-subscription-manager.md) 自身が先送りを認めている** —— 「マージ無しで動くものを先に出し、必要になった時点で管理システムの内側に足せる」。
3. **こちらは待つと高くつく。** followups は「**上に 3 層積む前が最も安く直せる**」と書いている。マージはその 1 層である。時間プロファイルが逆なので、順序を入れ替えるのが正しい。

**本仕様は REQ マージを含まない。** 後続 #5 はこのスライスの後に残る。

## 1. 計測が設計を変えた

設計前に、`#onEvent` がやっている配列操作だけを取り出して測った（2026-08-02、`scripts/research/measure-section-reader-burst.mjs` で再実行可能）。

| 投入件数 | 実装 | 比較回数 | 通知回数 |
|---|---|---|---|
| 500 | 現状 | 256,137 | 500 |
| 500 | 二分探索挿入（プローブ） | 3,793 | 1 |
| 2,000 | 現状 | 1,766,307 | 2,000 |
| 2,000 | 二分探索挿入（プローブ） | 11,688 | 1 |

**比較回数の列だけを信用すること。通知回数の「1」はプローブの人工物である** —— プローブは全件を 1 ループで回しているので合流が起きているが、実配信ではそうならない（1.2）。実配信で通知を 1 回に落とすのは 5 節のバッチであって、二分探索挿入ではない。

**この計測が設計を 2 箇所で変えた。**

### 1.1 素朴な二分探索挿入は現状と違う結果を出す

両実装の出力を突き合わせたところ一致しなかった。原因は `created_at` の同値である。

```
同一 created_at 3 件 A,B,C を投入
  現状      : A,B,C   ← 安定ソートが到着順を保つ
  素朴な挿入 : C,B,A   ← 等値の「前」に挿入してしまう
```

`created_at` を全てユニークにすると完全一致する。

**（2026-08-03 訂正）** 初版はここに「**集合としては同一**（脱落する要素は同じ）で、ずれるのは同値内の順序だけ」と書いていた。**これは一般には誤りである。** 初版が観測したのは特定の分布での偶然であり、**同値が上限の境界をまたぐと、どのイベントが残るかまで変わる。**

上限 5、`created_at=200` が 2 件、境界の `created_at=100` に 5 件が集中し、到着順が `id` の逆順という入力で確かめた:

```
到着順: y(200) z(200) e(100) d(100) c(100) b(100) a(100)
  旧実装 : y,z,e,d,c   ← 同値のうち先に着いた 3 件を残す
  新実装 : y,z,a,b,c   ← 同値のうち id の小さい 3 件を残す
```

保持されるのはどちらも 5 件で、`created_at` が厳密に大きいものは両方とも全部残す。**変わるのは「同値のうちどれを残すか」だけだが、それは順序の違いではなく内容の違いである。**

この訂正は本仕様の結論を変えない —— むしろ補強する。旧実装が残す 3 件は**到着順**で決まっており、Outbox では到着順がネットワーク次第である以上、**旧実装は「どのイベントが残るか」自体が実行ごとに変わりうる**。新実装は入力の集合だけで決まる。

無視できない理由が 3 つある。Nostr の `created_at` は秒粒度でリレーはバーストで配信するので**同値は日常的**である。上限 500 では同値内の順序が「どれが末尾から落ちるか」を決める。`<For>` のキーが並べ替わると DOM が動く。

**そして現状の「到着順を保つ」は、実は安定していない。** [ADR-0005](../../adr/0005-outbox-model-from-v1.md) の Outbox では同じイベントが複数リレーから届き、どちらが先かはネットワーク次第である。現状の順序は、実行ごとに変わりうるものを基準にしている。

### 1.2 followups が提案していた「マイクロタスクで合流」は効かない

followups の対処案は「`#notify` をマイクロタスクで合流させ」だった。**これは誤りである。**

NIP-01 のリレーは `["EVENT", subid, event]` を **1 イベント 1 メッセージ**で送る。ブラウザは WebSocket メッセージごとに別のタスクを回すので、メッセージ N で積んだマイクロタスクは N+1 が届く前に flush される。500 イベント = 500 タスク = **合流は起きず通知は 500 回のまま**である。マイクロタスクが merge できるのは「1 メッセージ内で同期的に発生した複数の通知」だけで、実際の配信パターンはそうなっていない。

上表で通知回数が 1 になっているのは、プローブが全件を 1 ループで回しているためである。**実配信では成立しない。**

メッセージをまたいで合流するにはマクロタスク境界が要る。

## 2. 保持順を全順序として固定する

**保持順 = `created_at` 降順、同値は `id` 昇順。**

```ts
export const compareEvents = (a: NostrEvent, b: NostrEvent): number =>
  b.created_at - a.created_at || (a.id < b.id ? -1 : a.id > b.id ? 1 : 0);
```

`id` を tiebreak に選ぶ理由: `NostrEvent` の中で、必ず存在し・一意で・到着経路に依存しないフィールドは `id` だけである。昇順か降順かは任意だが、**固定されていることが本質**である。

これは現状から見える順序を変える。ただし 1.1 のとおり**現状の順序は再現性を持っていない**ので、失うものは無い。

## 3. `src/core/read/sorted-events.ts`

このスライスで最も微妙な振る舞い（同値の順序、上限到達時にどれが落ちるか、上限到達後に古いイベントが来たときの扱い）を 1 つの単位に閉じ込める。

```ts
export class SortedEvents {
  constructor(capacity: number);
  /** 採用されたら true。上限により採用されなかった、または重複なら false。 */
  add(event: NostrEvent): boolean;
  has(id: string): boolean;
  get size(): number;
  /** 保持順のコピー */
  toArray(): NostrEvent[];
  clear(): void;
}
```

**`add` が真偽値を返すのが要点である。** 上限に達した状態で保持順の末尾より後ろに来るイベントは、**挿入せずに** `false` を返す。呼び出し側は画面に変化が無いと分かるので、通知を積まずに済む。

**id 集合を配列と同じ場所に持つ。** 現状は `SectionReader` が `#ids` を別に持ち、追い出しのたびに「落ちた分を id 集合からも外す」ために全件を舐め直している（`section-reader.ts:198-201`、**1 イベントごとに O(n)**）。両方を `SortedEvents` が持てば、追い出した 1 件の `id` を消すだけで済む。

**`EventStore` には置かない。** [ADR-0024](../../adr/0024-shared-bodies-per-section-membership.md) が store を共有本体、順序と membership をセクションごとと定めている。順序を store へ移すと「カラムごとに表示順が違う」という前提が壊れる。

## 4. 表示順は保持順から導く

`order` は `"created-at-desc" | "created-at-asc"`（`"thread-tree"` は型に予約済み、スレッドカラムの計画で扱う）。

- **保持順**（どれを残すか）は表示順に関わらず常に `created_at desc, id asc`。既存コードの意図（`section-reader.ts:190-191`：「上限は表示順に関わらず新しい順で決める。表示順でスライスすると昇順表示時に古い方から採用してしまい、上限到達後キャップが凍結する」）をそのまま引き継ぐ。
- **表示順**は `SectionReader` が導く。`desc` は保持順のまま、`asc` は `created_at asc, id asc` で明示的に並べ替える。

**`asc` を単純な `reverse()` にしない。** reverse だと同値が `id` 降順になり、「同値は `id` 昇順」という規則がモードによって反転する。明示ソートは 1 バッチにつき 1 回・最大 500 件（約 4,500 比較）で、削減する 256,000 比較に対して誤差である。使っていないモードに落とし穴を残すより、**規則を 1 つに保つ**方を選ぶ。

## 5. 通知はバッチする

`SectionReaderOptions` に `scheduler?: Scheduler` を足す。既定は `defaultScheduler`（`connection-pool.ts` が export 済み —— 「注入されなければ実タイマー」という規約を読み取り層の一箇所に置くためのもの）。

```ts
/** 通知をまとめる窓。60fps の 1 フレーム。ADR-0011 の「操作の画面反映 100ms」に対して十分小さい。 */
const NOTIFY_BATCH_MS = 16;
```

**デバウンスではなくバッチである。** 変化のたびにタイマーを張り直す実装（デバウンス）だと、イベントが 16ms 間隔未満で流れ続ける限り**通知が永久に発火しない**。最初の変化でタイマーを 1 本張り、発火したら畳む。以後の変化は既存のタイマーに相乗りする。

**守る不変式: `reader.items` と `reader.status` は同期的に正しいまま。** 遅れるのは通知だけであり、直接読む消費者は常に最新を見る。`createSection` は `start()` の直後に `sync()` を明示的に呼んでいる（`create-section.ts:49`）ので、初期状態は同期的に拾える。

`stop()` は保留中のタイマーを破棄する。破棄しないと、停止済みのセクションが後から通知を出す。

### 5.1 `#starting` ガードとそのテストの扱い

`#starting`（`section-reader.ts:48`。`start()` 中の通知を抑制し、settled→initial のちらつきを観測者に見せない）は、バッチを入れると**役割を失う** —— `start()` 中の変化は後続と合流するので、観測者はそもそも中間状態を見ない。

**問題はフラグ自体ではなくテストである。** `section-reader.test.ts:216`「never reports settled from within start() itself, even when a relay closes synchronously from inside subscribe()」はリスナー経由で phase 列を集めて主張しており、**バッチを入れると `#starting` を削除しても通る**。落ちなくなるテストであり、前スライスで狩り出したのと同じ欠陥である。

**裁定（2026-08-02 訂正）: `#starting` を削除する。**

初版は「残す（保険として安い）。テストは『バッチが隠しているのか、ガードが効いているのか』を区別できる形に書き直す」と裁定していた。**この要求は満たせない。** 実装計画を書く段階で、バッチ導入後の `#starting` があらゆる経路で到達不能だと分かった:

- `#scheduleNotify()` はタイマーを 1 本張るだけなので、`start()` 中に何回変化してもタイマーは 1 本
- そのタイマーが発火するのは `start()` が返った後（実 `setTimeout` は同期発火せず、fake clock は `advance()` でしか発火しない）
- したがって観測者は `start()` 中の中間状態をそもそも見ない

**区別できる観測点が存在しない以上、「ガードが効いている」ことを示すテストは原理的に書けない。** 残せば、死んだコードと、それを守っているように見えて実は何も守っていないテストの両方が残る。[ローカルフィルタ照合のスライス](./2026-08-02-local-filter-matching-design.md) 6 節が `kind:10002` の引き金に下したのと同じ裁定を適用する。

**代わりに**、既存テスト（`section-reader.test.ts:216`）は「観測者は settled を早すぎる時点で見ない」という**観測可能な**主張に書き直す。実装計画は、書き直したテストが**バッチを壊したときに**落ちることを A/B で示すこと（`#starting` を削除したときではない —— それでは落ちないのが今回の論点である）。

### 5.2 既存テストへの影響

`section-reader.test.ts` の 30 件のうち、`reader.subscribe(...)` を使って**リスナー経由で主張しているのは 4 件だけ**である（`awk` で `it()` ブロック単位に数えた。`rg -c 'subscribe\('` だと `manager.subscribe(` まで数えて 8 件に見えるが、それは誤り）。

1. `never reports settled from within start() itself, even when a relay closes synchronously from inside subscribe()`（5.1 で書き直す対象）
2. `notifies listeners when items change`
3. `does not strand a later listener when an earlier listener throws`
4. `subscribe()` を使う残り 1 件（`statuses.push(reader.status)` で phase 遷移を集めているもの、`section-reader.test.ts:123` 付近）

残り 26 件は `reader.items` / `reader.status` を直接読んでおり、5 節の不変式（同期的に正しいまま）により影響を受けない。上記 4 件は fake clock を進める形に直す（`connection-pool.test.ts` が既に使っているパターン）。

## 6. テスト戦略

前スライスの総括（「計画は最も考えていたテストには falsifiability の規律を適用し、事務作業とみなしたテストには適用しなかった」）を受けて、**すべてのテストに「捕まえる変異」を明記する。**

### 6.1 `sorted-events.test.ts`

| 主張 | 捕まえる変異 |
|---|---|
| 同値 3 件 A/B/C が `id` 昇順に並ぶ | tiebreak を落とす／降順にする |
| 先頭・中間・末尾への挿入位置が正しい | 二分探索の境界の取り違え |
| 上限到達後、末尾より後ろに来るイベントは `add` が `false`、`has` も false | 挿入してから追い出す実装（結果は同じでも `add` の戻り値が変わる） |
| 上限到達後、末尾より前に来るイベントは採用され、末尾が追い出され、その `id` が `has` から消える | 追い出し時に `id` 集合を更新し忘れる |
| 重複 `id` は `false`、`size` 不変 | 重複判定の欠落 |

### 6.2 `section-reader.test.ts`

| 主張 | 捕まえる変異 |
|---|---|
| N 件を**別々の配信**で流し、クロックを進めるまでリスナーが 1 回も呼ばれない | バッチをやめて同期通知に戻す |
| クロックを進めたら**ちょうど 1 回**呼ばれる | デバウンス（毎回張り直し）にする／バッチせず N 回呼ぶ |
| 上限で弾かれたイベントは通知を積まない | `add` の戻り値を無視して常に通知する |
| `stop()` が保留中の通知を破棄する | `stop()` で `clearTimeout` を忘れる |
| 書き直した `#starting` テスト（5.1） | `#starting` の削除 |

### 6.3 計測 —— 防げないものを防げるふりはしない

`scripts/research/measure-section-reader-burst.mjs` と `docs/research/2026-08-02-section-reader-burst.md`。接続プールの計測（`measure-outbox-connection-budget.mjs`）と同じ形で、再実行可能にして数字を記録する。

**これは回帰を防がない。** 決定的に主張できるのは通知回数と順序までである。本番コードに比較カウンタを埋めるのは筋が悪く、壁時計の比は CI で揺れる。**数字は記録として残し、いつでも測り直せる状態にする** —— それ以上を主張しない。

### 6.4 E2E —— ADR-0011 の指標を 1 つ「測定済み」にする

500 件を超えるイベントを持つ著者を seed し、`/debug/v1-section` の `items` がちょうど 500 で止まることを主張する。followups が「小さい追加であり、今すぐ入れられる」としていたものである。

これで ADR-0011 の 7 指標のうち測定済みは 30 接続上限に続いて 2 つ目になる。

## 7. 影響を受ける ADR

- **[ADR-0011](../../adr/0011-performance-budget.md)** — 変更なし。本仕様は予算値を動かさず、500 件上限を E2E で測定可能にする側である。
- **[ADR-0015](../../adr/0015-section-status-excludes-renderer-fetches.md)** — `phase` の意味は変わらない。観測されるタイミングが最大 `NOTIFY_BATCH_MS` 遅れることだけ追記する。
- **[ADR-0024](../../adr/0024-shared-bodies-per-section-membership.md)** — 変更なし。順序と membership がセクションごとであることを本仕様は強化している（3 節）。
- **[ADR-0023](../../adr/0023-centralized-subscription-manager.md)** — 「実装の段階」に **#6（セクションの保持と通知）** を追記し、**#5（REQ マージ）より先に着手したこと**とその理由（0 節）を記録する。この追記をしないと、本仕様が名乗っている「#6」がどの系列の番号なのか読者が確かめられない。

新しい ADR は起こさない。決めているのは既存 ADR の実装方法である。

## 8. 本仕様に含めないもの

- **REQ マージと `max_subscriptions`**（後続 #5）— 0 節のとおり順序を入れ替えただけで、消えてはいない。
- **`status` ゲッターのメモ化** — 読むたびに 2 本の配列を filter するが、バッチにより 1 バッチ 1 回になる。それ以上は測ってから。
- **`items` に store の内部オブジェクトを入れている問題**（followups「小さいもの」）— 凍結もコピーも本仕様では入れない。**永続化（IndexedDB 水和）のスライス**が触る場所である。
- **仮想スクロール** — 500 件の `<For>` そのものを減らす話であり、レンダラの計画に属する。
- **ADR-0011 の残り 5 指標** — カラム数・初回表示 2 秒・操作反映 100ms・メモリは、いずれもデッキか書き込み経路が要る。
