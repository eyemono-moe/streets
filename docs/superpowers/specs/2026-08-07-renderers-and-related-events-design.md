# A-2 レンダラと関連イベント — 設計

## 0. このスライスは何のためにあるか

A-1 でデッキとカラムができ、8 カラムを実地で回せるようになった。だが**描画できるのは kind:1 の本文だけ**である。リポストは中身の見えない空の箱として出て、引用は本文中の ID のまま、返信は文脈なしで並ぶ。[ADR-0003](../../adr/0003-open-column-abstraction.md)・[ADR-0004](../../adr/0004-kind-knowledge-lives-in-renderers.md)・[ADR-0017](../../adr/0017-declarative-renderer-needs.md) の 3 本が決定を記録しているのに、**実装は 1 行も無い。**

このスライスはその 3 本に実装を与える。同時に、**ADR-0017 を実測に基づいて改訂する**（4 節）。

前提知識は [CONTEXT.md](../../../CONTEXT.md)、決定は [docs/adr/](../../adr/)、繰延事項は [read-layer-followups.md](../../design/read-layer-followups.md)。

## 1. 範囲

**含む。** kind → レンダラの登録機構。詳細表示と小型表示の 2 つ。未登録 kind のフォールバック。kind:1 の関係（引用 `q` / 返信 `e`）と kind:6 / kind:16 のリポスト。関連イベント取得のコアレッサ（`createProfileRequests` の一般化）。ADR-0017 の改訂。初回描画時間の常設計測。

**含まない。** リアクション（kind:7）。スレッド表示・通知カラム・ユーザー詳細カラム。**`content` のパース**（URL・画像・`nostr:` メンション・カスタム絵文字 —— v0 の `parseTextContent` 相当は独立して大きく、このスライスと直交する）。NIP-19 のルーティング。3 秒問題の原因分解（計測の入れ物だけ作る）。ページネーション。

## 2. 唯一の描画入口

```ts
// src/core/view/renderer-registry.ts
export type EventRendererProps = { event: NostrEvent; variant: EventVariant };
export type EventVariant = "full" | "compact";

export type EventRenderer = {
  kind: number;
  full: Component<{ event: NostrEvent }>;
  compact: Component<{ event: NostrEvent }>;
};

export const defineRenderer = (renderer: EventRenderer): EventRenderer => renderer;
export const rendererFor = (
  renderers: readonly EventRenderer[],
  kind: number,
): EventRenderer | undefined;
```

```tsx
<EventView id={eventId} variant="full" />
```

**`EventView` が唯一の描画入口である。** id から `EventStore` を引き、無ければコアレッサへ要求し、届いた kind でレンダラを選び、未登録なら fallback を出す。カラムの各アイテムも、引用先も、返信の親も、リポストの対象も、すべてこの 1 つを通る。

**id 起点にする理由。** セクションは既に `NostrEvent` を持っているので二度引きになるが、経路を 1 本にする利点を取る —— [ADR-0024](../../adr/0024-shared-bodies-per-section-membership.md) が「セクションはイベント本体を保持しない。表示時に ID から store を引く」と決めており、id 起点はその方針そのものである。また、`EventView` が「store に無ければ要求する」を一手に引き受けるので、**取得を発行する場所がアプリ全体で 1 箇所に固定される。**

### 2.1 依存の渡し方は context にする

`EventView` は `EventStore` / `EventRequests` / `ProfileRequests` / レンダラ集合の 4 つを必要とし、**レンダラの中にさらに `EventView` が現れる**（引用先・親・リポスト対象）。props で通すと、レンダラを 1 つ書くたびに 4 つを受け取って下へ渡す作業が発生し、**渡し忘れが型でしか止まらない**。

Solid の context を 1 つ置く（`src/core/view/render-context.tsx`）。`/v1` が root で提供し、`EventView` とレンダラはそこから読む。

**グローバルなシングルトンにはしない。** context の値は `/v1` が組み立てて渡す —— テストが差し替えられること、`/v1` 以外の画面（`/debug/*`、将来のスレッド表示）が別の集合を使えることの 2 つが理由。レンダラ集合も context に含める。

## 3. 詳細表示と小型表示 —— `compact` は関連を引かない

**すべてのレンダラは `full` と `compact` の 2 つを持つ。** 引用先・返信の親・リポストの対象として現れたイベントは `compact` で描く。

**`compact` は自分の関連イベントを一切要求しない。** 著者と本文だけを出す。

これが**深さ上限そのもの**である。ADR-0017 は「深さ上限の既定値を決める必要がある」を宿題として残していたが、**カウンタは要らない**。`full` → `compact` で打ち止めになり、`compact` が何も要求しないので、入れ子は構造的に深さ 1 で止まる。引用の引用が「カードの中のカードの中のカード」になることは起こりえない。

**この規則の利点は、ユーザーに説明できることである。** 「小さく出るものは、その中身をさらに開かない」は画面を見れば分かる。隠れた取得回数の上限ではなく、見える表示の規則になっている。

## 4. 取得 —— ADR-0017 を改訂する

### 4.1 何を改訂するか

[ADR-0017](../../adr/0017-declarative-renderer-needs.md) は「レンダラが純粋関数 `needs(event)` で宣言し、読み取り層が波状に解決する」と決め、**実行時に取得を発行する方式を明示的に却下した**。却下理由は次のものだった。

> `useProfile(pubkey)` のように描画中に取得を発行する方式は自然だが、バッチングがマイクロタスク合流という**暗黙の仕組み**に依存する。合流に失敗すれば N+1 が復活し、しかもそれは型でもテストでも検出されない。

**この却下理由は無効になった。** 縦断スライス（2026-08-05）が作った `src/core/read/profile-requests.ts` は、まさに却下されたはずの実行時要求方式でありながら、合流を**マイクロタスクではなく明示的なコアレッサ**（200ms の窓を持つ独立した部品）で行っている。実測は **50 ノート・10 著者に対し kind:0 の REQ がちょうど 1 本**だった（[followups](../../design/read-layer-followups.md) 問い1）。ADR-0017 が恐れた N+1 は起きていない。

さらに followups は `needs` の純粋性そのものを疑っている —— 「必要な関連データはイベントだけで決まらない（折り畳み状態、ミュート、展開操作、復号可否）。純粋な宣言ではなく『表示状態を持つ問い合わせ』になる可能性がある」。**本設計はその疑いを正しいものとして扱い、表示状態が取得を決める形をそのまま採る。**

**採らないと決めるもの:** 宣言的な `needs(event)`、波状解決、深さ上限のカウンタ。

**失うもの（正直に記録する）:** ADR-0017 は「純粋関数として宣言された依存は LLM が生成しやすくレビューで検証しやすい」ことを [ADR-0007](../../adr/0007-nip-tracking-pipeline-draft-pr-only.md) の NIP 追従パイプラインの利点として挙げていた。実行時要求ではこれが失われる —— 「このレンダラが何を引くか」はコンポーネントを読まないと分からない。**代替の担保は `compact` が何も要求しないという規則**であり、これは「どのレンダラが何を引くか」を知らなくても取得量の上界を決められる。

### 4.2 何を作るか

`src/core/read/event-requests.ts` に `createEventRequests` を足す。`createProfileRequests` と**同じ形**にする（同じ 200ms 窓、同じ `request` / `subscribe` / `dispose`、同じ `Scheduler` 注入）。

```ts
export type EventRequests = {
  /** この id のイベントを要求する。既に store にあれば何もしない。 */
  request(id: string, relayHint?: RelayUrl): void;
  /**
   * その id を含むバッチが 1 本片付いたのに、store にまだ現れていないか。
   * 「取得中」と「取得できなかった」を呼び出し側が区別するための唯一の手段
   * (7 節)。要求したことが無い id については false。
   */
  isUnresolved(id: string): boolean;
  subscribe(listener: () => void): () => void;
  dispose(): void;
};
```

**`isUnresolved` は `createProfileRequests` には無い。** あちらは `<Profile>` が「名前が出ないなら pubkey を切り詰めて出す」で縮退できるので、区別が要らなかった。こちらは**引用先のカードを出すか、失敗を出すか**という別の描画に分岐するので必要になる。`fetchOnce` は全リレーが EOSE/CLOSED を返すかタイムアウト（10 秒）で必ず解決するので、「バッチが片付いた」は判定できる。

`relayHint` は NIP-10 / NIP-18 のタグが運んでくるリレー URL（5 節）。**このスライスでは受け取るだけで使わない** —— ヒントを渡す先（`fetchOnce` の明示リレー指定）は既にあるが、ヒントの信頼性（悪意あるリレーが任意の URL を書ける）を検討していない。引数に place holder を置くのではなく、**受け取って捨てることを明記する** —— 呼び出し側がタグから読む処理はどのみち書くので、その値の行き先を後から足せるようにする。

**2 つのコアレッサを 1 つに統合しない。** `createProfileRequests` は `{ kinds: [0], authors: [...] }`、`createEventRequests` は `{ ids: [...] }` で、フィルタの形も重複判定も違う。統合すると両方の条件を持つ 1 つの部品になり、それは深くならない。

## 5. NIP の一次情報（2026-08-07 に確認）

**v0 の実装（`src/shared/libs/parser/`）は現行仕様とずれている。参照しないこと。**

### NIP-10（返信）

`e` タグの形は `["e", <event-id>, <relay-url>, <marker>, <pubkey>]`。

- **marker は `"reply"` と `"root"` の 2 つだけ。** v0 のパーサは `"mention"` を割り当てるが、**現行 NIP-10 に `mention` marker は存在しない**
- **スレッドのルートへの直接の返信は、`root` marker の `e` タグ 1 本だけを持つ。** したがって「親」を求める規則は `reply` があればそれ、無ければ `root`
- **5 番目の要素に参照先の pubkey が入る**（省略可）。v0 のパーサはこれを読んでいない
- marker 無しの位置ベースの旧形式は deprecated（後方互換のためだけに残る）
- **返信の `p` タグはスレッド全体の `p` タグを引き継ぐ。** したがって `p` タグから「誰への返信か」を求めてはならない

### NIP-18（リポストと引用）

- **kind:6** はテキストノート（kind:1）のリポスト。`content` は**リポスト対象の JSON 文字列**（空でもよいが非推奨）。`e` タグは必須で、**3 番目のリレー URL も必須**。`p` タグは推奨（必須ではない）
- **kind:16** は kind:1 以外の汎用リポスト。`k` タグに対象の kind 番号を文字列で持つ。置換可能イベントには `a` タグ、`a` タグが無ければ `content` に対象の全 JSON
- **引用は `q` タグ**: `["q", "<event-id or event-address>", "<relay-url>", "<pubkey-if-a-regular-event>"]`。NIP-21 のメンションを `q` タグに変換することで、**引用がスレッドの返信として現れないようにする**のが目的
- NIP-70 で保護されたイベントのリポストは `content` を空にする

### この設計が使う帰結

1. **`e` / `q` タグが運ぶ pubkey で、親や引用先の「著者名」を取得前に出せる。** `<Profile>` は既にあるので、`@name への返信` は親イベントの到着を待たずに描ける
2. **リポストの多くは取得が要らない** —— `content` の埋め込みをそのまま使える。ただし埋め込みは**リポストした人が書いた任意の文字列**であり信用できない。**必ず `EventStore.put` を通し、署名検証に通ったものだけを使う**。通らなければ `e` タグから引き直す
3. **kind:16 は kind:1 以外を運ぶ。** 中身の kind が未登録なら fallback が出る —— レジストリの fallback 経路が最初に実地で効くのがここ

## 6. kind ごとの中身

| | full | compact |
|---|---|---|
| **kind:1** | 著者・本文・時刻。`e` タグ（reply ?? root）があれば上に「@name への返信」+ 親の `compact`。`q` タグがあれば本文の下に引用先の `compact` | 著者・本文・時刻のみ。**関連を一切要求しない** |
| **kind:6** | 「@x がリポスト」+ 対象の `compact` | 「@x がリポスト」の 1 行のみ |
| **kind:16** | 「@x がリポスト」+ 対象の `compact`（対象の kind が未登録なら fallback の `compact`） | 同上、1 行のみ |
| **未登録の kind** | kind 番号 +「未対応の種類です」+ `content` を 200 文字で切り詰めて表示 | kind 番号のみ |

**本文は今と同じくプレーンテキストとして出す。** URL も `nostr:` も画像も展開しない（1 節、スコープ外）。

## 7. 関連イベントが届かないとき

引用先が削除済み・どのリレーにも無い・単に遅い、はいずれも起こる。

**アラートにしない。** [ADR-0026](../../adr/0026-actionable-errors-visible-diagnostics-behind-developer-mode.md) の判定に照らすと、ユーザーに取れる行動が無い —— 引用先が消えていることは投稿者の行為の結果であって、閲覧者が直せるものではない。その場に **「読み込めませんでした」のプレースホルダ**を出すだけにする。

**`status` にも入れない。** [ADR-0015](../../adr/0015-section-status-excludes-renderer-fetches.md) が「セクションの `status` はレンダラの遅延取得を含めない」と決めており、本設計はそれを変えない。カラムの `phase` が `settled` であることは「そのカラムのフィルタに対する取得が終わった」という意味のままで、引用先が揃っていることは含意しない。

**取得中と取得失敗を区別する。** 要求してから一度も応答が無い間は「読み込み中」、`fetchOnce` のタイムアウト（10 秒）が過ぎたら「読み込めませんでした」。区別しないと、遅いだけのものが壊れて見える。

## 8. 初回描画の計測

`optimistic-insert-ms` と同じ形で、開発者モードに読み取り値を 1 つ足す（`data-testid="first-render-ms"`）。

**測る区間: ログイン（pubkey 確定）から、いずれかのカラムに最初のノートが描画されるまでの ms。** `performance.now()` で挟み、`signEvent` のような外部要因を含めない。

**なぜこのスライスで入れるか。** 実鍵での確認（2026-08-07）で初回描画が約 3 秒と報告されており、[ADR-0011](../../adr/0011-performance-budget.md) の「初回イベント表示 2 秒」を超えている。**A-2 は関連イベントの取得を増やすので、この数字を確実に悪化させる。** 入れた劣化を入れた本人が見られる状態にしておく。

**原因の分解はこのスライスではやらない。** 候補（ブートストラップの 2 往復 / schnorr 検証 / 接続確立）を絞り込むのは独立した作業であり、まず計測の入れ物を置く。

## 9. エラー処理

| 起きること | 扱い |
|---|---|
| 未登録の kind | fallback レンダラ（6 節）。**壊さない** |
| リポストの `content` の埋め込みが壊れている / 署名が通らない | `EventStore.put` が弾く。`e` タグから引き直す |
| リポストに `e` タグが無い（NIP-18 違反） | 対象を表示せず「リポスト（対象不明）」。**例外を投げない** —— v0 のパーサは throw するが、1 件の不正なイベントでカラム全体を壊してはいけない |
| `e` / `q` タグの pubkey が 64 桁 hex でない | その要素を無視し、著者名は親の到着後に出す |
| 引用先・親が届かない | 7 節 |
| `q` タグが event-address（`a` 形式）を指す | このスライスでは `compact` の代わりに「未対応の参照です」を出す。置換可能イベントの取得は範囲外 |

**このアプリに `ErrorBoundary` は無い。** 壊れた入力はレンダラの入口で吸収し、白画面にしない —— A-1 の `loadDeck` と同じ方針。

## 10. テスト

**ユニット（vitest）**

- タグの解釈（純関数、`src/core/nostr/` に置く）: `replyTarget(event)` が `reply ?? root` を返すこと、marker 無しの旧形式を無視すること、pubkey の 5 番目の要素を読むこと、`quoteTargets(event)` が `q` タグを読むこと、不正な要素を落とすこと
- リポストの埋め込み: `content` の JSON が正しいときに対象を返し、壊れているとき・署名が通らないときに `undefined` を返すこと
- `rendererFor`: 登録済み kind を返し、未登録で `undefined` を返すこと
- `createEventRequests`: 200ms 窓で 1 本にまとまること、store に既にある id を要求しないこと、`dispose` がタイマーを残さないこと（`createProfileRequests` のテストと同じ形）

**E2E（Playwright、ローカル docker リレー）**

- リポストがシードされたとき、カラムに対象の本文が出ること
- 引用がシードされたとき、引用先の本文が `compact` で出ること
- 返信がシードされたとき、「@name への返信」が出ること
- **未登録の kind がシードされたとき、カラムが壊れずに fallback が出ること**

`e2e/fixtures/` に kind:6 / 引用 / 返信 / 未登録 kind を含むシードを足す。

**このスライスのテストで特に落としやすいもの:** 「`compact` が関連を要求しない」という規則。これが破れると入れ子が止まらなくなるが、破れても画面は（深くなるだけで）動いてしまう。**`compact` で描いたときに `EventRequests.request` が呼ばれないことを直接主張するユニットテストを置くこと。**

## 11. 実際に動かして初めて答えられる問い

**このスライスの成果物はここへの回答でもある。** 完了時に `docs/design/read-layer-followups.md` へ書く。推測は書かない。

1. **初回描画は何秒になったか。** A-1 時点で約 3 秒（実鍵）。関連イベントの取得が乗った後の値を `first-render-ms` で読む。**悪化するのが当然の変更なので、悪化幅そのものが答えである**
2. **`compact` が関連を引かないという規則は、実際に見て不足を感じないか。** 引用の引用が見えないことが実用上の問題になるか
3. **リポストの `content` 埋め込みは実地でどれくらい使えるか。** 署名検証に通る割合。通らないものが多ければ、埋め込みを信じる最適化そのものが無駄になる
4. **8 カラムでの接続数は変わったか。** 関連イベントの取得は `fetchOnce` を増やすが、A-1 の実測はピーク 10 だった。関連取得が予算にどう効くか
5. **`e` / `q` タグの pubkey は実際に入っているか。** 「取得前に著者名を出せる」という 5 節の帰結は、タグに pubkey が入っているクライアントの割合に依存する。入っていなければこの最適化は効かない
