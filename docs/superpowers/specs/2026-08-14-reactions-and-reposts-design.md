# リアクションとリポストの表示 — 設計

## 0. このスライスは何のためにあるか

タイムラインに kind:7（リアクション）が流れてきても `UnknownKind` で「未対応の種類です」としか出ない。kind:6（リポスト）は出るが、**対象イベントを `compact` で描いており v0 と見た目が違う**。そしてノートに付いたリアクションの一覧（Discord/Slack のような集計表示）がどこにも無い。

前提知識は [CONTEXT.md](../../../CONTEXT.md)、決定は [docs/adr/](../../adr/)、スライスの記録は [read-layer-followups.md](../../design/read-layer-followups.md)。残タスクは [GitHub Issues](https://github.com/eyemono-moe/streets/issues)。

## 1. v0 は「デザインの一次情報」であり「プロトコルの一次情報ではない」

**この区別を守ること。** 見た目・レイアウト・情報の並びは v0 のコードが仕様である。NIP の解釈は [NIP-25](https://github.com/nostr-protocol/nips/blob/master/25.md) と v1 の `src/core/nostr/` を正とする。

**このスライスで実際に見つかった v0 の誤り（写してはいけない）:**

| v0 | 何が誤りか |
|---|---|
| `7_reaction.ts` の `input.content === "+"` だけを `like` とする | NIP-25 は「**空文字は `+` とみなす**」と定めており、v0 のコメント自身もそう書いているのに、コードは空文字を「空のテキストリアクション」にしてしまう |
| `parseReaction` がパース失敗で `throw` | v1 のレンダラは例外を投げてはならない。`<For>` の周りに `ErrorBoundary` が無く、1 件で列全体が落ちる（[#220](https://github.com/eyemono-moe/streets/issues/220)） |
| `-`（NIP-25 の dislike）を text 扱い | 誤りとまでは言えないが、NIP-25 が別の意味を与えている記号を素通しにしている。**このスライスでは text として出す**（v0 と同じ挙動）が、判断した結果としてそうする |

## 2. 範囲

**含む。** kind:7 のレンダラ（タイムラインに流れてくるリアクション）。`Repost` の対象を `compact` から完全な描画へ直す。ノートに付いたリアクションの一覧（集計・件数・展開）。一覧のための kind:7 の取得。

**含まない。** リアクションの**送信**（[#200](https://github.com/eyemono-moe/streets/issues/200)）とリポストの送信（[#201](https://github.com/eyemono-moe/streets/issues/201)）—— 別スライス。一覧の `+` ボタン（絵文字ピッカー）は送信の入口なので、そちらへ回す。アクション行（返信・リポスト・ふぁぼ・ブックマーク・zap）。ホバーカード（#275 依存）。名前を押してユーザーカラムを開く（#205 依存）。

## 3. リポスト・リアクションの骨格

v0 の `Repost.tsx` / `Reaction.tsx` が仕様。**どちらも「1 行の見出し + 対象イベントを子として完全に描く」形。**

```
┌──────────────────────────────────┐
│ ⟳ @name がリポスト                │  ← 見出し (c-secondary / text-caption)
│ ┌──────────────────────────────┐ │
│ │ [avatar] display_name @name  │ │  ← 対象を **完全な** Event として描く
│ │ [      ] 本文...              │ │     (返信先・引用・リアクション一覧を含む)
│ └──────────────────────────────┘ │
└──────────────────────────────────┘
```

**対象は `compact` ではない。** v0 は `<Event event={e} showReactions showActions />` を渡しており、対象のノートは返信先も引用もリアクション一覧も普通に持つ。**今の v1 の `Repost` は `compact` を渡しているので、これを直す。**

**入れ子の深さは v0 と同じにする** —— 制限しない。`compact` を使うのは引用先と返信先だけであり、リポスト・リアクションの対象は「そのイベントそのものを見せている」ので省略形にする理由がない。

### 3.1 見出しの行

| | リポスト | リアクション |
|---|---|---|
| アイコン | `i-material-symbols:repeat-rounded`、`c-green-5`、`w-4` | 反応内容による（下表） |
| 名前 | `@name`（`font-700`） | 同じ |
| 文言 | 「がリポスト」 | 「がリアクション」 |
| 色 | `c-secondary text-caption` | 同じ |

**リアクションのアイコンは反応内容そのもの**（`h-5`）:

| 反応内容 | 出すもの |
|---|---|
| `like`（`+` または空文字） | `i-material-symbols:favorite-rounded`、`c-accent-5` |
| `emoji`（NIP-30 のカスタム絵文字） | その画像。`alt`/`title` にショートコード |
| `text`（それ以外の文字列） | その文字列（`truncate`） |

## 4. 反応内容の分類（NIP-25）

`content` と `emoji` タグから 3 種のいずれかへ落とす。**例外を投げない。**

| 条件 | 結果 |
|---|---|
| `emoji` タグがあり、`content` が `:<その名前>:` と一致 | `{ type: "emoji", name, url }` |
| `content` が `"+"` **または空文字** | `{ type: "like" }` |
| それ以外 | `{ type: "text", content }` |

**空文字を `like` に含めるのが v0 との違い**（1 節）。NIP-25 は「空文字のときクライアントは `+` とみなすべき」と定めている。

**対象イベントは最後の `e` タグ、その著者は最後の `p` タグ。** NIP-25 がそう定めている（スレッドの祖先が前に並ぶため、最後が対象）。`e` タグが 1 つも無い kind:7 は**対象不明として扱い、描かない**（見出しだけ出しても意味がない）。

## 5. リアクションの一覧

v0 の `ReactionButtons.tsx` / `ReactionButton.tsx` が仕様。ノートの本文の下、引用カードの下に置く。

**反応内容ごとにまとめ、押した人と回数を数える。** まとめる鍵は emoji なら名前、text なら文字列、like なら `"+"`。

1 グループの見た目は、枠（`b-1 rounded`）の中に「反応内容 + 件数」。自分が押していれば `b-accent-5 bg-accent-5/10` で強調する。

**展開トグル。** 左端の三角（`i-material-symbols:arrow-drop-down-rounded`）を押すと縦積みになり、各グループの右に「誰が押したか」が `@name, @name (2)` の形で並ぶ。トグルは**ノートにホバーしているときだけ出る**（v0 は `group-not-hover/event:hidden`）。

**リアクションが 1 件も無いノートでは一覧ごと出さない。**

**`+`（絵文字ピッカー）はこのスライスでは出さない** —— 送信の入口であり、範囲外（2 節）。

## 6. kind:7 の取得

**描画されたノートについて自動で取る**（v0 と同じ）。取得は `ProfileRequests` と同じ形のコアレッサを新設する —— 対象イベント id を窓の間だけ溜め、`{ kinds: [7], "#e": [...ids] }` の 1 本のフィルタにまとめて投げる。

**なぜ新しいコアレッサが要るか。** 既存の `EventRequests` は「id でイベントそのものを引く」もので、`#e` で**そのイベントを指している別のイベント**を引く形ではない。フィルタの形が違うので同じ器には載らない。

**段階的レンダリング（先頭 40 件）と噛み合う。** 画面に出ていないノートのリアクションは要求されない。窓が伸びたぶんだけ新しい id が溜まり、次の窓でまとめて飛ぶ。

**取得の失敗は「リアクションが無い」と同じ扱い。** 一覧が出ないだけで、ノート本体は描かれる。

## 7. エラー処理

| 起きること | 扱い |
|---|---|
| kind:7 に `e` タグが無い | そのリアクションイベントは描かない（対象不明） |
| リポスト/リアクションの対象がまだ届いていない | 見出しは出し、対象の位置に `EventView` の「読み込み中」 |
| 対象が取得できなかった | `EventView` の「読み込めませんでした」。**見出しは残す** |
| `emoji` タグの画像が読み込めない | `:shortcode:` のテキストへ戻す（`NoteContent` の絵文字と同じ） |
| kind:7 の取得が失敗 | 一覧を出さない。ノート本体は描く |

## 8. テスト

**ユニット（vitest）**

反応内容の分類（`src/core/nostr/reaction.ts`）:
- `+` が `like`
- **空文字が `like`**（v0 が誤っている点。1 節）
- `emoji` タグと `:name:` が一致すれば `emoji`
- `emoji` タグがあっても `content` が一致しなければ `text`
- 対象は**最後の** `e` タグ（複数あるとき先頭を取らない）
- `e` タグが無ければ対象なし。**例外を投げない**

一覧の集計（`src/core/view/reaction-groups.ts`）:
- 同じ内容がまとまり件数が合う
- 同じ人が 2 回押したら 1 グループの中で 2 と数える
- emoji と text が同じ文字列でも混ざらない

**コンポーネント（vitest、`createRoot`）**
- リポストの対象が `compact` ではないこと（**今の実装との違いそのもの**）
- 対象が未取得でも見出しが出ること
- リアクションが 0 件のノートで一覧を描かないこと

**E2E**
- kind:7 をシードし、タイムラインに「@x がリアクション」と対象ノートが出ること
- ノートに付いたリアクションが件数付きで出ること

## 9. 実際に動かして初めて答えられる問い

1. **`#e` のコアレッサが 1 バッチで何件になるか。** 段階的レンダリングで初回 40 件・カラム 3 本なら 120 件が上限のはずだが、リレーのフィルタ長制限（NIP-11 の `max_message_length`）に当たらないかは実測が要る
2. **リポストの対象を完全に描くと、カラムの DOM 量がどれだけ増えるか。** 直前のスライスで段階的レンダリングを入れたばかりで、リポストが多いタイムラインでは 1 アイテムが 2 ノート分になる
3. **リアクションの多いノートで一覧が何行になるか。** v0 は折り返して縦に伸びるので、カラム幅 400px で読めるかは実データを見ないと分からない
