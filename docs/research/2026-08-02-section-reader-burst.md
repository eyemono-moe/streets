# セクションの保持コスト — 全ソートと全順序つき二分探索挿入の比較

Task 1〜3 で `SectionReader` の保持ロジックを「1 件ごとに全ソート + スライス」
(旧実装) から「全順序つき二分探索挿入」(`SortedEvents`、新実装) へ置き換えた。
この文書はその置き換えが何を変えたかを数字で残す。

計測日 2026-08-02。**この数字は腐る前提で扱うこと。** 再実行は
`node scripts/research/measure-section-reader-burst.mjs`。

## 0. 方法

`scripts/research/measure-section-reader-burst.mjs` が単体で走る。依存は足さない。

1. `created_at` に意図的な重複を混ぜた kind:1 相当のオブジェクト列を生成する
   (`makeEvents`)。`created_at` が全てユニークだと同値の扱いが問われない
   最良ケースになるため。
2. 旧実装 (`legacy`) を `[...items, stored].sort().slice(0, MAX)` を経由順に
   再現する。比較関数の呼び出し回数を数える。
3. 新実装 (`ordered`) を `src/core/read/sorted-events.ts` の `add()` と同じ
   アルゴリズム (末尾より後ろなら早期 return、二分探索して `splice`、上限
   超過分を `pop`) で再現する。同じく比較回数を数える。
4. 空のセクションへ N 件 (100 / 500 / 1000 / 2000) が届く場合と、既に上限
   500 に達した状態へさらに 500 件が届く場合の両方を計測する。
5. 3000 件を両実装に通し、保持内容の差分 (位置ずれ件数、旧実装にしか
   無い件数) を数える。**集合が一致することは主張しない** — 理由は 1 節末尾。

## 1. 結果

空のセクションへ N 件のバーストが届く:

| 投入 | 実装 | 比較回数 | ms |
|---|---|---|---|
| 100 | legacy | 10,594 | 0.5 |
| 100 | ordered | 526 | 0.1 |
| 500 | legacy | 255,988 | 4.4 |
| 500 | ordered | 3,781 | 0.3 |
| 1000 | legacy | 761,059 | 20.0 |
| 1000 | ordered | 7,357 | 0.3 |
| 2000 | legacy | 1,765,315 | 46.6 |
| 2000 | ordered | 11,232 | 0.5 |

上限 500 に達した状態へ、さらに 500 件が届く:

| 投入 | 実装 | 比較回数 | ms |
|---|---|---|---|
| 500+500 | legacy | 255,960 | 7.7 |
| 500+500 | ordered | 3,785 | 0.2 |

3000 件を通した際の保持内容の差分:

| | legacy | ordered |
|---|---|---|
| 件数 | 500 | 500 |
| 位置がずれた件数 | 0 / 500 | |
| 旧実装にしか無い件数 | 0 | |

**この回では偶然どちらも 0 だった。** 分布次第で変わりうる (2 節末尾)。
ms は実行ごとに数十%揺れたが、比較回数は完全に決定的で再実行しても
一致した。

## 2. 得られた事実

**比較回数は投入件数に対して旧実装が O(n² log n) 的に、新実装がほぼ
O(n log(min(n, 500))) で伸びる。** 2000 件では比較回数の比が約 157 倍
(1,765,315 対 11,232)。これは「1 件ごとに配列全体を毎回ソートし直す」
実装が持つ根本的な非効率で、二分探索挿入が狙った通りの効果を出している
ことを示す。

**上限に達した後の追加バーストでも差は縮まらない。** 500+500 のケースで
旧実装は毎回 500〜1000 要素の配列を丸ごとソートし続けるが、新実装は
「末尾より後ろなら早期 return」で比較 1 回だけで済ませられる件数が多く、
比較回数は空のセクションに 500 件を入れる場合とほぼ同じ (3,785 対
3,781)。**新実装のコストは「上限に達しているかどうか」にほとんど依存しない**
— 早期 return が効くケースが多いため。旧実装は依存し続ける。

**同値が上限の境界をまたぐと保持内容そのものが変わりうる。** 旧実装は
同値のうち到着が先だったものを残し、新実装は id が小さいものを残す
(`compareEvents` の tiebreak)。今回の 3000 件・seed 42 では偶然どちらも
一致したが、これは分布に依存する結果であって保証ではない。**「新旧で
保持内容が一致する」という主張はしない。** スクリプトはこの点を明示的に
出力する。

## 3. この計測の限界

- **配列操作だけを取り出したものであり、`setItems` のコピーと `<For>` の
  突き合わせ (実アプリの支配項) は含まない。** Solid の `<For>` はキー付き
  差分更新を行うため、実アプリでの体感コストはここで測った比較回数の比とは
  別に、DOM 側の再利用効率にも左右される。ここで測っているのは
  `SortedEvents` 自身の計算量だけである。
- **通知回数は測っていない。** 実配信ではリレーが 1 イベント 1 メッセージで
  送るため、通知を 1 回にまとめて `<For>` の突き合わせ回数を減らすのは
  Task 3 のバッチ (スケジューラ経由) の仕事であって、二分探索挿入そのものの
  効果ではない。この文書が測っているのは挿入アルゴリズムの計算量だけで、
  通知削減の効果は別の議論になる。
- **これは回帰を防がない。** 決定的に主張できるのは通知回数と順序までで、
  それは vitest 側 (`sorted-events.test.ts` / `section-reader.test.ts`) が
  担っている。ここでの数字はいつでも測り直せる記録として残すだけであり、
  CI で自動的に閾値を割ったら落ちる、という類のガードではない。壁時計の ms
  は環境依存で揺れる (今回も実行ごとに数十%動いた) ため、本番コードへ
  比較カウンタを埋め込んで閾値を張るのも筋が悪い。
