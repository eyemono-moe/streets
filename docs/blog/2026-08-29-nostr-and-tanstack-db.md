# Nostr のカラムは何の関数なのか

TweetDeck 型のマルチカラム Nostr クライアントを作っている。
2026 年 5 月、その中核データ層に TanStack DB を据えようとして失敗した。
コレクションを 5 つ定義し、プロジェクタを書き、2 日と経たずに全部消した。

消したこと自体は当時のコミットに残っている。
だが「なぜ合わなかったのか」がリポジトリの ADR に書かれたのは 2 か月半あとで、しかも消した当日に書いた理由とは一致していない。
当時の差分を読み直すと、噛み合わなかった点は 2 つある。
カラムに何が入るかを store から決められないことと、読み込み中と 0 件と失敗を行として表せないことである。
どちらもカラムの話で、それ以外の層はむしろよく噛み合っていた。

## 消えた 5 つのコレクション

最初のコミットは 3 つのコレクションを作った。
`events`（id から生イベントを引く）、`profiles`（pubkey から kind:0 を畳んだ行を引く）、`queryStates`（フィルタごとの取得状態）である。
どれも同期元を持たないローカル専用コレクションで、リレーから届いたイベントをプロジェクタが書き込む形だった。

この時点では動いていた。
kind:0 が届けばプロフィール行が上書きされ、ライブクエリが再描画する。
より新しい kind:0 が来れば新しい値になる。
ユニットテストも通っていた。

1 日半後、カラム（当時のコードは「フィード」と呼んでいた）を実装しようとしたコミットが、コレクションを 2 つ足した。

```ts
eventFeedItems: Collection<EventFeedItemRow, ...>;
eventFeedStates: Collection<EventFeedStateRow, ...>;
```

`EventFeedItemRow` の主キーは `${feedId}:${eventId}` である。
どのカラムにどのイベントが属するかを、イベント本体とは別の行として手で書き込んでいた。
`EventFeedStateRow` のほうはもっと直接的で、`eoseRelays`、`activeRelays`、`hasMoreBackfill`、`oldestCreatedAt` を持っていた。
カラムの中身も進行状況も、クエリエンジンではなく呼び出し側が計算して upsert していたことになる。

その 3 時間半後、設計文書が書き換わった。
当時つけた理由は「Nostr のフィルタ意味論を直接扱うべきで、汎用のデータベースクエリモデルへ翻訳すべきではない」というものだった。

> since/until/limit are Nostr filter concepts, not generic SQL concepts

さらに 1 時間後、`@tanstack/db` は `package.json` から消えた。
最初のコレクションを作ってから依存を外すまで、コミットの時刻で 32 時間ほどである。

## TanStack DB が置いている前提

TanStack DB は、API から取ってきたデータをクライアント側に正規化して置き、そこへライブクエリを張るための層である。
ライブクエリは差分データフロー（`d2ts`）で実装されていて、コレクションが変わったときにクエリ全体を再実行せず、影響を受けた部分だけを再計算する。
TanStack のブログが挙げている数字では、10 万件のコレクションで 1 行更新したときの再計算が M1 Pro の MacBook で約 0.7ms とされている。

この仕組みは 3 つの前提の上に建っている。

- **クエリはコレクションの純粋関数である**。差分データフローはコレクションの変化から結果の変化を計算するので、同じコレクションから同じ結果が出ることを前提にしている。そうでなければ差分から結果を導けない。
- サーバが正である。楽観的な更新は先に UI へ出るが、いずれサーバから同期された状態に上書きされる。
- サーバはクエリに答えられる。オンデマンド同期では、`where` 句や `limit` を同期アダプタへ渡して部分取得するので、渡した条件に一致する行が返ってくることが前提になる。

バックエンドが 1 つあり、そこへ問い合わせれば決まった答えが返るアプリでは、この 3 つは全部成り立つ。
差分計算が効くのも、1 つ目が成り立っているからである。

## Nostr が満たさない前提

Nostr で壊れるのは 1 つ目である。
壊れ方は 1 種類ではなく、少なくとも 4 つの独立した経路がある。

### limit はリレーの裁量である

NIP-01 は `limit` をこう定めている。

> Relays SHOULD use the `limit` value to guide how many events are returned in the initial response. Returning fewer events is acceptable, but returning (much) more should be avoided.

`limit: 500` で返ってくるのは「フィルタに一致する全件のうち新しい順に 500 件」ではない。
そのリレーが返すことを選んだ 500 件である。
選び方は仕様が決めていないので、同じフィルタを 2 つのリレーへ投げれば別の 500 件が返る。

### 同じフィルタでも取得先が違えば中身が違う

このクライアントは「特定のリレーだけを見るカラム」を機能要件として持っている。
フィルタが同一で取得先リレーだけが違うカラムを 2 つ並べたとき、両者は違う中身を表示しなければならない。
ところがクエリエンジンから見れば、この 2 つのクエリは区別できない。
述語がまったく同じだからである。

### ページネーション位置はカラムごとに独立している

同じフィルタのカラムでも、片方だけ 3 ページ遡っていれば見えるものが違う。
遡った履歴はイベントの属性ではなく、そのカラムがたどった経路の属性である。

### 要求していないイベントが届く

リレーは、購読で指定していない著者や kind のイベントをその購読へ押し込める。
署名検証はこれを止めない。
検証が保証するのは「この pubkey が確かにこの内容に署名した」ことだけで、「それが要求したものか」については何も言わないからである。
Outbox モデルを採るとこの面積はさらに広がる。
どのリレーに接続するかを決めるのが、利用者本人ではなくフォローしている著者の `kind:10002` になるためである。

### 4 つに共通するもの

カラムのメンバーシップは `filter(store)` ではない。
`filter(store) ∩ この購読で実際に配信されたもの` である。
右側の項は経路依存であり、store の状態だけからは再現できない。

差分計算の前提が壊れているのはこの一点に尽きる。
同じ入力から同じ出力が出ないなら、差分的に再評価する意味がない。

### ただし「どのライブラリでも破れる」は言い過ぎである

当時の記録にはここで「store に対するリアクティブクエリでカラムを表現する案は、どのライブラリを使っても同じ理由で破れる」と書いた。
読み直すと強すぎた。

破れるのは `filter(store)` の素朴な形である。
store が「どのリレーから届いたか」まで持ち、クエリの側が取得先とページングの窓を含むなら、上の 4 つのうち取得先の違いとページング位置は式で区別できる。
要求していないイベントは入口で捨てるので store に入らず、そもそも関係ない。
再現できないまま残るのは `limit` の裁量だけになる。

それでもカラムをクエリとして書かない理由は、再現可能性ではなく別の 3 つにある。
取り切ったかどうかを式が言えないこと、欠落の理由を返り値に置けないこと、そして**メンバーシップを毎回計算する設計では store から何も捨てられなくなる**ことである。
このうち最後の 1 つは交換条件であって、好みの問題ではない。

## 読み込み中と 0 件と失敗をどう区別するか

ここまでは「カラムに何が入るか」の話だった。
もう 1 つ、独立した壊れ方がある。
しかも時系列ではこちらが先に出ていて、最初のコミットの時点ですでに現れている。

最初に作った 3 つのコレクションのうち 1 つは `queryStates` だった。
イベントでもプロフィールでもなく、`{ filter, status, updatedAt, error }` だけを持つ行である。
`status` の値は `idle`、`loading`、`complete`、`error` の 4 つだった。
カラムを足したコミットが `eventFeedStates` を足したのも同じ動機で、そちらは `eoseRelays`、`activeRelays`、`hasMoreBackfill`、`oldestCreatedAt`、`error` を持っていた。

どちらも、コレクションに入れたい行が増えたから足したのではない。
**行では表せないものを、無理に行にするために足した。**

### 空のカラムには理由が 4 つある

カラムが空のとき、そうなっている理由は少なくとも 4 通りある。

- まだ REQ を投げていない、または投げたが EOSE がまだ来ていない。
- 全リレーが EOSE を返し、本当に 0 件だった。
- リレーが CLOSED を返した（`rate-limited`、`restricted`、NIP-42 の `auth-required` など）。
- 接続そのものが張れなかった、または接続予算を超えて開かなかった。

画面に出るものはどれも空のリストで同じである。
だがユーザーが取るべき行動は全部違う。
1 つ目は待てばよく、2 つ目は何もすることがなく、3 つ目はログインやリレーの変更が要り、4 つ目はリレー設定を直す話になる。

### プロトコルはこの区別を助けない

NIP-01 は、一致するイベントが無いときにリレーが何かを言うことを要求していない。
EOSE は「保存済みイベントの終わり」を示すだけで、「無かった」と「返さないことにした」を区別しない。

CLOSED には機械可読の接頭辞が付く。

> The standardized machine-readable prefixes for `OK` and `CLOSED` are: `duplicate`, `pow`, `blocked`, `rate-limited`, `invalid`, `restricted`, `mute` and `error` for when none of that fits.

ただし CLOSED が来るのは、リレーが REQ を拒否したときか、自分の都合で購読を打ち切ったときである。
黙って 0 件を返すのはどちらでもないので、CLOSED は来ない。
つまり「答えたが何も無かった」と「答えなかった」は、プロトコルの上でも区別が付かないことがある。

区別できる材料は、届いたイベントの側には無い。
どのリレーへ何本の REQ を投げ、そのうち何本が EOSE を返し、何本が CLOSED で、何本がそもそも繋がらなかったか。
これは購読の属性であって、イベントの属性ではない。
イベントを行として持つコレクションに、この情報を書く場所は存在しない。

### TanStack DB の status は粒度が合わない

TanStack DB に読み込み状態が無いわけではない。
コレクションは `idle`、`loading`、`initialCommit`、`ready`、`error`、`cleaned-up` の状態を持ち、`useLiveQuery` は `status` と `isLoading` と `isReady` と `isError` を返す。

問題は粒度である。
この status はコレクションのものであって、クエリのものではない。
イベント本体を 1 つのコレクションで共有すると、そのコレクションは最初の同期が済んだ時点で `ready` になり、以後どのカラムのクエリも `ready` を返す。
あるカラムの購読がまだ EOSE を待っていることも、そのカラムの取得先だけが落ちていることも、ここには出てこない。

カラムごとにコレクションを分ければ status も分かれる。
それでもまだ足りない。
Outbox によって 1 カラムは N 本の REQ へ分解されるので、欲しいのは 1 つの status ではなく「N 本のうち何本が終わったか、終わらなかった残りはなぜか」だからである。
`loading` と `ready` の 2 値には畳めない。

## 噛み合っている部分

置換可能イベントは、逆に store の純粋関数である。
NIP-01 は同じ `kind` と `pubkey`（パラメータ付きなら `d` タグも）の組に対して勝者を一意に定めていて、`created_at` が最大のものを残し、同着なら id の辞書順で小さいほうを残す。

> In case of replaceable events with the same timestamp, the event with the lowest id (first in lexical order) should be retained, and the other discarded.

これは経路に依存しない。
どのリレーから何本届いても、届いた集合が同じなら勝者は同じである。
最初のコミットの `profiles` コレクションが動いていたのはこのためであり、偶然ではなかった。
プロフィール（kind:0）、フォローリスト（kind:3）、リレーリスト（kind:10002）、ミュートリスト（kind:10000）は全部この形をしている。

イベントから導かれる集計も同じ性質を持つ。
対象イベントごとに畳んだリアクション数、リポスト数、あるイベントへの返信の集合が該当する。
どれも「手元にあるイベント集合の関数」であって、どういう順序で届いたかに依存しない。
差分維持が素直に効く形であり、ライブクエリが本来得意とする仕事でもある。

楽観的更新については、噛み合いは半分である。
投稿してすぐ画面に出し、失敗したら巻き戻すという流れ自体は Nostr にも当てはまる。
ただし Nostr の publish は複数のリレーへ同時に投げるものであり、「3 本中 2 本が受理して 1 本が拒否した」が日常的に起こる。
成功か失敗かの二値で巻き戻す設計には収まらない。

つまり噛み合わないのはカラムであって、イベントから導かれる派生ビューではない。
この線引きが最初から見えていれば、コレクションを 5 つ作る前に止まれた。

## TanStack DB で書くとしたらどう書けたか

いま当時のコードを読むと、答えはコードのほうが先に出していた。
`eventFeedItems` は、`${feedId}:${eventId}` を主キーに持つメンバーシップの表である。
これを手で upsert していたということは、カラムを書き始めた時点で「カラムは store へのクエリである」という設計はすでに放棄されていたことになる。
残っていたのは、そのメンバーシップの表を TanStack DB のコレクションとして持つか、自前の配列で持つか、という選択だけだった。

そう捉え直すと、TanStack DB を使う正しい形も見えてくる。

- `events` コレクションはイベント本体を id で持つ。全カラムで共有する。
- カラムごとに `membership` コレクションを 1 つ持つ。行は `{ eventId, order }` 程度で、書き込むのはそのカラムの購読である。
- ライブクエリは `membership` と `events` の join として書く。

この形なら前提は壊れない。
メンバーシップは購読が押し込むものであってクエリの結果ではないので、コレクションの中身が経路依存であっても矛盾しない。
そのうえでライブクエリが担うのは、並べ替え、ミュート済み著者の除去、kind ごとの分岐といった、メンバーシップが決まったあとの仕事になる。
これらは純粋関数であり、差分計算がそのまま効く。

ただし、この形にしても読み込み状態は解決しない。
`membership` コレクションが `ready` かどうかは「最初の同期が済んだか」でしかなく、そのカラムが待っている N 本の REQ のうち何本が終わったかを表せない。
状態はどう組んでもコレクションの外に置くことになる。

払う価値があるかは別の問題である。
差分計算が効くのは行数が多いときであり、TanStack のブログが挙げている数字も 10 万行の話である。
このクライアントは 1 カラムの保持件数を 200 件で打ち切ると決めている（性能予算として先に固定した）。
200 件を数カラム分並べ替える程度の仕事に差分データフローを持ち込んでも、返ってくるものは少ない。
実際、いま動いているのは挿入位置を二分探索で決める配列 1 本であり、上限を超えたら末尾を 1 件捨てるだけである。

## 他のクライアントはどうしているか

同じ問題は Nostr クライアントを書けば必ず出るので、既存の実装がどう扱っているかを見ると、選択肢の分布がわかる。

### タイムラインをどう持っているか

| 実装 | タイムラインの持ち方 | イベント本体 | 取得先リレーの指定 |
|---|---|---|---|
| applesauce | `TimelineModel` が store へのクエリ | 共有 `EventStore` | timeline に渡す口が無い |
| welshman | `FeedController` が `onEvent` を叩き、受け手が貯める | `Repository` を別に持つ | リクエスト単位で持つ |
| NDK | `ndk.subscribe()` が購読ごとにコールバック | キャッシュアダプタ | リレーセットを購読ごとに組む |
| rx-nostr / nostr-tools | REQ ごとの Observable またはコールバック | 持たない | 接続ごと |

applesauce だけが、タイムラインを store へのクエリとして表している。
`TimelineModel` は `getTimeline(filters)` で現在の store から初期値を取り、以後は `insert$` に流れてくるイベントを `matchFilters` で濾して足していく。
`filter(store)` そのものである。

そして `getTimeline(filters)` には取得先リレーを渡す引数が無い。
この形では「同じフィルタで取得先だけ違うカラムを 2 つ並べる」は表現できない。
これは applesauce の欠陥ではなく射程の違いである。
取得先ごとに中身が変わるカラムを要求しないクライアントなら、この形が一番短く書ける。

welshman は反対側に振り切っている。
`FeedController` はページを取得しながら `onEvent` を呼ぶだけで、結果集合はフィードごとの `seen` セットとして自分で持つ。
ページングは指数的なウィンドウ拡大で行い、`until` を返ってきたイベントの `created_at` から更新していく。
そのコードには次のコメントが付いている。

```ts
// Relays can't be relied upon to return events in descending order, do exponential
// windowing to ensure we get the most recent stuff on first load, but eventually find it all
```

独立した実装が、リレーの返す順序を信用しないという同じ結論に到達している。

NDK も押し出し側である。
`ndk.subscribe()` は購読ごとに `onEvent` と `onEose` を呼び、キャッシュに同期的に見つかった分は `onEvents` でまとめて 1 回渡す。
複数のコンポーネントが同時に同じような問い合わせを出すことへの対処は、クエリを 1 つの store に集約することではなく、購読をバッファして束ねることで行っている。

分布としては、4 つのうち 3 つが「購読が押し出し、受け手がメンバーシップを持つ」形を採っている。

### 完了と失敗をどう伝えているか

もう 1 つの論点（読み込み中と 0 件と失敗の区別）についても、4 つの実装は違う答えを出している。

| 実装 | 完了の判定 | 失敗の伝え方 |
|---|---|---|
| welshman | リレーごとに EOSE か CLOSED か切断を待ち、リレー集合のうち `threshold` の割合が閉じたら解決する | `onEose`、`onClosed(reason, url)`、`onDisconnect(url)`、`onInvalid`、`onFiltered`、`onDuplicate`、`onDeleted` に分けたコールバック |
| NDK | 全リレーの EOSE、またはクエリが埋まったら確定。揃わなければ EOSE の到達率に応じて縮む待ち時間で打ち切る | `closed` イベントが `(relay, reason)` を渡す |
| applesauce | ローダ側が `loading` と `complete` とカーソルを持つ。`TimelineModel` は行だけを出す | ローダの Observable のエラー |
| rx-nostr | 集約しない。`EosePacket`、`ClosedPacket`（`notice` 付き）、`ConnectionStatePacket` をそのまま流す | 同じくそのまま流す |

welshman の閾値は、汎用の `load` で 0.5、タイムアウト 3 秒である。
半分のリレーが閉じた時点で結果を返すという判断で、残り半分を待たない。
検索リレーへ投げるときの閾値は 0.1 まで下がる。

NDK の打ち切りはもう少し込み入っている。
基準の待ち時間は 1 秒で、EOSE を返したリレーの割合だけ短くする。
作動するのは 2 本以上かつ 50% 以上が EOSE を返してからで、直近 20ms 以内にイベントが届いていれば「まだ流れている」と見て延長する。

4 つに共通しているのは、完了が購読の性質であって store の性質ではないという扱いである。
違うのはどこまで畳むかで、welshman と NDK は「全部を待つと遅すぎる」ことを認めて閾値とタイムアウトを入れ、applesauce と rx-nostr は畳まずに呼び出し側へ渡す。
**どれも「store に問い合わせれば分かる」形にはしていない。**

welshman には 1 つだけ、待たずに済ませる仕組みがある。
`getFilterResultCardinality` がフィルタから返り得る件数を計算できるとき（`ids` でイベントを名指ししたときなど）、その数だけ受け取った時点で購読を閉じる。
「取り切った」と言い切れる唯一の場合である。

## 押し出しを前提にしたデータ層の形

ここまでの制約から出てくる指針は 6 つある。

**配信は押し出しであり、メンバーシップは受け手が持つ。**
購読管理からカラムへ流れるのは「このイベント id をあなたのメンバーシップに足せ」という通知である。
store がカラムの中身を決めるのではない。
この向きさえ守れば、`limit` の裁量も取得先の違いも独立したページングも、全部そのまま表現できる。

イベント本体は共有し、メンバーシップだけをカラムごとに持つ。
本体をカラムごとに複製すると、メモリがカラム数倍になる。
カラムが持つのは id の集合と表示順だけにして、描画時に id から本体を引く。

置換可能イベントと集計は、store の純粋関数として書く。
ここだけはリアクティブクエリが正しい道具である。
カラムとこの層を同じ仕組みで書こうとすると、どちらかに無理が来る。

フィルタ照合をクライアント側にも置く。
要求していないイベントは必ず来るので、購読が指定したフィルタと届いたイベントを手元でもう一度突き合わせる必要がある。
このとき照合を署名検証より先に置くと、要求していないイベントの洪水を浴びても払うコストが文字列比較で済む。
schnorr 検証はそのあとでよい。

「読み込み完了」の定義を層で分ける。
EOSE はリレーごとの購読単位のイベントであって、フィルタ単位でも画面単位でもない。
リレー単位の完了、カラム単位の完了（待っている全リレーが完了したとき）、そしてレンダラ単位の完了は意味が違う。
最後のものは関連イベントの遅延取得を含むので有限時間で確定せず、カラムの状態に混ぜると完了が永遠に来なくなる。

劣化は数として型に出し、空の配列へ潰さない。
接続できなかったリレー、リレーを解決できなかった著者、予算超過で落とした著者は、それぞれ別の数として残す。
潰した瞬間に、空のカラムの理由を後から復元する手立てが無くなる。

## いまの実装

ここまでの指針は後付けの整理ではなく、実装がその形に育った結果である。
ただし全部が入っているわけではない。
2026 年 8 月末の時点で何が動いていて何が動いていないかを、数字と一緒に置く。

### 大きさ

| 部分 | 実装 | テスト |
|---|---:|---:|
| 読み取り層（`src/core/read`） | 5,150 | 10,054 |
| イベント構築とパース（`src/core/nostr`） | 1,264 | 2,262 |
| 署名器（`src/core/signer`） | 953 | 549 |
| 書き込み層（`src/core/write`） | 497 | 1,356 |
| デッキ（`src/core/deck`） | 442 | 802 |
| v1 の UI（`src/routes/v1`） | 6,325 | 6,926 |

ユニットテストは全体で 1,113 件、E2E は Playwright で 13 spec ある。
`docs/` は 31,500 行あり、実装より多い。

この比率は一度、外部レビューで批判されている。
「実装が設計を検証しているのではなく、設計を維持するために実装している状態へ近づいている」という指摘で、当時は読み取り層 3,056 行に対して、それを使っている画面が診断用の 1 本しか無かった。
受け入れて、以後は読み取り層の続きではなく縦断スライス（1 つの機能をリレーから画面まで通す単位）を作る順序へ変えた。
上の表で UI が読み取り層に並ぶ大きさになっているのはその結果である。

### 読み取り層で動いているもの

接続は `ConnectionPool` が全部所有する。
1 リレーにつき WebSocket 1 本、同時 30 本まで、超過分は開かずに `incomplete` として数える。
ソケットが死んだら指数バックオフ（初回 1 秒、上限 60 秒、ジッタ付き）で張り直し、諦めない。

購読は `SubscriptionManager` がまとめる。
著者の `kind:10002` から取得先リレーを引き、まだ被覆していない著者が多いリレーから貪欲に選び、同じリレーへ向かう複数カラムのフィルタを 1 本の REQ へ束ねる。
届いたイベントは `matchesAnyFilter` でローカル照合してから `EventStore` へ渡す。
照合を通らなかった件数はリレーごとに数えていて、開発者モードの診断パネルから見える。

`EventStore` は id から検証済みイベントを引く 1 つの Map である。
既知の id が再配送されたときは id を再計算するだけで schnorr 検証を走らせない。
置換可能イベントは `kind + pubkey`、addressable イベント（kind 30000 番台）は `kind + pubkey + d` を key にして最新版を索引する。
起動時に IndexedDB から非同期で 1 回だけ水和し、以後の読み取りは同期である。

カラムは `SectionReader` が持つ。
保持順は `created_at` 降順で同着は id 昇順という全順序で、挿入は二分探索、200 件を超えたら末尾を 1 件捨てる。
購読者への通知は 16ms 窓でまとめる。
`items` と `status` 自体は同期的に正しいままで、遅れるのは通知だけである。

kind:0 のような、表示のたびに引きたくなるものはコアレッサが 200ms 窓でまとめて 1 本の REQ にする。
50 件のノートに 10 人の著者が出てくる画面で、実際に出た kind:0 の REQ は 1 本だった。

### 書き込みで動いているもの

署名器は NIP-07（ブラウザ拡張）と NIP-46（bunker）の 2 つで、秘密鍵はアプリに一度も入らない。
NIP-44 の暗号化と復号も署名器へ委譲する。

`Writer` は 2 つの口を持つ。
`publish` は新しいイベントを署名して write リレーへ投げる。
`replace` は置換可能イベントを write リレーから引き直してから差分を当てる。
NIP-51 の非公開ミュートのように、復号して差分を当てて暗号化し直す必要があるものも、この非同期処理を `Writer` の内側で待つ。
取得を外へ出すと、その間に届いた最新版を古い内容で上書きできてしまう。

楽観表示は、署名して `EventStore` へ入れた時点で画面に出す。
リレーのエコーが返るまでの間、`mergeProjectedEvents` が楽観イベントをカラムのフィルタへ `matchesAnyFilter` で掛けて、購読由来のメンバーシップに重ねる。

ここは、フィルタをローカルの集合に適用する形が正しい唯一の場所である。
楽観イベントはまだどのリレーも通っていないので、経路依存性が存在しない。
どのカラムに出すかは手元のフィルタだけで決まる。

いま書けるのは、投稿、返信、リアクション、リポスト、削除、プロフィール更新、フォロー、ブックマーク、ミュート（NIP-51 の公開と非公開の両方）、リレーリスト（NIP-65）である。

### 画面

`/v1` に TweetDeck 型のデッキがある。
カラムの種別は 3 つで、フォロー中の投稿、通知、そしてフィルタと取得先リレーを直接指定するものである。
最後のものが、この記事で「同じフィルタでも取得先が違えば中身が違う」と書いたカラムに当たる。

レンダラは kind:1、kind:6、kind:7 の 3 つと、未知の kind へのフォールバックが 1 つある。
スレッド表示、プロフィールカード、設定画面（アカウント、リレー、ミュート、実験機能）が載っている。
リレーに繋がずに表示だけ確かめられるよう、Storybook のシーンも用意してある。

### 完了と失敗をどう出しているか

`createSection` が返す `status` は 2 つの部分に分かれている。
`phase` は `initial`、`streaming`、`settled` の 3 値で、`incomplete` は `unreachableRelays`、`unroutableAuthors`、`uncoveredAuthors` の 3 つの数である。

`settled` の意味は「待つのをやめた」であって「無いと確定した」ではない。
到達不能なリレーは待ち対象から外れるので、全リレーが落ちているセクションも `settled` になる。
そのとき `incomplete.unreachableRelays` が 0 でない値を持つ。

この 2 つを組み合わせると、空のカラムの理由が読める。

| 画面 | `phase` | `incomplete` | 意味 |
|---|---|---|---|
| 空 | `initial` | なし | まだ来ていない |
| 空 | `settled` | 無し | 本当に 0 件 |
| 空 | `settled` | `unreachableRelays > 0` | 取りに行けなかった |

問い合わせ先が 1 つも無いセクションは `settled` である。
空集合に対するクエリの結果は空であり、そのクエリは完了している。
「どこも見ていない」のではなく「見るべき場所が存在せず、そこには何も無かった」が正しい記述で、欠落しているものが無いのだから報告すべき劣化も無い。

これを人間に見せるかどうかは、また別の判断である。
`columnAlerts` が、カラムの定義とこの `status` とリレーリストの状態を受け取り、ユーザーが行動できるものだけを文言にする。
自分で URL を指定したカラムのリレーが落ちていれば知らせるが、Outbox が選んだリレーが落ちている場合は知らせない。
後者はユーザーに変える手立てが無いからで、`uncoveredAuthors` も同じ理由で診断値のまま開発者モードの背後に置いてある。

起動直後には固有の罠がある。
自分の read リレーが 0 本であることは、「設定が無い」とも「まだ届いていない」とも読める。
両方を空の配列へ潰すと、起動のたびに「リレー設定が見つかりません」が一瞬光って消える。
まだ存在しない劣化を、確定した事実として見せることになる。

だから `RelayListState` は `signed-out`、`loading`、`missing`、`ready` の 4 相を持ち、件数へ潰さない。
`loading` は「まだ外部へ接続しない」、`missing` は「fallback のリレーで待つ」という別の動作になるので、件数だけでは正しく分岐できない。

### まだ無いもの

**ページネーションが無い。**
`createSection` は `loadMore` を型として持っているが、中身は空の関数である。
カラムは最初の 200 件を出したらそこで止まる。

この記事は「ページネーション位置はカラムごとに独立している」を、store へのクエリが成立しない理由の 1 つとして挙げた。
その要件は生きているし、設計もそれを前提に組んである。
だが実装して動かして確かめたわけではない。
確かめたのは残る 3 つ、つまり `limit` の裁量、取得先の違い、要求していないイベントの到着である。

性能予算は 7 つの指標を先に決めたが、E2E で実際に測れているのは接続数の上限と 1 カラムの保持件数の 2 つだけである。
しかも CI に Playwright を走らせるジョブが無いので、その 2 つも push のたびに機械的に守られるわけではない。
測定できない予算は要件ではなく願望であり、残る 5 つは満たしていない要件として数えている。

意図的にやっていないものもある。
DM（NIP-17）は、中途半端な暗号化実装が利用者を実害に晒すので v1 では作らない。
モバイルでのデッキ編集も、マルチカラム UI がモバイルで成立しないので作らない。
本番の配信はまだ v0 のままで、v1 は `/v1` という内部ルートに閉じてある。
v0 と同等になってから一括で切り替える。

### いま作っているもの

デッキの保存先を localStorage から NIP-78（`kind:30078`）へ移す作業が、いま作業ツリーにある。
`EventStore` と `Writer` に addressable イベントを通し、その上に汎用の `Nip78Document<T>` を載せる形である。
2 秒のデバウンス、保存の直列キュー、基準イベント id による競合検出、NIP-44 での自己暗号化までを、デッキに限らない部品として書いている。

これが入ると、デッキの構成は端末ではなくリレーに載る。
そして置換可能イベントの層がまた 1 つ増える。
記事の前半で書いた「置換可能イベントは store の純粋関数である」という性質を、いちばん直接に使う機能でもある。

## 共有 store から何を捨てるか

本体を共有すると、破棄の戦略が新しく要る。
カラムが 200 件で打ち切っても本体は store に残り、カラムを閉じても残る。
誰からも参照されなくなったイベントを知る仕組みが要るということである。

applesauce はこれを参照カウントで解いていて、`addClaim` と `removeClaim` を持ち、どのモデルからも claim されていないイベントを落とせるようになっている。
こちらは永続層のバケット戦略までは決めたが、メモリ側の破棄はまだ決めていない。
本体を共有すると決めた時点で持ち込んだ要件であり、共有しない設計なら存在しなかった。

## 同じ提案がまた出てきたときのために

TanStack DB を選んだことが間違いだったのではない。
カラムを store へのクエリとして書きたくなる引力が強く、その引力はライブラリを変えても消えない。
消えるのは、2 つのことを認めたときだけである。
カラムのメンバーシップが経路に依存すること、そして空のカラムの理由が行の中に無いことである。

だから当時の記録には「TanStack DB が悪い」とは書かなかった。
同じ形の提案がまた出てきたときに、同じ検証をやり直さずに済むように、なぜモデルが合わなかったかだけを残してある。
