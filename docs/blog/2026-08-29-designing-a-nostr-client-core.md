# 0 から Nostr クライアントの基盤を作るなら

3 つの記事にわたって、自分たちの失敗と他クライアントの実装を読んできた。
ここでは、それを踏まえて基盤を最初から設計するならどうするかを書く。

抽象的な原則からではなく、**認めなければならない前提**から始める。
Nostr クライアントの設計は、この前提のどれかを認め損ねたところで壊れる。

## 認めるところから始める

**1. リレーは答えを選ぶ。**
`limit: 200` で返るのは「一致する全件のうち新しい 200 件」ではなく、そのリレーが返すことを選んだ 200 件である。
0 件で EOSE が返ったとき、無かったのか返さないことにしたのかは区別が付かない。

**2. 同じイベントが複数の経路で届く。**
Outbox を採れば、同じノートが 5 本のリレーから 5 回届く。
重複は無駄ではなく経路の情報でもあるので、捨てずに記録する。

**3. 完了は購読の性質であって store の性質ではない。**
EOSE は 1 本の REQ について言えることで、カラムについても画面についても何も言わない。

**4. 何を持っているかと、何を見せてよいかは別である。**
削除、期限、ミュート、未対応の kind。
どれも「store には有るが、この画面には出さない」を作る。

**5. `created_at` は著者が決める。**
未来の時刻を付けたイベントは、降順のタイムラインに永久に居座る。

**6. カラムの中身は store の関数ではない。**
同じフィルタでも取得先が違えば中身が違い、遡った深さが違えば見えるものが違う。

前の 3 つはネットワークの話、後の 3 つはデータの話である。
以下の構造は、この 6 つをそれぞれどこで受け止めるかで決まっている。

## 層

```
UI
  ↑ createView(intent) → { items, status }
ビュー層     メンバーシップ（id の列）と、閲覧者側の可視性
  ↑
購読層       ルーティング、分割、マージ、予算、完了判定
  ↑
Store        本体、索引、著者側の可視性
  ↑
接続層       1 リレー = 1 WebSocket
```

上向きの矢印は「下が上へ押し出す」ことを表す。
**store がカラムの中身を決めるのではなく、購読がカラムへ id を押し込む。**
前提 6 を受け止めるのはこの向きである。

呼び出し側が学ぶのは `createView(intent)` が返す 2 つだけにする。
`items` は表示するイベントの配列、`status` は読み込みの状態である。
ルーティングも分割も合流も重複排除も予算も完了判定も、この裏に隠す。

## 中核は 3 つのデータ構造

| 構造 | 持つもの | 数 |
|---|---|---|
| `EventStore` | id から検証済みイベント | アプリに 1 つ |
| `Membership` | ビューごとの id の列（全順序） | ビューごと |
| `VisibilityIndex` | 削除と期限の索引 | アプリに 1 つ |

イベント本体は 1 つの `EventStore` が持ち、全ビューで共有する。
ビューが持つのは id の列と表示順だけで、描画時に id から本体を引く。
本体をビューごとに複製すると、メモリがビュー数倍になる。

`Membership` の保持順は全順序で固定する。
`created_at` 降順、同着は id 昇順である。
到着順を tiebreak に使ってはいけない。
Outbox では同じイベントが複数のリレーから届き、どちらが先かはネットワーク次第なので、再現しない順序になる。

3 つ目の `VisibilityIndex` が、この設計で前の記事から増えている部分である。

## seenRelays を持てば、メンバーシップは store の関数になるか

前提 6 で「ビューの中身は store の関数ではない」と書いた。
では store が「どのリレーから届いたか」を持っていたらどうか。

**この問いには、以前この主張を立てたときより正確に答える必要がある。**
以前は「store に対するリアクティブクエリでカラムを表す案は、どのライブラリを使っても同じ理由で破れる」と書いた。
これは強すぎた。
provenance（どのリレーから届いたか）を持つ store に対しては、大半が関数になる。

理由として挙げた 4 つを 1 つずつ見る。

**取得先が違えば中身が違う。**
`filter(store) ∩ { e | seenRelays(e) ∋ R }` と書けば、R から届いたものだけを選べる。
取得先だけが違う 2 つのビューは区別できる。
**ここは関数にできる。**

ただし `seenRelays` は**肯定的な事実しか記録しない。**
「R が持っている」は分かるが「R が持っていない」は分からない。
R にまだ問い合わせていない間、この式は正しく空を返してしまう。
式が正しい答えを返すのは取得が終わったあとだけであり、**それまで「まだ」と「無い」を区別できない。**

**ページネーション位置がビューごとに独立している。**
遡った深さはビューごとに違うが、その窓をクエリに含めれば `{ ..., since: T }` で式が変わる。
**これも関数にできる。**

**要求していないイベントが届く。**
これは入口で捨てるので store に入らない。
**関数化とは無関係だった。**

**`limit` はリレーの裁量である。**
リレーが返した 200 件と、`filter(store)` を `created_at` 降順に 200 件取ったものは違う。
**ここだけは再現できない。**

つまり 4 つのうち 2 つは解け、1 つは問題ですらなく、残るのは `limit` だけである。

### 再現できないことは、必ずしも欠陥ではない

`limit` の再現不能は、実害の形で言い直したほうがよい。

store から取った 200 件は複数の経路の合流なので、リレーが返した 200 件より**多い**ことが普通である。
多いこと自体は困らない。
困るのは、**別のビューが何を取ったかでこのビューの中身が変わる**ことである。

スレッドを開いたら、そのスレッドの取得先がホームのカラムと同じだったために、ホームに無かったノートが増える。
表示されているものは全部「R が持っていた」ので嘘ではない。
だが「このカラムは R がこのクエリに返したものを見せている」という理解は壊れる。

### 関数にしても解けない 3 つ

再現可能性を脇に置いても、関数の形には残らないものが 3 つある。

**網羅性。**
`filter(store)` は行を返すが、その範囲を取り切ったかどうかを言わない。
空の結果が「無かった」なのか「まだ来ていない」なのかを区別できない。
これは読み込み状態の問題そのものであり、provenance を足しても消えない。

**欠落の理由。**
到達できなかったリレー、ルーティングできなかった著者、予算を超えて落とした著者。
どれも**取得の試みの属性**であって、届いたデータの属性ではない。
関数の返り値に置く場所が無い。

**破棄。**
ここがいちばん構造的である。
メンバーシップを毎回 store から計算するなら、どのビューがいつ何を必要とするか事前に分からないので、**store から何も捨てられない。**

逆に、メンバーシップを明示的な id の列として持てば、その列がそのまま参照カウントになる。
どのビューの列にも入っていないイベントは捨ててよい。
applesauce の `addClaim` と `removeClaim` はこれをやっている。

### 結論

`seenRelays` を持てば、メンバーシップは「取得先と時間窓を含むクエリの、store に対する関数」として書ける。
破れるのは `filter(store)` の素朴な形であって、provenance を持つ store に対する形ではない。

それでも明示的なメンバーシップを選ぶ。
理由は再現可能性ではなく、上の 3 つである。
**とくに破棄は交換条件になっている。**
関数として計算する設計は、何も捨てられない store と引き換えにしか成り立たない。

## 可視性を判断者で 4 つに分ける

「store には有るが画面に出さない」には理由が何種類もある。
これを 1 つの真偽値に潰すと、**変わる時刻が違うものを同じ箱に入れる**ことになって破綻する。

判断しているのが誰かで分けるのが、いちばん筋がよかった。

| 判断者 | 例 | 置き場 | いつ変わるか | 永続化 |
|---|---|---|---|---|
| 著者 | NIP-09 の削除、NIP-40 の期限 | `EventStore` | 削除が届く、時刻が過ぎる | する |
| 閲覧者 | NIP-51 のミュート、WoT | アカウント境界の内側 | 設定変更、アカウント切替 | アカウント別に |
| プロトコル | 署名不正、フィルタ不一致、未来の `created_at` | 入口 | 変わらない | しない（捨てる） |
| クライアント | 描けない kind | レンダラ | 実装が増えれば変わる | しない |

この分け方が効くのは、**それぞれ「いつ再評価が要るか」が違う**からである。

著者の判断は、イベントが届く前に材料が来ることがある（削除が先に届く）。
だから store は、本体を持っていない id についても「これは削除されている」を記録できなければならない。

閲覧者の判断はアカウントを切り替えると全部変わる。
だからミュートの結果を store に焼き込んではいけない。
ミュートは元に戻せる操作でもあるので、**メンバーシップから外すのではなく、描画の段階で畳む**のが正しい。
外してしまうと、ミュートを解除したときにそのイベントを取り直す羽目になる。

プロトコルの判断は入口で終わる。
不正な署名も、要求していないイベントも、未来の時刻も、store に入れずに捨ててよい。

クライアントの判断はレンダラの問題であって、store もメンバーシップも関知しない。
未知の kind は「未対応」として枠だけ出せばよく、そのために取得をやめる理由は無い。

## NIP-09 の実装で外せない 6 点

削除は、この 4 分割のうち「著者の判断」の代表例である。
仕様は短いが、素直に実装すると必ず踏む穴がいくつかある。

**1. 削除できるのは本人のイベントだけである。**

> A client MUST validate that each event `pubkey` referenced in the `e` tag of the deletion request is identical to the deletion request `pubkey`.

これを検証しないと、誰でも他人の投稿を画面から消せるクライアントになる。
`e` タグは id しか持たないので、検証にはその id のイベントを持っていることが要る。
持っていない場合は「削除されたことにする」ではなく「保留する」しかない。

**2. 削除リクエストは先に届くことがある。**

購読は時系列順に届くとは限らない。
削除の kind:5 が、削除対象のノートより先に届く場合がある。
だから削除の索引は、**本体を持っていない id についても引ける形**にする。
「削除された id の集合」を先に作り、あとから届いたイベントを挿入時に照合する。

**3. `a` タグは `created_at` 以前の版だけを消す。**

> When an `a` tag is used, relays SHOULD delete all versions of the replaceable event up to the `created_at` timestamp of the deletion request event.

削除の索引を「消された座標の集合」に潰してはいけない。
座標ごとに削除リクエストの `created_at` を持つ必要がある。
潰すと、削除したあとに出し直した新しい版まで消える。

そして `a` タグの対象は addressable（kind 30000 番台）だけではない。
`kind:pubkey:` の形で、通常の replaceable（kind:0、kind:3、kind:10000 番台）も指せる。
addressable だけを見る実装は、リレーリストやプロフィールの削除を取りこぼす。

**4. 削除リクエスト自体は削除できない。**

> Publishing a deletion request event against a deletion request has no effect.

kind:5 を削除対象から除外する分岐を、索引の側に 1 つ置く。

**5. 永続化しないと復活する。**

これがいちばん重い。
Outbox では、削除を尊重したリレー A と尊重しないリレー B の両方から取りに行く。
B からは何度でも届く。
削除の索引をメモリだけに置くと、リロードのたびに削除したはずのものが全部戻る。

**削除リクエストは、本体ごと永続化する。**
id の集合に圧縮してはいけない。
3 の理由で `created_at` が要り、1 の理由で `pubkey` が要るからである。

**6. 本体を捨てるか、隠すか。**

削除されたイベントの本体を store から消すと、次に同じイベントが届いたとき未知の id として schnorr 検証が走る。
削除されたイベントほど何度も届くので、これは効いてくる。

一方で本体を持ち続けるとメモリを食う。
折衷案は、**id と pubkey と kind だけを残した墓標を置き、本体は捨てる**ことである。
再配送されたときは id の再計算だけで同一性を確かめ、検証せずに捨てられる。
applesauce は `keepDeleted` を選べるようにしているので、方針を固定しない手もある。

## 期限は時刻で変わる唯一の軸

NIP-40 の `expiration` タグは、削除とよく似ていて 1 点だけ違う。

削除は「届いたら真になり、以後変わらない」。
期限は「**何も届かなくても、時刻が過ぎたら真になる**」。

つまり期限だけは、可視性の再評価をイベントの到着で駆動できない。
選択肢は 2 つある。

- 読むたびに評価する。単純だが、`items` を引くたびに全件の `expiration` を見ることになる。
- 期限つきイベントだけを別の索引に入れ、いちばん早い期限にタイマーを 1 本張る。

後者を採る。
期限つきイベントは全体から見れば少数なので、索引は小さい。
タイマーは 1 本で足り、発火したら期限切れを外して次のタイマーを張り直す。

仕様が明示している注意も、UI に反映する必要がある。

> Relays MAY NOT delete expired messages immediately on expiration and MAY persist them indefinitely.

期限切れは消えることの保証ではない。
「もう表示しない」だけであって、消えたと利用者に伝えてはいけない。

## `created_at` は著者が決める

`created_at` は署名の対象ではあるが、正しさは誰も保証しない。
未来の時刻を付けたイベントは、降順のタイムラインの先頭に居座り続ける。
悪意でなくても、時計がずれた端末が同じことをする。

NDK は `futureTimestampGrace` という設定を持っていて、指定した猶予を超えて未来のイベントを落とせる。
これはプロトコル層の判断なので、**入口で捨てる**のが正しい。
store に入れてから並べ替えで何とかしようとすると、どのビューでも同じ処理を書くことになる。

猶予をどれくらい取るかは決め打ちでよい。
数分あれば端末の時計ずれは吸収できる。

## 接続層

接続層の仕事は 2 つしかない。
1 つの URL につき WebSocket を 1 本だけ持つことと、その 1 本の生死を上へ正しく伝えることである。

`RelayConnection` が 1 リレー分を受け持つ。
NIP-01 のメッセージの送受信、NIP-42 の AUTH、そして**ソケットそのものの死の通知**を持つ。
最後の 1 つを購読単位の `CLOSED` と混ぜてはいけない。
`CLOSED` は「この REQ は終わった」で、ソケットの死は「この接続に張っていた全部が消えた」である。
区別しないと、再接続したときに何を張り直すべきか分からなくなる。

`ConnectionPool` が URL から接続を引く唯一の場所になる。
ここを 1 箇所に絞ると、接続数の予算をここだけで守れる。
散らすと、予算の判断が呼び出し側の数だけ増える。

プールが持つべき仕掛けは 3 つある。

- **同時接続要求の重複排除。** 同じ URL への `connect()` が並行に走ると、ソケットが 2 本開く。welshman も Damustr も、進行中の接続 Promise を URL ごとの Map に入れて解決している。
- **参照カウントと猶予つきクローズ。** 購読が 0 になった瞬間に閉じると、カラムを閉じて開き直すたびにハンドシェイクが走る。applesauce は `share({ resetOnRefCountZero: () => timer(keepAlive) })` で、参照が 0 になってから一定時間経って初めて切る。
- **指数バックオフの再接続。** 初回 1 秒、上限 60 秒、ジッタ付き。**回数で諦めない。** リレーは落ちて戻ってくるものであり、諦めた接続は誰も張り直さない。

## 購読層

**ここがいちばん難しい。**
理由は個々の仕事が難しいからではなく、5 つの仕事が互いに影響し合うからである。

| 仕事 | 内容 |
|---|---|
| ルーティング | どの著者をどのリレーへ割り当てるか |
| 予算 | 接続数と、リレーあたりの購読数 |
| マージ | 同じリレーへ向かう複数ビューのフィルタを束ねる |
| 配達 | 届いたイベントをどのビューへ渡すか |
| 完了 | いま誰を待っているか |

相互作用のほうが厄介である。
マージすると待つ相手が変わる。
予算が足りないとルーティングの結果が変わる。
`kind:10002` が届くとルーティングが変わる。
再接続すると完了がリセットされる。

### プランを純粋関数にする

この絡まりを解く一手が、**「いまどのリレーへ何を投げているか」を 1 つの値として持ち、それを純粋関数で作ること**である。

```
plan(intents, routing, health, budget) → Map<view, Map<relay, filters>>
```

`intents` はビューが欲しいもの、`routing` は pubkey からリレーへの表、`health` はどのリレーが落ちているか、`budget` は接続数と購読数の上限である。
これらが決まれば結果が決まる。
ネットワークもタイマーも触らない。

こうすると 3 つが同時に手に入る。

- **テストできる。** ルーティングの分割も予算超過の切り捨ても、ソケットを 1 本も開かずに確かめられる。
- **差分が指示になる。** 古いプランと新しいプランを比べれば、開く REQ と閉じる REQ とフィルタを差し替える REQ がそのまま出る。
- **予算の判断が 1 箇所になる。** 全ビューの需要をまとめて 1 回だけ選ぶので、ビューごとに独立に選んで合計が予算を超える事故が起きない。

差分を当てる側は、フィルタが変わっただけのリレーについて**接続を開き直さず、同じ接続の上で `CLOSE` と `REQ` を送る**。
これを守らないと、ルーティングが変わるたびにハンドシェイクの嵐になる。

### マージには前提条件がある

同じリレーへ向かう複数ビューのフィルタを 1 本の REQ に束ねると、`EVENT` メッセージが持つのは 1 つの `subscription_id` だけになる。
**届いたイベントをどのビューへ配るかを決める手段は、手元でのフィルタ照合しかない。**
つまりローカルのフィルタ照合器はマージの付随作業ではなく前提条件であり、先に要る。

そして照合器は、どうせ別の理由でも要る。
リレーは要求していないイベントを押し込めるので、購読が指定したフィルタと届いたイベントを手元で突き合わせる必要がある。
**照合を署名検証より先に置く。**
要求していないイベントの洪水を浴びても、払うコストが文字列比較で済み、schnorr 検証まで行かない。

束ねてよいかどうかの判定は NDK の指紋が参考になる。
フィルタの「キーの形」が同じで、`since` と `until` の値が同じで、すぐ閉じる購読かどうかが同じものだけを束ねる。
そして **`limit` を持つフィルタは束ねない。**
`limit: 200` の 2 本を 1 本に畳むと、どちらのビューも 200 件を受け取れなくなる。

### 完了はマージしても分かる

EOSE は購読単位であってフィルタ単位ではない。
だがマージしたのは自分なので、グループの構成は分かっている。

```
リレーの完了   = そのリレー向けグループの EOSE が届いたとき
ビューの完了   = そのビューが待っている全リレーが完了と記録されたとき
```

失われるのは情報ではなく時間解像度だけである。
速いビューが遅いグループメイトを待つことになるが、その損失も、待たされているビューをグループから切り出せば消える。

### 購読数が足りないときにどうするか

リレーあたりの購読数は NIP-11 の `limitation.max_subscriptions` が決める。
宣言が無ければ 20 とみなす。

足りなくなったときの手は 3 つある。

- マージを強める（束ねる条件を緩める）
- 優先度の低いビューを待たせる
- 諦める

**3 つ目が要る。**
予算は必ず足りなくなるので、足りなかったことを黙って握り潰さない設計にしておく。
落としたビューは `incomplete` に出す。
上限を超えたときリレーが何をするかは仕様が決めていないので、**古い購読を黙って切られると、そのビューだけ更新が止まり、こちらからは EOSE 済みの正常な購読と区別が付かない。**
自分で数えていないと、この状態に気付く手段が無い。

### 実装で必ず踏む 4 つ

この層を書くと、設計とは別の次元で以下に必ずぶつかる。

**同期的なコールバック。**
死んだ接続に `subscribe()` すると、戻り値を受け取る前に `onClosed` が同期的に走る。
ハンドルを変数へ代入する前にハンドラが動くので、素朴に書くと `undefined` を触る。

**再帰。**
購読の失敗が再計画を呼び、再計画が購読を呼ぶ経路を作ると、失敗し続けるリレーで無限ループになる。

**バーストの畳み込み。**
フォロー 500 人の `kind:10002` が一斉に届くと、素朴には再計画が 500 回走る。
窓（200ms 程度）でまとめる。
デバウンスではなく、最初の変化でタイマーを 1 本張って以後を相乗りさせる形にする。
デバウンスにすると、変化が途切れない間ずっと再計画されない。

**テストの重さ。**
この層はネットワーク無しで決定的に再現できなければ書けない。
fake の `RelayConnection` を最初に用意する。
streets ではこの層の実装 5,150 行に対してテストが 10,054 行ある。
**比率が 2 倍になるのは、この層が「相互作用を確かめる」以外に確かめようがないからである。**

## 完了と失敗

`status` は 2 つの部分に分ける。

- `phase`: `initial`、`streaming`、`settled`
- `incomplete`: 到達できなかったリレー数、リレーを解決できなかった著者数、予算を超えて落とした著者数

`settled` の意味は「待つのをやめた」であって「無いと確定した」ではない。
だから空のビューの理由が、この 2 つの組み合わせで読める。

| 画面 | `phase` | `incomplete` | 意味 |
|---|---|---|---|
| 空 | `initial` | なし | まだ来ていない |
| 空 | `settled` | なし | 本当に 0 件 |
| 空 | `settled` | あり | 取りに行けなかった |

待ち方には閾値を入れる。
全リレーを待つと、生きているが遅い 1 本に引きずられる。
welshman は閉じた割合が 0.5 を超えたら解決し、Jumble は半数が EOSE した時点で一度返して全部揃ったら完了フラグを立てる。

**ただし閾値で打ち切ったことは `incomplete` に出す。**
出さないと「待つのをやめた」が「全部見た」に化ける。
Jumble の 2 段階（半数で一度返し、全部で完了）は、この点でよくできている。

そしてもう 1 つ。
**「引いたが無かった」には有効期限を付ける。**
プロフィールを持たない著者や削除されたノートの引用は、画面に出るたびに再要求されるので、抑制しないと同じ REQ が出続ける。
Damustr は 10 秒の負のキャッシュを持っている。

## 数字を先に決める

実装を並べて最も差が出たのは、上限の数字を持っているかどうかだった。
持たない実装は、負荷が上がったときにどこが先に壊れるかを予測できない。

最初に決めるのは次の 7 つである。

| 予算 | 決めること | 参考値 |
|---|---|---|
| 同時接続数 | WebSocket の本数 | 30 |
| リレーあたりの購読数 | NIP-11 の `max_subscriptions`、宣言が無いときの既定 | 20 |
| ビューの保持件数 | メンバーシップの上限 | 200 |
| ビューの描画件数 | DOM に出す件数と伸ばし幅 | 40 + 40 |
| コアレッサの窓 | 関連イベントをまとめる時間 | 100〜200ms |
| EOSE の閾値と上限 | 待つ割合と打ち切り時刻 | 0.5 と 5 秒 |
| 負のキャッシュ | 「無かった」を覚える時間 | 10 秒 |

**保持件数と描画件数を分けるのは効く。**
nostter は受け取った全部を `eventsStore` に持ち、表示用の `eventsForView` を 25 から 50 に保っている。
保持を絞るとスクロールで消え、描画を絞らないと DOM が膨らむ。
この 2 つは別の問題である。

そして、決めた数字は測る。
測れない予算は要件ではなく願望になる。

## seam は実装が 2 つあるものだけ

差し替え可能な接合部は、アダプタが実際に 2 つ以上あるものに限る。
1 つしかないものは仮説上の seam であり、抽象のコストだけ払って何も得ない。

| seam | アダプタ | 理由 |
|---|---|---|
| `RelayConnection` | WebSocket / fake | ルーティングと合流と完了判定をネットワーク無しで決定的にテストする |
| `EventPersistence` | IndexedDB / インメモリ | テストを IndexedDB 無しで走らせる |
| `Signer` | NIP-07 / NIP-46 / fake | 秘密鍵を持たない以上、外部実装が複数あることが前提 |

`EventStore` は seam にしない。
永続層を「差し替え」ではなく「背後の水和と退避」にすれば、実装は 1 つで足りる。
そして読み取りは同期に保つ。
`get(id)` が非同期になると、レンダラが本体を引くたびに await が入って描画が段階的になる。

## 永続化は何を保存しないかで決める

保存する候補は 3 種類に分かれる。

- **必ず保存する。** 削除リクエスト（保存しないと復活する）、フォロー中の人の replaceable イベント（起動直後に必ず要り、量はフォロー数で上限が決まる）。
- **保存すると効く。** ビューのメンバーシップ（id と `created_at` の組）。復帰時にキャッシュを先に返し、`since = 最新 + 1` で差分だけ取れる。
- **保存しなくてよい。** タイムラインのイベント本体。次に開いたときには古い。

nostter がこの判断をいちばん絞っていて、Dexie に置くのはフォロー中の人の replaceable イベントだけである。
フォローを外した人の分は消す。

メンバーシップを保存するのは、一見すると「カラムは store の関数ではない」と矛盾するように見える。
矛盾しない。
**経路依存であることと、その経路がたどった結果を保存して復元することは別である。**
むしろ store に問い合わせて再構成することを避ける、正しいやり方になる。

## store をどう実装するか

### 内側

```ts
class EventStore {
  #events      = new Map<string, StoredEvent>();      // id → { event, seenRelays, fetchedAt }
  #replaceable = new Map<string, string>();           // "kind:pubkey:d" → id
  #byTag       = new Map<string, Set<string>>();      // "e:<id>" → 参照している id の集合
  #deletions   = new Map<string, NostrEvent>();       // kind:5 の本体（pubkey と created_at が要る）
  #deleted     = new Set<string>();                   // 墓標。本体は持たない
  #evicted     = new Set<string>();                   // 破棄済み。墓標と混ぜない
  #expiring    = new MinHeap<{ at: number; id: string }>();
}
```

`#deleted` と `#evicted` を分けるのは、**どちらも「id は知っているが本体が無い」なのに意味が逆**だからである。
前者は再配送されても入れてはならず、後者は再配送されたら入れ直してよい。

`#deletions` を id の集合へ圧縮できないのは、`a` タグの判定に削除リクエストの `created_at` が要り、本人確認に `pubkey` が要るからである。

### 読み取り API はわざと狭くする

```ts
get(id: string): NostrEvent | undefined
latestReplaceable(kind: number, pubkey: string, d?: string): NostrEvent | undefined
eventsByTag(name: string, value: string): NostrEvent[]
```

**汎用の `queryEvents(filter)` は置かない。**
置くと、ビューがそれを使ってメンバーシップを計算し始める。
その形を採らないと決めたのだから、採れる口を開けない。

`get(id)` は**常に同じオブジェクト参照を返す。**
コピーを返してはいけない。
React の `useSyncExternalStore` は `getSnapshot` の返り値が毎回変わると無限ループになるし、Solid でも Svelte でも「変わっていない」を参照比較で判定できなくなる。
applesauce が「単一のインスタンスであることを保証する」と明記しているのはこの理由である。

### 通知は key ごとに配る

**これがいちばん間違えやすい。**

素朴に `store.subscribe(listener)` という 1 本のストリームを公開すると、購読者が全員、自分に関係あるかを毎回判定することになる。
1 イベント挿入あたりのコストが `O(購読者数)` になり、購読者は画面のアイテム数に比例する。

代わりに、購読する側が**何について知りたいか**を鍵として渡す。

```ts
watch(key: WatchKey, listener: () => void): () => void

type WatchKey =
  | { type: "event";       id: string }
  | { type: "replaceable"; kind: number; pubkey: string; d?: string }
  | { type: "tag";         name: string; value: string }
```

内部は `Map<string, Set<() => void>>` 1 つでよい。
`put()` は、挿入したイベントから影響を受ける鍵だけを計算する。

```
ev:<id>                         そのイベント自身
rp:<kind>:<pubkey>:<d>          置換可能なら
tag:e:<値>  tag:p:<値>  …        そのイベントが持つタグごと
```

`eventsByTag` の索引を既に持っているなら、通知の鍵はその索引の鍵と同じものになる。
**索引があるのに通知が全体ストリームなのは、片方だけ作った状態である。**

### 通知は遅らせ、読み取りは遅らせない

リレーは 1 イベント 1 メッセージで送り、ブラウザはメッセージごとに別のタスクを回す。
だからマイクロタスク（`queueMicrotask`）では**メッセージをまたいで合流できない。**
まとめるにはマクロタスクの境界（`setTimeout` 0 か `requestAnimationFrame`）が要る。

```ts
#dirty = new Set<string>();
#timer: Timer | null = null;

#markDirty(key: string) {
  this.#dirty.add(key);
  if (this.#timer === null) {
    this.#timer = setTimeout(() => this.#flush(), NOTIFY_BATCH_MS);  // 16ms
  }
}
```

**デバウンスにしない。**
最初の変化でタイマーを 1 本張り、以後の変化はそれに相乗りする。
デバウンスにすると、イベントが途切れない間ずっと通知されない。

そして **`get()` はこの遅延の影響を受けない。**
メモリは常に最新で、遅れるのは通知だけである。
別の理由で描画が走った消費者が古い値を読むことがない。

### フレームワークとの接続

| | 橋渡し |
|---|---|
| React | `useSyncExternalStore(subscribe, getSnapshot)`。`getSnapshot` は `store.get(id)` をそのまま返す（参照が安定しているので比較が効く） |
| Solid | `createSignal` のバージョン番号を `watch` で進める。`onCleanup` で解除 |
| Svelte 5 | `$state.raw` に同じ形で入れる |

配列を返す場合（`eventsByTag`）は注意が要る。
毎回新しい配列を作ると参照が変わるので、`useSyncExternalStore` が無限ループする。
索引が変わったときだけ配列を作り直してキャッシュする。

## 永続化

### 3 つの経路に分ける

```
起動   IndexedDB → メモリへ水和（非同期、1 回だけ）
読み   メモリのみ（同期）
書き   メモリへ同期 + IndexedDB へ非同期キュー
```

永続層を `EventStore` の**差し替え**にしてはいけない。
差し替えにすると `get(id)` が非同期になり、レンダラが本体を引くたびに await が入って描画が段階的になる。
**背後の水和と退避層**にすれば、読み取りは同期のまま残る。

### 水和は検証しない経路を分ける

`put()` は挿入のたびに schnorr 検証する。
キャッシュ全件を `put()` で流し込むと、起動時に全件を再検証することになり、初回表示の予算がそれだけで埋まる。

だから信用済み挿入を**別のメソッド**にする。

```ts
hydrate(entries: readonly PersistedEvent[]): void
```

分岐ではなくメソッドを分けるのは、**型で経路を塞ぐ**ためである。
`PersistedEvent` を作れるのは永続層だけにしておけば、リレー由来の値がこの無検証の経路へ迷い込む余地が型の時点で無くなる。

水和は件数が多いと同期ループでメインスレッドを止める。
N 件ごとに `await sleep(0)` で譲る。

そして**削除リクエストを先に水和する。**
後に回すと、削除済みのイベントが一瞬メモリに入って画面に出る。

### 書き込みはキューにまとめる

1 イベントごとに IndexedDB のトランザクションを張ってはいけない。
バーストでは毎秒数百件になり、トランザクションのコストがそれを上回る。

- 配列に溜める
- タイマー（1 秒程度）か、件数（200 件程度）のどちらか早いほうで flush
- flush 1 回につき `readwrite` トランザクション 1 つ
- `visibilitychange` が `hidden` になったときと `pagehide` でも flush する（`beforeunload` は当てにならない）

**flush の中で操作の順序を守る。**
「書き込みを全部やってから削除を全部やる」という 2 ループにすると、同じ flush の中で「書いてから消した」が「消してから書いた」になって復活する。
1 本の順序つき操作ログとして持つ。

### 何を保存し、何を保存しないか

kind ごとに方針を持たせる。
保存するかどうかは 2 つの軸で決まり、**混ぜて 1 つのフラグにできない。**

- **保持**（どれだけ持つか）: 最新 1 件だけ / 件数上限つき / 持たない
- **範囲**（誰が見てよいか）: 公開 / アカウント別 / セッションのみ（ディスクへ書かない）

`kind:3` のフォローリストは「公開だが保持しない」なので、1 つのフラグでは表せない。
NIP-44 の復号結果は「セッションのみ」であり、ディスクへ書いた時点で事故になる。

そのうえで、実際の判断は次の 3 段になる。

| | 何を | なぜ |
|---|---|---|
| 必ず保存 | 削除リクエスト | 保存しないと、削除を尊重しないリレーから何度でも戻る |
| 必ず保存 | フォロー中の人の replaceable | 起動直後に必ず要り、件数がフォロー数で頭打ちになる |
| 保存すると効く | ビューのメンバーシップ（id と `created_at` の列） | 復帰時にキャッシュを先に出して差分だけ取れる |
| 保存しない | タイムラインの本体 | 次に開いたときには古い |

### object store の分け方

鍵の空間が有界なものを分けるのが要点である。

| store | 鍵 | 中身 |
|---|---|---|
| `events` | `id` | 本体と `seenRelays` と `fetchedAt` |
| `replaceable` | `[kind, pubkey, d]` | 最新 1 件だけ |
| `deletions` | `id` | kind:5 の本体 |
| `membership` | ビューの鍵 | id と `created_at` の列 |

`replaceable` を分けると、起動時にプロフィールを `bulkGet` で一括取得でき、`events` の全走査が要らなくなる。
nostter は Dexie の 1 テーブルを `[kind+pubkey]` で、Jumble は kind ごとに専用の object store を約 20 個で、同じことをしている。

### 破棄

メンバーシップの id の列が、そのまま参照カウントになる。

- ビューが id を捨てたとき（上限超過）と、ビューを閉じたときに減らす
- 参照が 0 になったイベントは候補に入れる
- **すぐには捨てない。** スクロールで戻ると再参照されるので、参照 0 のものを LRU に数千件だけ残す
- 削除リクエストは捨てない。フォロー中の人の最新 replaceable も捨てない

捨てたイベントの id は `#evicted` に残す。
再配送されたときに「知っているが本体が無い」と分かれば、入れ直す判断ができる。

## TanStack DB が使えたら何が変わるか

使えたとしても、書く量はあまり減らない。

減るのは、上の「通知は key ごとに配る」と「フレームワークとの接続」の 2 つである。
ライブクエリと差分データフローがそこを引き受ける。

減らないのは残り全部である。
可視性の索引（削除、期限）、永続化の方針、破棄、そして読み込み状態。
どれもコレクションの外に置くことになる。

そして 200 件を数ビュー分並べ替える程度の仕事に差分計算を持ち込んでも、返ってくるものは少ない。
**自前で書く場合、上の store は 400 行程度に収まる。**
索引が 3 つ、通知が 1 つ、永続化の口が 2 つで、それ以外は無い。

## 意図的にやらないこと

- **高水準の Nostr ライブラリに依存しない**、とまでは言わない。1 リレー分のメッセージ層は 150 行なので自前でも書けるが、それは「ルーティングと予算を自分で設計する」と決めたときの帰結である。既製のデータ層の形が要件に合うなら乗ったほうが速い。
- **DM は暗号を自分で書かない。** 署名器へ委譲できないなら、実装しない。
- **カラムごとに別アカウント**は作らない。署名対象と「自分宛」が一意に決まらなくなる。

## streets を今の形から変えるなら

この設計は、いま動いているものとほとんど同じ形になった。
違うのは 4 点である。

1. **`VisibilityIndex` を明示的な構造として切り出す。** 現状は削除の索引が `EventStore` の中に private フィールドとして 3 つ（`#deletionsByEvent`、`#deletionsByAddress`、`#hiddenEvents`）あり、期限と未来の `created_at` は未実装である。同じ場所に置く先が決まっていない。
2. **`a` タグの削除を replaceable にも広げる。** 現状は addressable の座標しか受け付けないので、kind:0 や kind:10002 の削除を取りこぼす。
3. **NIP-40 と未来の `created_at` を入口に足す。** どちらも現状は何もしていない。
4. **メンバーシップを永続化する。** 現状は `EventStore` を水和しても、リレーが同じイベントを再配送するまでカラムは空のままである。

削除の扱いが最初から重い作りになっているのは、あとから足せないからである。
本体を持たない id について判断できる索引と、その永続化は、store の形そのものを決める。
後から入れようとすると `put()` の signature から変えることになる。
