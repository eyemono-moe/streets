# レンダラは必要な関連イベントを宣言し、読み取り層が波状に解決する

> **この決定は A-2（レンダラと関連イベント、2026-08-07）で覆った。** 実際に実装されたのは、下記の宣言的 `needs(event)` でも波状解決でもなく、**実行時に取得を要求し明示的なコアレッサでまとめる方式**（`src/core/read/event-requests.ts` の `createEventRequests`）である。深さ上限のカウンタも作っていない。以下の決定文・却下理由・Consequences は、**却下した当時の記録としてそのまま残す** —— 却下理由そのものが後から無効と分かったので、その顛末は末尾の「実装の段階」の A-2 の項に書いた。この文書の上から順に読んで A-2 の項へ辿り着く前に離脱すると、まだ実装されていない案を実装対象だと誤解する。

レンダラは「何が必要か」を純粋関数 `needs(event)` で**宣言する**だけで、取得は行わない。`render(event, related)` は解決済みの関連イベントを受け取る純粋関数となる。

```ts
defineRenderer({
  kind: 30003,
  needs: (event) => ({
    events:   tagValues(event, "e"),
    profiles: [event.pubkey],
  }),
  render: (event, related) => /* ... */,
})
```

読み取り層は**波状**に解決する。

1. セクション内の全アイテムの `needs` を集約 → **1 クエリ**
2. 新しく届いたイベントの `needs` を集約 → **次の 1 クエリ**
3. 収束するか、**深さ上限**に達したら停止

## なぜ波状か — 入れ子は静的に解けない

`kind:1` の投稿が `q` タグで別のイベントを引用している場合、引用先を取得するまで**引用先が何を必要とするか分からない**。必要な関連イベントを最初に全部列挙することは原理的に不可能である。

波状解決はこれを解きつつ、副次的に2つの必須要件を構造的に満たす。

- **各波が 1 クエリであるため N+1 が潰れる** — [ADR-0011](./0011-performance-budget.md) のバッチング要件。
- **深さ上限がそのまま取得回数の上限になる** — [ADR-0004](./0004-kind-knowledge-lives-in-kind-specific-code.md) の「取得回数の上限制御」。

## 実行時フックを採らなかった理由

`useProfile(pubkey)` のように描画中に取得を発行する方式は自然だが、バッチングがマイクロタスク合流という**暗黙の仕組み**に依存する。合流に失敗すれば N+1 が復活し、しかもそれは型でもテストでも検出されない。10 カラム × 500 件の環境では事故が確実に起きる。

宣言的 `needs` にはもう1つ利点がある。[ADR-0007](./0007-nip-tracking-pipeline-draft-pr-only.md) の LLM 自動 PR パイプラインにとって、**純粋関数として宣言された依存は生成しやすく、レビューで検証しやすい**。「このレンダラは何を引くのか」がコードを追わずに分かる。

> **（2026-08-07 追記）この却下理由は無効になったと判定した。** 詳細は「実装の段階」の A-2 の項。

## Consequences

- レンダラは `needs` / `render` ともに純粋関数になるため、**`related` を手で組み立てて呼ぶだけでテストできる**。フック環境も Provider も不要。
- ユーザー操作によって初めて決まる動的な依存（「返信を展開」など）は `needs` では表現できない。そうしたものは別セクション・別カラムとして開く設計に寄せる。
- 深さ上限の既定値を決める必要がある（引用の引用をどこまで辿るか）。**（2026-08-07 追記）この宿題はカウンタでは解かれなかった。A-2 の項を参照。**

## 実装の段階

- **v1 縦断スライス（2026-08-05）** — 宣言的レンダラ登録機構の一般形は**まだ実装しない**。**撤回ではない** —— [仕様](../superpowers/archive/specs/2026-08-04-v1-vertical-slice-design.md) 4 節のとおり、本 ADR が定める波状解決を**プロフィール (kind:0) 1 種類に限って**先取りした「要求のコアレッサ」（`src/core/read/profile-requests.ts` の `createProfileRequests`）を作った。`<Profile pubkey={x} />` がマウントごとに 1 件ずつ要求し、コアレッサが短い窓 (200ms) でまとめて 1 本の `{ kinds:[0], authors:[...] }` に落とす —— `needs(event)` のような汎用の宣言 API ではなく、kind:0 専用に決め打った形である。深さ上限・複数 kind への一般化・純粋関数という前提の妥当性（[read-layer-followups.md](../design/read-layer-followups.md) の「縦断スライスを動かしてから決めるもの」参照）はいずれも未着手。一般形は本 ADR のまま据え置く。
- **A-2（レンダラと関連イベント、2026-08-07）— 本 ADR の決定は置き換わった。** 実装されたのは宣言的 `needs(event)` でも波状解決でもなく、**実行時に取得を要求し、明示的なコアレッサでまとめる方式**である（[仕様](../superpowers/archive/specs/2026-08-07-renderers-and-related-events-design.md) 4 節）。

  **却下理由が無効になった。** 本 ADR は「`useProfile(pubkey)` のように描画中に取得を発行する方式は、バッチングがマイクロタスク合流という暗黙の仕組みに依存し、合流に失敗すれば N+1 が復活し、しかもそれは型でもテストでも検出されない」ことを理由に実行時フックを却下した（上記「実行時フックを採らなかった理由」）。v1 縦断スライス（2026-08-05）が作った `src/core/read/profile-requests.ts` の `createProfileRequests` は、まさにその却下されたはずの実行時要求方式でありながら、合流を**マイクロタスクではなく、200ms の窓を持つ独立した明示的なコアレッサ**で行う。実測は **50 ノート・10 著者に対し kind:0 の REQ がちょうど 1 本**だった（[followups](../design/read-layer-followups.md)「v1 縦断スライス」問い1）。本 ADR が恐れていた N+1 は起きていない。A-2 はこのコアレッサの形を `src/core/read/event-requests.ts` の `createEventRequests` として汎化し（kind:0 専用ではなく `{ ids }` による任意イベントの要求、`isUnresolved` で「取得中」と「取得できなかった」を区別）、唯一の描画入口 `EventView`（`src/routes/v1/EventView.tsx`）から呼ぶ形にした。

  **採らないと決めたもの:** 宣言的な `needs(event)`、波状解決、深さ上限のカウンタ。

  **代わりに深さ上限を担うもの:** すべてのレンダラが持つ `full`/`compact` の 2 表示のうち、**`compact` は自分の関連イベントを一切要求しない**という表示規則（[仕様](../superpowers/archive/specs/2026-08-07-renderers-and-related-events-design.md) 3 節）。`full` → `compact` で必ず打ち止めになるため、引用の引用・リポストのリポストのような入れ子は構造的に深さ 1 で止まる。カウンタを持たずに済み、しかも「小さく出るものは中身をさらに開かない」という規則は画面を見れば分かる —— 隠れた取得回数の上限ではなく、見える表示の規則になっている。

  **失うもの（正直に記録する）:** 本 ADR は宣言的 `needs` の利点として、[ADR-0007](./0007-nip-tracking-pipeline-draft-pr-only.md) の NIP 追従 LLM 自動 PR パイプラインにとって「純粋関数として宣言された依存は生成しやすく、レビューで検証しやすい」ことを挙げていた。実行時要求ではこれを失う —— 「このレンダラが何を引くか」はコンポーネントを読まないと分からない。代替の担保は `compact` が何も要求しないという規則であり、これは「どのレンダラが何を引くか」を知らなくても取得量の上界を決められるが、依存関係そのものを機械的に列挙・検証する手段ではない。

  詳細と実測の根拠は [仕様](../superpowers/archive/specs/2026-08-07-renderers-and-related-events-design.md) 4.1 節、実装は Task 1〜5（`.superpowers/sdd/2026-08-07-renderers-and-related-events/`）、実測に基づく評価は [followups](../design/read-layer-followups.md) の「A-2 レンダラと関連イベント」節を参照。
