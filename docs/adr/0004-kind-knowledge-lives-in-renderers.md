# kind 固有の知識はレンダラに置き、レンダラが関連イベントを要求できる

「kind 30003 の `e` タグは対象イベントを指す」「kind 7 の `e` タグはリアクション先を指す」といった **kind 固有の知識は、その kind のレンダリングコンポーネントが持つ**。レンダラは必要な関連イベント（参照先イベント、著者のプロフィールなど）を取得層に要求できる。カラム層は kind を一切知らない。

[ADR-0003](./0003-open-column-abstraction.md) の動機（NIP 変更の影響範囲を kind に閉じる）を成立させるには、取得の意味論も kind 側に無いと成立しない。カラム定義側に写像を宣言する方式では、リスト系 kind を追加するたびにカラム層を触ることになり、動機と矛盾する。

## Considered Options

- **レンダラ側。関連イベントを要求できる** ← 採用
- **カラム定義側で写像を宣言する** — 取得が1箇所に集中し最適化しやすいが、新 kind 追加のたびにカラム層を触る。ADR-0003 と矛盾。
- **kind 定義をデータとして登録し取得層が解決する** — 両立するが、メタ記述 DSL の設計コストが高く、表現力の限界に達したとき逃げ場がない。
- **解決せず ID のまま表示** — 抽象は最も薄くなるが実用に耐えず、ADR-0001 と衝突。

## Consequences

以下は v1 の**必須要件に繰り上がる**。この決定の代償であり、後から足せない。

- **要求の合流・重複排除・バッチング。** 100 件の投稿レンダラが各々著者プロフィールを要求するため、素朴に実装すると N+1 のリクエスト爆発を起こす。
- **カラムの「読み込み完了」の再定義。** レンダラが遅延取得するため、リレーから EOSE を受け取った時点では描画は完了していない。カラムの読み込み状態は EOSE と一致しない。
- **取得回数の上限制御。** レンダラが自由に要求できる以上、無限スクロールと組み合わせると要求が青天井になる。

また、旧 v1 設計ドキュメントにあった「派生ビュー（ProfileView 等）は決してフェッチしない」という原則は **本 ADR により破棄**される。
