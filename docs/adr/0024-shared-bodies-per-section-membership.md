# イベント本体は共有し、メンバーシップはセクションが持つ

**イベントの本体**（ID → 検証済みイベント）は単一の `EventStore` が持ち、全セクションで共有する。**どのイベントがこのセクションに属するか**（メンバーシップと表示順）は、各セクションが自分で持つ。

```
EventStore      本体      共有・1 つ      ID → NostrEvent
SectionReader   membership セクションごと  ID の集合と表示順
```

## なぜ「store に対するクエリ」ではないのか

「大きな store を用意し、各カラムはその store に対するクエリである」という設計は自然に見える。**しかし Nostr では成立しない。**

**カラムのメンバーシップは store の純粋関数ではない。** 同じフィルタを持つ 2 つのカラムでも中身が違いうる。

- `limit: 500` で表示されるのは「store 内でフィルタにマッチする全イベント」ではなく、**リレーが返すことを選んだ 500 件**である。NIP-01 は `limit` を「初回クエリで返す最大数」と定めており、どれを返すかはリレーの裁量にある。
- 特定リレー内タイムラインのカラムは、フィルタが同じでも**取得先リレーが違えば中身が違う**。これは [ADR-0003](./0003-open-column-abstraction.md) が明示的に要求している表示である。
- ページネーション位置はカラムごとに独立している。同じフィルタでも、遡った深さが違えば見えるものが違う。

つまりメンバーシップは `filter(store)` ではなく **`filter(store) ∩ この購読で実際に配信されたもの`** であり、**経路依存**である。store の状態だけからは再現できない。

## TanStack DB を採らなかった理由

v1 の初期検討では TanStack DB を中核データ層に据える設計を試し、うまくいかなかった。原因は上記である。TanStack DB は「クエリはコレクションの純粋関数であり、コレクションが変われば差分的に再評価される」という前提の上に建っている。Nostr のカラムはその前提を満たさない。

**この ADR は「TanStack DB が悪い」と言っていない。** モデルが合っていなかったという記録であり、**同じ形の提案が再び出てきたときに同じ検証をやり直さないため**に残す。「store に対するリアクティブクエリでカラムを表現する」という案は、どのライブラリを使っても同じ理由で破れる。

## Consequences

- **共有 store には破棄戦略が要る。** これは新しい要件である。セクションが 500 件で打ち切っても（[ADR-0011](./0011-performance-budget.md)）、本体は store に残る。カラムを閉じても残る。**誰からも参照されなくなったイベントを知る仕組み**（メンバーシップ集合からの参照カウント、または LRU）が必要になる。[ADR-0019](./0019-two-bucket-cache-policy.md) は永続層のバケット戦略を決めたが、**メモリ側の破棄は未決定**である。
- **重複配信は安価である。** 複数セクションが同じ著者を含めば同じイベントが複数回届くが、`EventStore.put` は ID 一致を**署名検証より前**に判定するため、重複のコストは JSON パースと Map 参照のみ。schnorr 検証は走らない。これは [ADR-0023](./0023-centralized-subscription-manager.md) のマージが「必須」ではなく「最適化」に留まる理由でもある。
- **管理システムからセクションへの配信は「メンバーシップに追加せよ」という通知である。** store がカラムの中身を決めるのではない。この向きを守ること。
- セクションはイベント本体を保持しない。表示時に ID から store を引く。本体を持つと共有の意味がなくなり、メモリが列数倍になる。
