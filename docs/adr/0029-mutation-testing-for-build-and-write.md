# テストが宣言する変異は実際に落とせなければならない、を `src/core/nostr/build/`・`src/core/write/` で Stryker により強制する

このリポジトリには以前から規約がある。**すべてのテストは、コメントで「自分がどの変異 (mutation) を捕まえるためのものか」を書く。** 縦断スライスの計画・実装・レビューを何回か経て自然に生まれた慣習で、[read-layer-followups.md](../design/read-layer-followups.md) の随所に実例が残っている。しかし**この規約自体を定めた文書は無かった** —— 存在するのは各スライスの実装計画（`docs/superpowers/archive/` へ消える）と、そこから転記されたテストコメントだけである。本 ADR がこれを初めて明文化する。

規約には自明でない前提がある。**「この変異を捕まえる」と書いたコメントが本当かどうかは、書いた本人の推論では検証できない。** 実際にこの前提を欠いたまま 4 回、独立に破られた（[read-layer-followups.md](../design/read-layer-followups.md) 「くり返し踏んだ罠」節）。

- `reaction.test.ts` / `deletion.test.ts`: フィクスチャの既定 `kind` が期待値と同じ `"1"` だったため、`String(target.kind)` を `"1"` へハードコードする変異がテストを通過した。
- `buildReply` の `kind` アサーション（`note.test.ts`）で同じ形。
- `removeFollow` のフィクスチャ順序で同じ形。
- IndexedDB のある往復テストは、宣言した変異がリクエストの処理順によってマスクされており、実際にその変異を注入しても red にならなかった。

いずれも「コメントを書き忘れた」のではなく、**コメントは書いたが内容が誤っていた**。テストは green のまま、宣言された変異は実際には捕まえられていない。**足りなかったのは規律の周知ではなく、それが本当かどうかを機械的に確かめる手段だった。**

## 決定

[StrykerJS](https://stryker-mutator.io/) を `src/core/nostr/build/**` と `src/core/write/**` に導入する（`stryker.config.json`）。ソースの各行に変異（比較演算子の反転、文字列リテラルの空文字化、条件式の `true` 化など）を注入し、既存テストを実行して、**その変異でテストが red にならなければ「survived」として報告する。** survived な変異は「その行を実際には守っていないアサーション」の機械的な証拠になる。

初回計測: 21 秒、92.57%、22 survived + 2 uncovered。survived のほとんどは本物の穴（親イベントの `root` マーカー誤判定、`mergeProfile` の配列/プリミティブ混入、`buildRepost` の relay-url 省略など）で、実アサーションを足して閉じた。閉じられなかったものは、`this.name`/エラーメッセージの文言のように **コードが `instanceof` でしか分岐しない値** —— 行単位の disable コメント（理由付き）で明示的に「等価」と扱った。最終計測は 100.00%（317 killed / 0 survived）。

### なぜこの 2 ディレクトリで、リポジトリ全体ではないか

`src/core/nostr/build/` と `src/core/write/` は、**誤りが最も高くつく場所**である。ここで作った Nostr イベントは署名され、リレーへ publish されると配信されて回収できない —— 誤ったタグを積んだイベントは「壊れて失敗する」のではなく **「そのまま publish に成功し、他人のクライアントの中でだけ誤動作する」**。テストが green でも中身が間違っている状態を最も検出したい場所であり、かつ最も検出しにくい場所でもある（誤りが自分のプロセス内で完結せず、失敗が跳ね返ってこない）。

読み取り層（`src/core/read/` 以下）は対象に含めない。理由は 2 つ。

- **誤りの帰結が非対称。** 読み取り層のバグは自分の画面が壊れるだけで、直せば直る。書き込み層のバグは他人のクライアントで見え続ける。
- **テストの性質が Stryker と噛み合わない。** 読み取り層のテストは fake relay・タイマー・IndexedDB の往復を含み遅い（`vitest run` 全体で数秒どころではない）。Stryker は変異の数だけテストスイートを繰り返し走らせるため、対象を広げるほど実行時間が積み上がる。21 秒で回るからこそ「PR の前に手元で回す」運用に乗る。

## Considered Options

- **何も強制せず、レビューに頼る** — 4 回連続で同じ defect が抜けた実績がある。レビュアーが「このテストは本当にこの変異を捕まえるか」を都度手計算するのは持続しない。却下。
- **リポジトリ全体に Stryker をかける** — 読み取り層を含めると 1 回の実行が数分〜数十分になり、「気軽に回す」が成立しなくなる。読み取り層の誤りは書き込み層ほど高くつかない（上記）ため、コストに見合わない。将来 read 層のテストが速くなれば対象拡大は再検討してよいが、今回はしない。
- **今すぐ CI に組み込み、PR をブロックする** — このリポジトリの CI はまだ Playwright (e2e) すら実行していない（[read-layer-followups.md](../design/read-layer-followups.md) 「CI が Playwright (e2e) を一度も実行していない」節）。CI 組み込みの順序は e2e を含めて別途決める話であり、本 ADR の範囲ではない。今回は npm script (`pnpm mutation`) として手元実行できる状態に留める。
- **`src/core/nostr/build/` と `src/core/write/` を対象に、CI 非組み込みでローカル実行** ← 採用

## Consequences

- **これら 2 ディレクトリでは「テストが green」がもう十分条件ではない。** 新しいビルダやライタのコードを書いたら `pnpm mutation` を回し、survived が無いことまで確かめて初めて完了とみなす。
- **正当なリファクタでも disable コメントが要る場面が出てくる。** `this.name`/エラーメッセージのように、値そのものではなく `instanceof` で分岐する箇所は変異させても検出不能で、これは規律の欠如ではなく設計上の性質である。`// Stryker disable next-line <mutator>: <理由>` を行単位で使う —— `StringLiteral` ミューテータをファイル単位・グローバルで無効化してはならない。タグ名 (`"p"`/`"root"` など) の文字列リテラルは値そのものが仕様であり、無効化すると本物の穴を隠す。
- **`thresholds.break` を初回計測の値（100）に固定した。** 回帰を機械的に止めるためのラチェットであり、上げるのは歓迎するが下げてはならない。下げる必要が生じたら、その理由を本 ADR の改訂として書く。
- **対象拡大は別の決定。** 読み取り層を含めるか、CI に組み込むかは、どちらもこの ADR が「今回はしない」と決めただけで、「しない」と決めたわけではない。実行時間・CI 整備の状況が変われば再検討してよい。
