# 画面は Passive View に徹し、動作は Mediator が裁定する

`apps/web` のコンポーネントは、次の形に揃える。

> すべてのコンポーネントを Root からなる階層構造下に置き、各コンポーネントは MVP パターンの Passive View として描画に関わるパラメータだけを操作し、動作は Chain of Responsibility でイベントをバブリングさせて、ステートマシンとして振る舞う Mediator に裁定させること。

言い換えると、次の 3 つを分ける。

- **View**：受け取ったパラメータを描くだけ。取得も書き込みもせず、押されたら「何が起きたか」をイベントとして上へ渡す
- **イベントの経路**：View から親へ、階層を遡って渡る。途中の段は、自分が裁定するものだけを受け取り、残りはさらに上へ渡す
- **Mediator**：状態を持つステートマシン。届いたイベントで次の状態を決め、読み書き（`@streets/core`）を呼び、View へ渡すパラメータを作る

## なぜ

画面を作り進めるうちに、取得・書き込み・画面の状態が部品のあちこちに散った。

- 描くだけのはずの部品が読み取りを始める：`Avatar` / `AuthorNames` / `UserCard` が `useProfile` で store を読み、足りなければ取りにいく。`ProfileHeader` と `Column` は自分で購読を作る
- 押された部品がその場で書き込む：`FollowButton` と `ActionBar` が `actions` を直接呼ぶ
- 画面の状態を部品が抱える：`Column` が重ねたカラムの配列と閉じている途中の状態を持つ。`Event` は押されたら自分でカラムを積む

このままだと、同じ操作の規則（二重送信を防ぐ、失敗をトーストへ出す、閉じる動きが終わってから外す）が部品ごとに書かれ、揃っているかを読んで確かめるしかない。View を描くだけにすれば、Storybook ではパラメータを並べるだけで全状態を出せる。裁定を 1 か所に集めれば、状態の遷移を core と同じようにテストできる。

## まだ決めていないこと

整理に着手するときに決める。決めたらこの節を書き換える。

- **Mediator の粒度**：Root に 1 つか、デッキ・カラム・スタックのように段ごとに置くか
- **Ark UI の内部状態**：メニューの開閉・フォーカス・ホバーの遅延は Ark UI（zag）が状態機械として持っている。View の内側の事情として残すか、`open` などを制御して Mediator へ上げるか
- **読み取りの置き場**：プロフィールや反応の数のように、投稿 1 件ごとに引くものまで Mediator がまとめて渡すか
- **イベントを上へ渡す仕組み**：Solid の context で親のハンドラを連ねるか、DOM のイベントとして泡立てるか

## Consequences

- 新しく作る部品は、この形で書く。既存の部品は Issue で整理するまで今の形のまま置く
- View のストーリーは、パラメータとイベントの受け口だけで書けるようになる（読み取り層の差し替えが要らなくなる）
- Mediator の状態遷移は、UI の単体テストではなく純粋なロジックとしてテストできる
