# 画面は Passive View に徹し、動作は Mediator が裁定する

`apps/web` のコンポーネントは、次の形に揃える。

> すべてのコンポーネントを Root からなる階層構造下に置き、各コンポーネントは MVP パターンの Passive View として描画に関わるパラメータだけを操作し、動作は Chain of Responsibility でイベントをバブリングさせて、ステートマシンとして振る舞う Mediator に裁定させること。

言い換えると、次の 4 つを分ける。

- **View**：受け取った props を描くだけ。取得も書き込みもせず、押されたら「何が起きたか」をイベントとして上へ渡す
- **Presenter**：読み取り（store・購読）を props に変えて View へ渡す。動作は持たない
- **イベントの経路**：View から親へ、階層を遡って渡る。途中の段は、自分が裁定するものだけを受け取り、残りはさらに上へ渡す
- **Mediator**：状態を持つステートマシン。届いたイベントで次の状態を決め、書き込み（`@streets/core`）を呼ぶ

## なぜ

画面を作り進めるうちに、取得・書き込み・画面の状態が部品のあちこちに散った。

- 描くだけのはずの部品が読み取りを始める：`Avatar` / `AuthorNames` / `UserCard` が `useProfile` で store を読み、足りなければ取りにいく。`ProfileHeader` と `Column` は自分で購読を作る
- 押された部品がその場で書き込む：`FollowButton` と `ActionBar` が `actions` を直接呼ぶ
- 画面の状態を部品が抱える：`Column` が重ねたカラムの配列を持つ。`Event` は押されたら自分でカラムを積む

このままだと、同じ操作の規則（二重送信を防ぐ、失敗をトーストへ出す、閉じる動きが終わってから外す）が部品ごとに書かれ、揃っているかを読んで確かめるしかない。View を描くだけにすれば、Storybook では props を並べるだけで全状態を出せる。裁定を 1 か所に集めれば、状態の遷移を core と同じようにテストできる。

## 決めたこと

**Mediator は段ごとに置く。** Root（セッション）・デッキ（カラムの並び・開いているパネル・並べ替え・一時カラム）・カラム（設定の開閉・重ねた段）のように、階層の段ごとに 1 つ。Root に 1 つだけにすると、デッキ・カラム・投稿の状態が 1 か所に集まって大きくなる。

**状態の遷移は純粋関数として `@streets/core` に書く。** `(state, event) => state` の形にし、テストはそこへ書く（UI の単体テストは書かない方針のまま）。書き込みの呼び出しや Toast への通知は、遷移の結果を見て `apps/web` 側の Mediator が行う。

**イベントは Solid の context で上へ渡す。** 各段が `dispatch` を context で配り、自分が裁定しないイベントは親の `dispatch` へ渡す。イベントは判別可能な union で型を付ける。DOM の CustomEvent にしないのは、メニューやダイアログが Portal で body の末尾に出るため。DOM 上は元の親の外にあるが、Solid の所有ツリー上は元の場所にいるので、context なら経路が途切れない。

**投稿 1 件ごとの読み取りは Presenter が持つ。** プロフィールや反応の数は、Presenter（例: `EventPresenter`）が store を読んで View（例: `EventView`）の props にする。Mediator は読み取りの細部を持たない。

**Ark UI の内部状態のうち、見た目の都合は View の内側に残す。** メニューの開閉・フォーカス・ホバーの遅延は Ark UI（zag）が状態機械として持っており、アクセシビリティもそこにある。アプリの動作が開閉に依存するもの（重ねたカラムの段など）だけ、`open` を制御して Mediator が持つ。

## Consequences

- 新しく作る部品は、この形で書く
- 既存の部品は #368 で整理する。1 つの PR にまとめず、状態の遷移がはっきりしているスタック（重ねたカラム）から始め、形を確かめてから広げる
- View のストーリーは、props とイベントの受け口だけで書けるようになる（読み取り層の差し替えが要らなくなる）
