# 大域予算のもとで冗長度つき貪欲集合被覆によりリレーを選ぶ

`selectRelays`（`src/core/read/relay-selector.ts`）は、[ADR-0011](./0011-performance-budget.md) の同時接続上限 [`MAX_CONNECTIONS = 30`](../../src/core/read/default-relays.ts) のもとで、どの write リレーを実際に開くかを決める純関数である。冗長度は [`RELAY_REDUNDANCY = 2`](../../src/core/read/default-relays.ts)（[ADR-0016](./0016-routing-bootstrap.md) で「後続タスク #3 の選定器」として予告されていたのがこれである）。

## 決定

冗長度つきの**貪欲集合被覆**で選ぶ。各著者について「まだ何本のリレーを確保する必要があるか」を管理し、毎ステップで**残り必要な著者を最も多くカバーするリレー**を 1 本ずつ選ぶ。予算 (`budget`) に達するか、選んでも誰の必要も満たさなくなったら止める。

根拠は実測（[docs/research/2026-08-01-outbox-connection-budget.md](../research/2026-08-01-outbox-connection-budget.md)）。フォロー 1300 人規模の実アカウント 4 名で、write リレーは 378〜1251 本に分散しているが、貪欲に選べば **30 本で冗長度 2 の被覆率 96〜98%**（冗長度 1 なら 99〜100%）に達する。残り 1000 本以上は数 % の著者のためだけに存在する。**したがって 30 本は「足りないときにどう調停するか」という窮乏の問題ではなく、「どの 30 本を選ぶか」という被覆の問題である。** この関数はその方針を丸ごと閉じ込める。

## 却下した案

**セクションごとの予算分割。** 10 カラムそれぞれに `30/10 = 3` 本ずつのように予算を割ると、各カラムがフォローする著者は重なり合う（同じユーザーが複数カラムで同じ著者を追っていることが普通にある）ため、カラムをまたいで同じリレーへの重複接続が生まれ、実測で足りている 30 本の大半をカラム境界で無駄に消費する。集合被覆が効くのは要求全体を一度に見たときだけであり、事前分割はその情報を捨てる。[ADR-0016](./0016-routing-bootstrap.md) が著者ごとの本数制限（`MAX_RELAYS_PER_AUTHOR`）を廃止した理由と同型の失敗である。

**優先度キューによる遅延接続。** 予算超過分を「後で接続する」キューに積んで順次昇格させる案。実測が示すのは、30 本で被覆できない著者はもともと write リレーを 1 本しか宣言していないなど**この選び方では原理的に救えない層**（2〜5%）が大半だということ。キューが実際に働くのはこの数 % に対してだけであり、キュー・昇格・降格の状態機械を追加する複雑さに見合わない。素朴な貪欲 1 発で 96〜98% が取れる以上、遅延接続は後回しにできる最適化であって初期実装の要件ではない。

## `min(redundancy, 宣言本数)` で初期化する理由（2026-08-01 訂正）

各著者の残り必要本数を `redundancy`（例: 2）ではなく `min(redundancy, urls.length)` で初期化する。write リレーを 1 本しか宣言していない著者（実測で 2〜5%）は原理的に冗長度 2 へ到達できないので、これが本当の目標値である。

**初版はここで「redundancy で初期化すると貪欲の判断を歪める」と書いていたが、これは誤りだった。** レビューで指摘され、5000 試行のファズ（demand の形・redundancy・budget・pinned・current を振る）で divergence 0 件を確認して撤回する。

理由: `gain` は「need > 0 の著者数」を数える**ブールな**指標であり、大きさを見ない。宣言本数 k 本の著者について、k 本のうち j 本が選ばれるまでは `min` ありの `need`（`k - j`）も `redundancy` そのままの `need`（`redundancy - j`、`redundancy >= k > j` なので正）も、どちらも「正である」という点で一致する — gain への寄与は同じ回数だけ発生する。k 本すべてが選ばれ終えた後は、`min` ありなら 0、`redundancy` のままなら正のままという差が出るが、そのときにはその著者の宣言リレーは全部 `candidates` から消えているので、この差は他のどの候補の gain にも影響しない。結果として `picks` / `assignment` / `uncovered` は両方の初期化で完全に一致する。

**`min` が変えるのは選定結果ではなく、この研究計測（[docs/research/2026-08-01-outbox-connection-budget.md](../research/2026-08-01-outbox-connection-budget.md)）が出す「充足率」という指標である。** 「宣言本数に対して何人が目標冗長度に達したか」を数えるとき、`redundancy` で初期化した集計は 1 本しか宣言していない著者を分母はそのままに「未達」として扱ってしまい、被覆率を過小評価する。`min` はこの計測上のバイアスを取り除く。関数の出力ではなく計測のための正しい定義である。

**それでも `min` を残す。** 意味的に正しい値であり、`gain` が現状の「need > 0 の著者数」というブールな数え上げではなく、将来「1 本選ぶことで回復する冗長度の大きさ」のような重み付き指標になれば、`min` の有無が選定結果そのものを左右するようになる。そのときのために正しい値を保持しておく。

## 粘着性は同点のときだけ効く

`current`（いま開いているリレー）は、被覆への貢献が同点の候補が複数あるときの決定順にだけ影響する。目的はカラムを 1 つ追加するたびに 30 本を全部張り直し、他の全カラムの `phase`（[ADR-0015](./0015-section-status-excludes-renderer-fetches.md)）を巻き戻す churn を避けることである。

**被覆を犠牲にしてまでは維持しない。** 同点でなければ、より多くの著者をカバーする新しいリレーが常に勝つ。すでに開いているリレーがその役目を終えて誰の需要も満たさなくなれば、選ばれなくなる（回帰テスト「does not keep a current relay that has become useless」）。したがって churn は減るが、ゼロにはならない — 著者のフォロー先が変わる、リレーが `kind:10002` を更新するなどで貪欲の最適解自体が動けば、粘着性があっても入れ替わりは起こる。これは意図的なトレードオフであり、粘着性を「安定性の保証」として呼び出し側が当てにしてはならない。

## 関数の形

`budget` と `redundancy` は `MAX_CONNECTIONS` / `RELAY_REDUNDANCY` を import せず、引数として受け取る。これにより関数はテスト容易であり、予算 1 や冗長度 2 といった小さな数値で貪欲の分岐を直接検証できる。実際の呼び出し元（後続タスクで `SubscriptionManager` に配線）が定数を渡す。

`pinned`（ユーザーが明示指定したリレー・fallback）は予算を消費するが、被覆に寄与しなくても決して落とさない。ユーザーが明示的に指定したリレーを、貪欲アルゴリズムが「役に立たない」と判断して黙って外すのは驚き最小の原則に反する。`pinned.length >= budget` のときは pinned が予算を使い切り、全著者が `uncovered` になる — これは仕様であり、バグではない。

**`pinned` は予算の優先権であって免除ではない（2026-08-01 追記）。** [ADR-0005](./0005-outbox-model-from-v1.md) が言う「明示指定は著者ルーティングをバイパスする」は、[ADR-0011](./0011-performance-budget.md) の同時接続上限をバイパスすることまでは意味しない。30 はユーザーの意図で無料にできない資源上限であり、`pinned` が `budget` を超えれば超えた分はやはり `picks` から落ちる（上のとおり、すでにテスト済みの挙動）。ユーザーが名指ししたリレーは他の候補より先に確保されるが、際限なく確保されるわけではない。

**ブートストラップのインデクサは `pinned` ではない（2026-08-02 訂正）。** この ADR の初版・[設計仕様](../superpowers/specs/2026-08-01-connection-pool-design.md)はいずれも「インデクサは `pinned`」と書いていたが、接続プールの実装 (`bootstrap.ts` / `ConnectionPool.subscribe()` の `{ reserved: true }`) はそうなっていない — インデクサはこの関数の `pinned`/`demand` のどちらにも一切渡らず、`selectRelays` を経由せずに `ConnectionPool` の予算チェックそのものを迂回する、意味の異なる別の仕組み (`reserved`) を使っている。`pinned` は「この関数の中で予算を優先的に確保する」ものであり、`reserved` は「この関数を経由せず予算チェック自体を飛ばす」ものである — 後者はブートストラップ専用の脱出口であり、この関数の契約の一部ではない。混同したままだと「30 接続」という 1 つの数字を 2 つの仕組みが別々に主張することになる。詳細と帰結 (ピーク同時接続数が `30 + |indexers|` になりうる条件) は [read-layer-followups.md](../design/read-layer-followups.md) に記録した。

## degraded な URL は候補から完全に外す（Task 4 追記）

`selectRelays` は省略可能な `degraded`（`ConnectionPool.degradedRelays`、リレー自身に起因する連続失敗が `DEGRADED_AFTER_FAILURES` に達した URL）を受け取り、`demand` から `relayToAuthors` を組み立てる段階でこれに含まれる URL を丸ごと候補から除く。「最後の手段として残す」ことはしない —— 到達不能なリレーを著者に割り当てても被覆は 1 本も増えず、`budget` の枠だけが埋まって他の著者に回らなくなるからである。実地（2026-08-05）では `.onion` アドレスがこれを最も分かりやすく実演した: `replan()` のたびに同じ死んだ URL が選ばれ直し、その枠は永久に誰にも使われなかった。

degraded な URL しか宣言していない著者は `uncovered` に落ちる。これは [ADR-0011](./0011-performance-budget.md) の「劣化を隠さない」に適う挙動であり、バグではない —— `uncoveredAuthors` として正直に数が上がり、呼び出し側（`SectionPlan.uncoveredAuthors`）を通じて UI まで届く。

**`pinned` にはこの除外を適用しない。** `pinned` にはユーザーが明示指定したリレー・fallback・ブートストラップのインデクサが入る。これらを選択器が黙って落とすと、ブートストラップ経路そのものが静かに壊れる。degraded な pinned URL は今までどおり選ばれ続け、`ConnectionPool` は（[ADR-0021](./0021-reconnection-policy.md) のとおり）誰かが購読している限り再接続を試み続ける。

除外は再選択の話であって再接続の話ではない —— この区別と、degraded からの復帰経路 (`DEGRADED_COOLDOWN_MS` によるクールダウン) の詳細は [ADR-0021](./0021-reconnection-policy.md) を参照。

## Consequences

- **`assignment` は `demand` の全著者を含む。** 1 本も確保できない著者も空配列で入る（著者が丸ごと欠落するわけではない）。`planQuery` は「`demand` に著者がいない（relay list 自体が未解決）」「著者はいるが空配列」「著者がいて非空（購読先が決まっている）」の 3 通りを、この契約に基づいて区別する。**空配列になる理由は 2 つある** —— 接続予算で落ちた場合と、宣言リレーが全部 `degraded` だった場合（2026-08-06 追記）。区別せずどちらも `uncoveredAuthors` に数える。原因の内訳が要るなら、それは別の指標として足すこと。
- **選定は決定的だが最適ではない。** 集合被覆は NP 困難であり、貪欲は近似解法である。同点はリレー URL の辞書順で解決するため、同じ入力には常に同じ出力を返すが、理論上のベスト 30 本と一致する保証はない。実測（[research doc](../research/2026-08-01-outbox-connection-budget.md) 3節）でもこれは理論上限ではなく実装予定のアルゴリズムそのものの性能である。
- **接続の入れ替わり（churn）は残る。** 粘着性は同点のときしか効かないので、フォロー先の変化や `kind:10002` の更新で貪欲の最適解が動けば、すでに開いているリレーでも閉じられうる。呼び出し側（`SubscriptionManager`）は接続の open/close 自体にコストがあることを前提に、この関数の出力をそのまま毎回全張り替えするのではなく差分適用する必要がある。
- **`redundancy` を下げるほど churn とオーバーヘッドは減るが、片方のリレーの取りこぼしで著者がタイムラインから静かに消える（[ADR-0016](./0016-routing-bootstrap.md) 参照）リスクが上がる。** 既定値 2 の選定はこの関数の外（`default-relays.ts`）にある。
