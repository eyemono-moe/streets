# 性能予算を数値で固定し、E2E で測定可能にする

v1 は以下の性能予算を満たす。**これらは E2E テスト（Playwright）で測定可能でなければならない。測定できない予算は要件ではなく願望である。**

| 指標 | 予算 |
|---|---|
| 快適に動作するカラム数 | 10 列 |
| 動作を保証する上限カラム数 | 20 列（超過時は警告を表示する） |
| 1 セクションが保持するイベント数 | 200 件（超過分は古い方から破棄） |
| 同時 WebSocket 接続数 | 30 リレー（上限） |
| 初回イベント表示まで | 2 秒（ログイン済・キャッシュあり） |
| 操作の画面反映（リアクション等） | 100 ms（楽観的更新、リレー応答を待たない） |
| タブのメモリ使用量 | 500 MB 以内（10 列・各 200 件の状態で） |

## なぜ数値を先に決めるか

v1 の設計判断が、性能負債を構造的に積み上げているため。

- [ADR-0004](./0004-kind-knowledge-lives-in-kind-specific-code.md): レンダラが関連イベントを個別に要求する → **N+1**
- [ADR-0005](./0005-outbox-model-from-v1.md): 著者ごとにリレーを引く → **N+1 の二重化と接続数の増加**
- マルチカラム: 上記に**カラム数の掛け算**が乗る

素朴に実装すると購読数が三重の掛け算で爆発する。予算を後から決めると「動くが重い」実装が既成事実化する。

## 明示的に受け入れた劣化

- **同時接続 30 リレーの上限により、一部の著者の投稿が取得できない状況が発生する。** これを許容するが、**黙って欠落させてはならない** — 取得できていない著者がいることをユーザーに見せる。無制限に接続して重くなるより、上限を設けて欠落を明示するほうを選ぶ。

  **この項の「ユーザーに見せる」は [ADR-0026](./0026-actionable-errors-visible-diagnostics-behind-developer-mode.md) が改訂した（2026-08-06）。** 常に見せるのはユーザーが行動できる異常だけとし、`uncoveredAuthors` のように行動に移せない診断値は開発者モードの背後に置く。**「黙って欠落させてはならない」は撤回していない** —— 値を計算し続けること、セクションが完全なふりをしないこと、E2E で測定可能であること（本 ADR の中心的な要求）はいずれも要件のまま。改訂の根拠は、実鍵でこの数値が画面に出ている状態を初めて見た結果である。
- **1 セクション 200 件を超えると古い方から破棄するため、長時間開いたカラムではスクロールで戻れる範囲が有限になる。**

  **この項の件数は 500 件から 200 件へ改めた（2026-08-14）。** 当初の 500 件は「保持数」として決めた数だが、**保持数と描画数を同じ数にしていた**ため、カラム 3 本で 1500 件が一度に DOM へ現れ、初回描画がメインスレッドを 1.2 秒塞いでいた（実測は `docs/design/read-layer-followups.md`）。描画数を保持数から切り離した（先頭 40 件から段階的に増やす）ことで、保持数に残る意味は「どこまで遡れるか」だけになった。遡れる範囲は 500 件ぶんから 200 件ぶんへ浅くなる —— **測定可能であること（本 ADR の中心的な要求）は変わらず、`e2e/section-cap.spec.ts` が新しい値を主張する。**

## Consequences

達成手段（キャッシュ戦略、ライブラリ選定など）は詳細設計で決める。本 ADR は予算値のみを固定する。
