# カラムを「イベントの配列」の開いた抽象とし、kind 別レンダラで拡張する

v0 はカラム種別を 9 種の閉じた union（`timeline` / `notifications` / `user` / `reactions` / `reposts` / `followees` / `followers` / `thread` / `search`）として定義し、種別ごとに専用のデータ取得とコンポーネントを実装していた。

v1 ではこれを廃止し、**カラムは「イベントの配列を表示するもの」という開いた抽象**とする。新しい種類の表示を増やす作業は、原則として **kind に対応するレンダリングコンポーネントを1つ足すだけ**になることを目指す。

## なぜ

Nostr では **NIPs が頻繁に更新され、イベントの定義そのものが変わる**。カラム種別ごとに取得と表示を個別実装していると、1つの NIP 変更が複数のカラム実装に波及する。

kind 単位でレンダラを分離すれば、**NIP の変更による修正範囲がその kind に閉じる**。これは NIPs 追従を LLM による自動 PR パイプラインに乗せる計画（別途決定）とも直結する — 変更範囲が機械的に特定できることが前提になるため。

## Consequences

- v0 の `reactions` / `reposts` / `followees` / `followers` カラムは **個別実装せず Could に降格**する。カラム抽象が正しく作れていれば、これらは個別実装なしに表現できるはずであり、**逆にこれらを個別 Must にすると抽象を作る動機が失われる**。この降格は抽象の正しさを検証するテストケースとして機能する。
- 「イベントの配列」に素直に収まらないケース（ユーザー詳細、スレッド、ブックマークセット、フォロー中一覧など）をこの抽象がどう扱うかを別途定義する必要がある。抽象の妥当性はそこで決まる。
- 未知の kind に対するフォールバック表示が必須になる（レンダラが未実装でもカラムが壊れないこと）。

## 実装の段階

- **v1 縦断スライス（2026-08-05）** — レンダラ登録機構は**まだ実装しない**。**撤回ではない** —— 縦断スライスの目的は「読み取り層を使う画面を初めて実際に動かす」ことであり、抽象を実物なしに設計することを避けるためにあえて薄く作った（詳細は[仕様](../superpowers/specs/2026-08-04-v1-vertical-slice-design.md) 2 節）。実際に足したのは kind:1 専用の `Note` コンポーネント（`src/routes/v1-preview/Note.tsx`）1 つを `<For>` で直に描画するだけの形で、kind 別レンダラの登録・フォールバック表示・未知 kind の扱いはいずれも作っていない。一般形は本 ADR のまま据え置く。
- **A-1（デッキとカラム、2026-08-07）** — レンダラ登録機構は依然として**まだ実装していない**（A-2 待ち）。`Note` コンポーネント（ルート移設に伴い `src/routes/v1/Note.tsx` へ移動）を `<For>` で直に描画する形は変わっていない。

  一方で、本 ADR が「別途定義する必要がある」としていた 4 ケースのうち 3 つに決着がついた（[仕様](../superpowers/specs/2026-08-07-deck-and-columns-design.md) 5 節、決定として記録）。「1 本のリストに混ぜる」（例: 通知）は `NostrSource.filters` の複数フィルタ（NIP-01 の OR）で表現できる。「構造を持つ」（例: スレッド）は `Order` の `thread-tree` が表現できる。**残る「領域を積む」（例: ユーザー詳細 — プロフィール + 固定ポスト + 投稿一覧）だけは、`filters`（何を取るかしか言えない）にも `Order`（1 つのメンバーシップ集合に対する順序）にも `needs`（[ADR-0017](./0017-declarative-renderer-needs.md)、このイベントを描くのに他に何が要るか）にも表現手段が無い。**

  A-1 はここを「1 カラム = 1 セクション」という決定として明記し、**ひっくり返す条件も明記した: ユーザー詳細カラムを作るとき。** それが「領域を積む」の最初の実例であり、レンダラ登録機構（A-2）を実装する人が、セクションとレンダラの境界をその実例に合わせて同時に決めることになる。`Deck.version`（現在 2）はこの種の変更のための足場として残してある。

  A-1 が実際に作った 4 種別と、それぞれが通す読み取り層の経路:

  | 種別 | `ColumnSource` | 経路 |
  |---|---|---|
  | ホーム | `{ kind: "followees", kinds: [1] }` | 派生（`resolveSource` が描画のたびにフォローリストを展開） + Outbox ルーティング（多数著者） |
  | ユーザー | `{ kind: "literal", filters: [{ kinds: [1], authors: [pubkey] }] }` | Outbox ルーティング（単一著者）。write relay が引けなければ `unroutableAuthors` |
  | ハッシュタグ | `{ kind: "literal", filters: [{ kinds: [1], "#t": [tag] }] }` | `authors` を持たないフィルタ → `fallbackRelays`（pinned、接続予算から落ちない） |
  | グローバル | `{ kind: "literal", filters: [{ kinds: [1] }], relays: [...FALLBACK_RELAYS] }` | 明示リレー、Outbox バイパス |

  6 問への回答の根拠と、まだ実地で確かめていない項目は [followups「A-1 デッキとカラム」節](../design/read-layer-followups.md) を参照。

- **A-2（レンダラと関連イベント、2026-08-07）** — [ADR-0017](./0017-declarative-renderer-needs.md) が定めるレンダラ登録機構を**初めて実装した**。`src/core/view/renderer-registry.ts` の `defineRenderer`/`rendererFor` と、唯一の描画入口 `src/routes/v1/EventView.tsx` が骨組みで、kind ごとに `full`/`compact` の 2 表示を持つ（[仕様](../superpowers/specs/2026-08-07-renderers-and-related-events-design.md) 3 節）。実際に登録したのは kind:1（`Note`）と kind:6/16（`Repost`、2 kind が同じレンダラを共有）の 2 組のみ。

  **未登録 kind への fallback（`UnknownKind.tsx`）は実地で効いた。** 最初にこの経路を踏んだのは、kind:16（汎用リポスト）の対象が未登録 kind であるケースで、`Repost.tsx` は対象イベントの `k` タグを一切読まず、対象自身の実 kind を `EventView` に渡して選ばせる（Task 4 報告）。これにより「レンダラが未実装でもカラムが壊れない」という本 ADR の要件を、決め打ちではなく実データで確認した。

  **A-1 が「1 カラム = 1 セクション」のひっくり返す条件として挙げていたユーザー詳細カラムは、A-2 でもまだ来ていない。** A-2 が実装した kind:1・kind:6/16・未登録 kind はいずれも「1 イベント = 1 描画」の範囲に収まり、「領域を積む」（プロフィール + 固定ポスト + 投稿一覧のような複数領域の合成）を要求する場面は生じなかった。セクションとレンダラの境界をその実例に合わせて決める作業は、依然としてユーザー詳細カラムが実際に作られるときまで先送りされている。
