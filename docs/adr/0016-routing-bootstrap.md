# ルーティング表は専用経路で構築し、ログイン時にウォームアップして永続キャッシュする

`kind:10002` の取得だけは **Outbox ルーティングを使わない専用経路**（ユーザー自身の read relay + 既定リレー）で行う。これにより「ルーティングには `kind:10002` が要る / その取得にはルーティングが要る」という循環を定義的に断つ。

そのうえで:

- **ログイン時にフォロー中全員分を1クエリでウォームアップする。** `{kinds:[10002], authors:[...]}` の1クエリであり、著者数分のクエリにはならない。
- **ルーティング表を TTL 付きで永続キャッシュする。**
- **未解決の著者は既定リレーへ暫定的に送信し、解決後に張り直す。** その間その著者は `status.incomplete.unroutableAuthors` に計上される（[ADR-0015](./0015-section-status-excludes-renderer-fetches.md)）。

## トレードオフ

初回起動は遅くなる。ウォームアップを待つため [ADR-0011](./0011-performance-budget.md) の「初回イベント表示 2 秒」を初回だけ割る。

これを受け入れられるのは、ADR-0011 の予算値が**「キャッシュあり」を条件としている**ため。2 回目以降の起動はキャッシュから即座にルーティングできる。

完全遅延解決（ウォームアップなし）を採らなかったのは、後からタイムラインに投稿が流れ込んで順序が乱れ、マルチカラムではその「チラつき」が同時に何列でも起きるため。逆にウォームアップ完了までセクションを開始しない方式は、新規ユーザーの第一印象を確実に損なう。

## Consequences

- **デッキ保存（[ADR-0013](./0013-deck-persisted-to-nip78.md)）とは別に、ルーティング表の永続キャッシュが必要になる。** これは要件定義の時点では洗い出せていなかった新しい永続化要件。保存先とサイズ上限を別途決める。
- キャッシュの TTL 切れと、著者が `kind:10002` を更新した場合の追従方法を決める必要がある。
- 既定リレーの選定が、ブートストラップの成否に直結するようになった（要件定義時の未解決事項4）。
