# ルーティング表は専用経路で構築し、ログイン時にウォームアップして永続キャッシュする

`kind:10002` の取得だけは **Outbox ルーティングを使わない専用経路**（ユーザー自身の read relay + 既定リレー）で行う。これにより「ルーティングには `kind:10002` が要る / その取得にはルーティングが要る」という循環を定義的に断つ。

そのうえで:

- **ログイン時にフォロー中全員分を1クエリでウォームアップする。** `{kinds:[10002], authors:[...]}` の1クエリであり、著者数分のクエリにはならない。
- **ルーティング表は `EventStore` 内の `kind:10002` から導出する。専用の永続化を持たない。**
- **未解決の著者は既定リレーへ暫定的に送信し、解決後に張り直す。** その間その著者は `status.incomplete.unroutableAuthors` に計上される（[ADR-0015](./0015-section-status-excludes-renderer-fetches.md)）。

### ルーティング表を導出状態として扱う（2026-08-01 改訂）

初版は「ルーティング表を TTL 付きで永続キャッシュする」とし、それを「デッキ保存とは別の新しい永続化要件」として記録していた。**これを撤回する。**

ルーティング表は `EventStore` が保持する `kind:10002` イベントから導出できる。専用の保存先も TTL も要らない。**永続化は [ADR-0018](./0018-indexeddb-event-cache.md) の IndexedDB が `kind:10002` を普通のイベントとして保存すれば自動的に得られる** — [ADR-0019](./0019-two-bucket-cache-policy.md) の「参照データ」バケット（置換可能イベントを著者ごと最新1件だけ全保持）がまさにこの形であり、鮮度も置換可能イベントの `created_at` 後勝ちで決まるので TTL の設計が不要になる。

welshman と applesauce が実際にこの形を採っている（[調査](../research/2026-08-01-nip65-relay-selection.md) 2.3 節）。

**実装上の帰結**: 同一 pubkey の `kind:10002` が複数版返ることがある（`purplepag.es` で最大4版を実測）。導出時は **`created_at` 最大の版を採る**こと。

### 著者ごとの本数制限を廃止し大域予算に置き換える（2026-08-01 改訂）

初版は著者ごとに `MAX_RELAYS_PER_AUTHOR = 3` で relay list を切り詰めていた。**これを廃止する。**

その理由は [実測](../research/2026-08-01-outbox-connection-budget.md) で判明した。各著者のリストを先頭 3 本で切ってから全体を選ぶと、最小リレー被覆（貪欲集合被覆）が必要とする情報をまさに捨てることになる。同一被験者・同一予算 30 本・冗長度 1 で比較すると、**切り捨てありでは 95〜98%、外すと 99〜100%** だった。制限は**著者ごとではなく大域の予算として持つべきである。**

具体的には:
- **`RoutingTable` は宣言された relay list をそのまま返すようにした。** 著者ごとの切り詰めを外す。
- **大域予算定数を置いた**: `MAX_CONNECTIONS = 30`（全体で同時に開く WebSocket の上限）と `RELAY_REDUNDANCY = 2`（1 著者あたり何本の relay から選ぶか）。これらの値と実測の詳細は [research doc](../research/2026-08-01-outbox-connection-budget.md) にある。
- **後続タスク（タスク #3）の選定器が**、このグローバル予算のもとで最適に選ぶ責務を持つ。

## 既定リレーは 2 つのリストに分ける

**「既定リレー」を単一のリストにしない。** 用途の異なる 2 つに分ける。

| 名前 | 用途 | 使われる場面 |
|---|---|---|
| `BOOTSTRAP_INDEXERS` | `kind:10002` と `kind:0` を引く専用経路 | 上記のウォームアップ、未知の著者に遭遇したとき |
| `FALLBACK_RELAYS` | ルーティングできない著者の投稿を取りに行く先 | `unroutableAuthors` に計上される著者の暫定送信先 |

分ける理由は 3 つ。① `indexer.coracle.social` のように `kind:10002` しか返さないリレーが実在し、汎用フォールバックには使えない。② インデクサは「短時間に大量の著者を一括問い合わせ」する使い方なので、`max_subscriptions` より `max_limit` と応答速度が効く。③ [ADR-0011](./0011-performance-budget.md) の 30 接続上限のもとで、両者は別の予算を持つべき（インデクサは起動時に一瞬、フォールバックは常時）。

調査した成熟クライアント（Amethyst / Coracle / noStrudel / Snort / Nostur / nostter、および NDK・applesauce・welshman）は**全員が独立にこの分離に到達している**。

具体的なリストと各リレーの選定根拠、および実測データは [docs/research/2026-08-01-nip65-relay-selection.md](../research/2026-08-01-nip65-relay-selection.md) にある。**このリストは半年で腐る前提で扱うこと。**

**locale による分岐は持たない。** Damus / Rabbit / nostter は `ja` 判定で日本向けリレーを足しているが、streets は日本語圏に強いリレーを無条件で既定に含める。分岐は「日本語 locale でない日本語話者」を取りこぼし、それは [ADR-0001](./0001-others-first-self-via-settings.md) の想定利用者に多い層である。

**将来的にはハードコードをやめ、最新のリレー利用状況を API から取得する形にしたい**（[ADR-0022](./0022-deploy-to-cloudflare-workers-static-assets.md)）。ハードコードされたリストは腐るという実例が既に観測されている（nostter が今も積む `nrelay-jp.c-stellar.net` は 502、Damus の `eden.nostr.land` は改名済み）。

## トレードオフ

初回起動は遅くなる。ウォームアップを待つため [ADR-0011](./0011-performance-budget.md) の「初回イベント表示 2 秒」を初回だけ割る。

これを受け入れられるのは、ADR-0011 の予算値が**「キャッシュあり」を条件としている**ため。2 回目以降の起動はキャッシュから即座にルーティングできる。

完全遅延解決（ウォームアップなし）を採らなかったのは、後からタイムラインに投稿が流れ込んで順序が乱れ、マルチカラムではその「チラつき」が同時に何列でも起きるため。逆にウォームアップ完了までセクションを開始しない方式は、新規ユーザーの第一印象を確実に損なう。

## Consequences

- ~~デッキ保存とは別に、ルーティング表の永続キャッシュが必要になる~~ — **上記の改訂により不要になった。** `kind:10002` は普通のイベントとして扱えばよく、新しい永続化要件は発生しない。
- ~~キャッシュの TTL 切れと、著者が `kind:10002` を更新した場合の追従方法を決める必要がある~~ — **同上。** 置換可能イベントの `created_at` 後勝ちで決まる。
- **導出は `created_at` 最大の版を採ること。** 同一 pubkey の複数版が返るリレーが実在する。
- 既定リレーの選定が、ブートストラップの成否に直結するようになった。選定と実測は [調査](../research/2026-08-01-nip65-relay-selection.md) にあり、2 つのリストに分けた（上記）。
- **永続化が入るまで（後続 #4）は毎回の起動でウォームアップが走る。** [ADR-0011](./0011-performance-budget.md) の「初回イベント表示 2 秒」は「キャッシュあり」を条件としているため要件違反ではないが、#4 までは体感が遅い状態が続く。
