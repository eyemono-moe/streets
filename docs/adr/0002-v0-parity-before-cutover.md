# v0 機能パリティを満たしてから一括切替する

v1 は v0 の全面書き換えだが、`streets.eyemono.moe` の置き換えは **v0 の機能パリティを満たしてから一括で行う**。未完成の v1 を本番に出して育てる方式は取らない。

これは [ADR-0001](./0001-others-first-self-via-settings.md)（他人が使えることを優先する）の帰結でもある。訪問者に機能退行した状態を見せない。

## Considered Options

- **最小セットで早期切替、以後育てる** — フィードバックは早いが、一時的に機能退行する。ADR-0001 と衝突する。
- **v0 機能パリティを満たしてから一括切替** ← 採用
- **別 URL で並走** — 2 系統の維持コストに対し、現状の利用規模（スター 9）では見合わない。
- **即座に本番へ出し壊れたまま育てる** — ADR-0001 と正面衝突するため却下。

## Consequences

- **v1 の Must は「v0 機能パリティ」で下限が固定される。** 何を Must とするかの議論は「v0 に何があるか」から始まる。
- 切替までフィールドからのフィードバックが得られない。設計の誤りが長期間露見しないリスクを負う。
- 個人開発で最も完成しにくいパターンであるため、**Must の絞り込みと v0 機能の棚卸し（捨てる機能の明示）が成否を分ける**。
- 開発中の v1 をどこで動作確認するかは別途決める（ローカル + `/debug` ルート、またはプレビューデプロイ）。

## 本番切替の戦略と開発の順序は別の問い（2026-08-04 追記）

本 ADR が決めているのは**本番切替の戦略**だけである。`streets.eyemono.moe` に未完成の v1 を出さない、という**ユーザー向け**の約束であり、**開発の順序**（読み取り層を作り切ってから UI を載せるかどうか）を一言も要求していない。

この区別が無いまま読むと、「ADR-0002 があるから機能が揃うまで画面を作らない」と誤読できてしまう。**実際にこのプロジェクトはその誤読の下で 201 コミット進んだ** — 読み取り層 3,056 行・そのテスト 6,142 行を積みながら、それを使う画面がデバッグルート 1 本しか無い状態を許した（詳細は[read-layer-followups.md](../design/read-layer-followups.md)の「外部レビュー（2026-08-04）」節）。

内部ルート（`/v1-preview` など）で縦断スライスを動かすことは、本番へ何も出していない以上、本 ADR と両立する。上記 Consequences の「切替までフィールドからのフィードバックが得られない」というリスクは、`streets.eyemono.moe` への一括切替という戦略にのみかかる話であり、社内・開発者自身が内部ルートを実際に動かして得るフィードバックとは別物である。
