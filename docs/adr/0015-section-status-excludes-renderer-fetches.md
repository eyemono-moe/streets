# セクションの `status` はレンダラの遅延取得を含めない

セクションの `status` は **そのセクション自身のリスト**についてのみ語る。レンダラが要求する関連イベント（著者プロフィール、参照先イベントなど）の取得状況は含めない。各レンダラが自分のスケルトンを表示する。

```ts
status: {
  phase: "initial" | "streaming" | "settled"
  incomplete?: {
    unreachableRelays: number    // 接続上限や失敗で届かなかったリレー数
    unroutableAuthors: number    // kind:10002 が引けずルーティングできない著者数
    uncoveredAuthors: number     // 接続上限に収まらず計画から漏れた著者数
  }
}
```

## `phase` の観測は最大 `NOTIFY_BATCH_MS` 遅れる

`phase` が語る意味（このセクション自身のリストについてのみ、という上記の3層分離）は変わらないが、**それが `subscribe()` のリスナーへ届くタイミング**は変わった。`SectionReader`（`src/core/read/section-reader.ts`）は `items` と `status` をイベント到着のたびに同期的に更新するが、購読者への通知は `Scheduler` 経由でバッチする（`NOTIFY_BATCH_MS = 16`、60fps の1フレーム）。したがってリスナーが `phase` の変化を知るのは最大16ms遅れうる。

**`reader.status` を直接読めば常に最新である。** 遅れるのは通知だけであり、`items` と `status` はいつ読んでも同期的に正しい。`createSection` は `start()` の直後に `sync()` を明示的に呼んでいる（`src/core/solid/create-section.ts:49`）ので、初期状態は同期的に拾える。

## なぜこの形か

「読み込み完了」が定義できなくなっていた原因は、意味の異なる3層が混ざっていたこと。

1. **リレー単位** — 各リレーが EOSE を返した。[ADR-0005](./0005-outbox-model-from-v1.md) によりリレーごとに担当著者が異なるため、単体では意味を持たない。
2. **セクション単位** — 全担当リレーの EOSE が揃った。ただし接続できなかったリレーや、ルーティングできなかった著者が残りうる。
3. **レンダラ単位** — 各アイテムの関連イベントが揃った。[ADR-0004](./0004-kind-knowledge-lives-in-kind-specific-code.md) により遅延取得のため**永遠に確定しない**。

3層目を `status` から外すことで、セクションの完了は有限時間で決定できるようになる。レンダラ単位のローディングは本質的にアイテムごとの関心事であり、セクション全体の状態に集約すべきものではなかった。

## 問い合わせ先がゼロのセクションは `settled` とする

セクションのソースが `relays: []`（**明示的な空配列**）を持つ場合、購読先は 1 つも開かれない。このとき `status` は **`phase: "settled"`、`incomplete` なし**を報告する。

これは [ADR-0011](./0011-performance-budget.md) の「黙って欠落させてはならない」と衝突しない。**空集合に対するクエリの結果は空であり、そのクエリは実際に完了している。** 「どこも見ていない」のではなく「見るべき場所が存在せず、そこには何も無かった」が正しい記述であり、空虚な真は数学的に正しい答えである。欠落しているものが無いのだから、報告すべき劣化も無い。

`relays` が **undefined** の場合はこれとは別物である。そちらは「Outbox ルーティングに任せる」という意味であり、ルーティングできない著者は fallback リレーへ回され `incomplete.unroutableAuthors` に計上される（[ADR-0016](./0016-routing-bootstrap.md)）。**空配列は「指定した結果ゼロ本」、未指定は「指定しない」** — 意味が違うので挙動も違う。

`incomplete` が2フィールドから3フィールドに増えても、この判断そのものは変わらない。**「見るべき場所が存在せず、そこには何も無かった」という記述の正しさはフィールド数に依存しない。** 明示的な空リレー配列を持つセクションは、`uncoveredAuthors` を含めても常に `phase: "settled"`、`incomplete` なしを報告し続ける。

## `uncoveredAuthors` を `unroutableAuthors` に合算しない理由

接続予算（後続の Connection Pool 計画）が上限に達すると、ルーティング自体はできているのに接続を張れない著者が出る。これは `unroutableAuthors`（kind:10002 が引けない）とは原因が違う。

- `unroutableAuthors` — 相手が kind:10002 を出していない、あるいは書き込みリレーを 1 つも宣言していない。**相手側の問題であり、こちらの設定を変えても直らない。**
- `uncoveredAuthors` — 接続予算が足りず計画から漏れた。**こちら側の上限を上げれば直る。**

両者を合算すると、「設定を変えれば直るのか」という問いに `incomplete` だけでは答えられなくなる。UI が「接続上限を上げる」導線を出すべきか、「相手が kind:10002 を出すのを待つしかない」と伝えるべきかは、この2つを区別できて初めて決まる。分けて持つ分インターフェースは複雑になるが、原因ごとに異なる対処法を案内できるようにするために必要な複雑さである。

現時点（Task 4）ではマネージャは `uncoveredAuthors` を常に 0 として返す。実際に接続予算を計算し、この値を埋めるのは後続のマネージャ側の Task。

### 将来この判断を見直す条件

現時点で `relays: []` を渡す呼び出し元は存在しない。将来 `kind:10006`（ブロックリレーリスト、NIP-51）に対応し、**リレー指定カラムの候補が全てブロックされて空になる**ケースが生じたときは、「ユーザーが指定したがブロックで全滅した」ことを伝える必要が出る。その時点で `incomplete` に第 3 のフィールドを足すか否かを判断する。**今は推測で `SectionStatus` を広げない。**

## なぜ単純な3値では足りないか

[ADR-0011](./0011-performance-budget.md) は「取得できていない著者の可視化」を Must としている。接続上限により一部の著者の投稿が欠落することを許容する代わりに、黙って欠落させないことを要件にした。`loading | live | error` の3値ではこの要件を満たせない。

一方で、リレー単位の詳細をすべて公開すると、インターフェースが実装と同じ複雑さになり読み取り層が shallow になる。`incomplete` を任意フィールドとすることで、気にしない呼び出し側は無視でき、警告バッジを出す UI だけが読む形にした。
