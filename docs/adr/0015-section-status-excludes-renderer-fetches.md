# セクションの `status` はレンダラの遅延取得を含めない

セクションの `status` は **そのセクション自身のリスト**についてのみ語る。レンダラが要求する関連イベント（著者プロフィール、参照先イベントなど）の取得状況は含めない。各レンダラが自分のスケルトンを表示する。

```ts
status: {
  phase: "initial" | "streaming" | "settled"
  incomplete?: {
    unreachableRelays: number    // 接続上限や失敗で届かなかったリレー数
    unroutableAuthors: number    // kind:10002 が引けずルーティングできない著者数
  }
}
```

## なぜこの形か

「読み込み完了」が定義できなくなっていた原因は、意味の異なる3層が混ざっていたこと。

1. **リレー単位** — 各リレーが EOSE を返した。[ADR-0005](./0005-outbox-model-from-v1.md) によりリレーごとに担当著者が異なるため、単体では意味を持たない。
2. **セクション単位** — 全担当リレーの EOSE が揃った。ただし接続できなかったリレーや、ルーティングできなかった著者が残りうる。
3. **レンダラ単位** — 各アイテムの関連イベントが揃った。[ADR-0004](./0004-kind-knowledge-lives-in-renderers.md) により遅延取得のため**永遠に確定しない**。

3層目を `status` から外すことで、セクションの完了は有限時間で決定できるようになる。レンダラ単位のローディングは本質的にアイテムごとの関心事であり、セクション全体の状態に集約すべきものではなかった。

## なぜ単純な3値では足りないか

[ADR-0011](./0011-performance-budget.md) は「取得できていない著者の可視化」を Must としている。接続上限により一部の著者の投稿が欠落することを許容する代わりに、黙って欠落させないことを要件にした。`loading | live | error` の3値ではこの要件を満たせない。

一方で、リレー単位の詳細をすべて公開すると、インターフェースが実装と同じ複雑さになり読み取り層が shallow になる。`incomplete` を任意フィールドとすることで、気にしない呼び出し側は無視でき、警告バッジを出す UI だけが読む形にした。
