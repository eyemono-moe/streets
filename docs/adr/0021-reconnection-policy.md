# リレー再接続の方針は接続プールと同じ計画で決める

**この ADR はまだ承認されていない。** 数値は提案であり、実装計画に入る前に確定させる必要がある。記録する目的は、[ADR-0020](./0020-no-nostr-library-noble-primitives-only.md) が「再接続とバックオフは自分たちの責任」と明示的に引き受けたにもかかわらず、**どの実装計画もそれを担当していなかった**という抜けを塞ぐこと。

## 現状（v1 読み取り層の第1スライス時点）

切断は**終局的**である。`WebSocketRelayConnection` の `onclose` / `onerror` は接続を閉じた状態にし、全購読に `onClosed` を配り、保留中の publish を reject する。`SectionReader` はそのリレーを `unreachable` として記録する。再接続は行われず、カラムはコンポーネントが再マウントされるまで死んだままになる。

**ただし黙って壊れてはいない。** 切断は `status.incomplete.unreachableRelays` として表面化するため、[ADR-0011](./0011-performance-budget.md) の「黙って欠落させてはならない」は満たしている。劣化するが隠さない状態であり、この状態でのリリースは要件違反ではない。

## なぜ接続プールと同じ計画に置くか

**所有していない接続は再接続できない。** 再接続はソケットの生死を握っている層の責務であり、それはプールである。加えて 30 接続上限（ADR-0011）と直接干渉する — 再接続を待っているソケットが枠を占有し続けてよいのかは、上限の設計と一体でしか決められない。

したがって再接続は**ページネーションと接続プールの計画（後続計画 #3）のスコープに含める**。

## 決めるべきこと（未確定）

| 項目 | 提案 | 理由 |
|---|---|---|
| バックオフ | 指数バックオフ、初回 1 秒、上限 60 秒、ジッタあり | ジッタなしだと全リレーへの再接続が同期し、復帰時に自分でバーストを作る |
| 諦める条件 | 連続失敗 8 回、または累計 5 分 | 無限リトライはモバイルのバッテリーとリレーのレート制限の両方を削る |
| 接続枠の扱い | 再接続待ちのソケットは 30 枠を**占有しない** | 死んだ接続が枠を握ると、生きているリレーへ繋げなくなる |
| 再購読の担当 | 接続層が `REQ` を張り直す | 呼び出し側にやらせると全セクションが再購読ロジックを持つことになり、[ADR-0014](./0014-thin-relay-connection-deep-read-layer.md) の薄いアダプタという前提が崩れる |
| 再接続中の `status` | `incomplete.unreachableRelays` に計上し続ける | 復帰したら自然に減る。ユーザーには「一部取得できていない」と伝わり続ける |
| 手動再試行 | 提供する | 自動再試行を諦めた後の唯一の復帰手段になる |

## Consequences

- 再接続中に取りこぼしたイベントの扱いを決める必要がある。単純に `REQ` を張り直すと、切断中に流れたイベントは失われる。`since` を切断時刻に設定して埋めるか、欠落を許容するかは上記と同時に決める。
- リレー側から見ると再接続は新規接続であり、NIP-42 (AUTH) を要求するリレーでは認証もやり直しになる。AUTH は現時点でどの計画にも入っていない。
