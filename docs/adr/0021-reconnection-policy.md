# リレー再接続の方針

streets は開きっぱなしで使うクライアントである。ノート PC をスリープして復帰したとき、全カラムが死んだままになってはいけない。この ADR は再接続の方針を確定する — [ADR-0020](./0020-no-nostr-library-noble-primitives-only.md) が「再接続とバックオフは自分たちの責任」と明示的に引き受けたにもかかわらず、どの実装計画もそれを担当していなかった抜けを塞ぐために書き起こされ、接続プール (実装計画 #3、Task 9) で実装された。

## 現状（Task 9 実装前）

切断は**終局的**だった。`WebSocketRelayConnection` の `onclose` / `onerror` は接続を閉じた状態にし、全購読に `onClosed` を配り、保留中の publish を reject する。`SectionReader` はそのリレーを `unreachable` として記録する。再接続は行われず、カラムはコンポーネントが再マウントされるまで死んだままになる。

**ただし黙って壊れてはいなかった。** 切断は `status.incomplete.unreachableRelays` として表面化するため、[ADR-0011](./0011-performance-budget.md) の「黙って欠落させてはならない」は満たしていた。

Task 8（接続プール）が先に、自然死したソケットの予算 (ADR-0011 の 30 接続上限) を即座に解放するところまでを実装した。死んだ接続のエントリ登録 (URL ごとの filters・handlers) はプールの `#pool` レジストリに残したまま消さない — これが Task 9 の再接続で「元のフィルタをそのまま張り直す」ときの元ネタになる。

## なぜ接続プールが再接続を担当するか

**所有していない接続は再接続できない。** 再接続はソケットの生死を握っている層の責務であり、それはプールである。加えて 30 接続上限（ADR-0011）と直接干渉する — 再接続待ちのソケットが枠を占有し続けてよいのかは、上限の設計と一体でしか決められない。

死んだリレーのエントリ登録（filters・handlers の集合）は、予算追跡のためにどのみちプールが保持している。これを接続層 (`RelayConnection`) 側に持たせると、[ADR-0014](./0014-thin-relay-connection-deep-read-layer.md) が定めた「1 ソケット・複数リレーへの同報もリトライも持たない薄いアダプタ」という前提が崩れ、同じ登録状態を 2 箇所で持つことにもなる。したがってプールが再購読も担当する。

## 決定

| 項目 | 決定 |
|---|---|
| バックオフ | 指数、初回 1 秒、上限 60 秒 |
| ジッタ | `delay = base * (0.5 + random())`。無いと 30 本の再接続が同期して復帰時にバーストを自作する |
| 諦める条件 | **永久に諦めない。** 60 秒で頭打ちにして回し続ける |
| 接続枠の扱い | 再接続待ちのソケットは 30 枠を**占有しない**（Task 8 で達成済み）。枠が埋まっていて再接続できないときは、生きている接続から奪わず後でもう一度試す |
| 再購読の担当 | **プール。** アダプタ (`RelayConnection`) は 1 ソケット・リトライ無しのまま保つ |
| 切断中のイベント | **元のフィルタをそのまま張り直す。** `since` で埋めない |
| 再接続中の `status` | `incomplete.unreachableRelays` に計上し続ける。復帰したら自然に減る |
| 手動再試行 | `ConnectionPool.retryNow()` / `SubscriptionManager.retryNow()` を公開。全保留タイマーを即座に発火し、バックオフをリセットする。`online` / `visibilitychange` へのイベント配線はアプリ側の責務（読み取り層は DOM イベントを直接掴まない） — UI ボタンは後続タスク |

### 提案から変えた 2 項目

**再購読の担当。** 提案時点では「接続層が `REQ` を張り直す」としていた。理由は「呼び出し側にやらせると全セクションが再購読ロジックを持つことになり、ADR-0014 の薄いアダプタという前提が崩れる」というものだった。しかし実装が進んだ結果 (Task 7/8)、URL ごとの登録 (filters・handlers) は既にプールが保持していることが判明した — 予算追跡そのものが、生きているエントリの集合をどこかに持つことを要求するからである。この登録をアダプタ側にも複製すると、まさに提案が避けようとしていた「薄いアダプタが太る」問題を接続層側で起こしてしまう。プールが唯一のレジストリであるという Task 7/8 の設計を尊重し、再購読もプールの責務とした。アダプタ (`WebSocketRelayConnection` / `FakeRelayConnection`) は 1 ソケット・リトライ無しのまま — ADR-0014 の意図は当初の想定と違う置き場所で守られる。

**諦める条件。** 提案時点では「連続失敗 8 回、または累計 5 分」だった。streets は TweetDeck 的に何時間も開きっぱなしで使うクライアントである。ノート PC が 6 分スリープしただけで、全カラムが「手動再試行」という当時は存在すらしないボタンに頼るしかない状態に陥るのは受け入れられない。8 回・5 分という上限は、モバイルのバッテリーとリレーのレート制限を守る意図だったが、60 秒キャップ済みの指数バックオフ + ジッタは、それ単体で無限リトライしても 1 分に 1 回程度の頻度にしかならず、バッテリー・レート制限への配慮としては十分である。したがって「永久に諦めない、60 秒で頭打ち」に変更した。手動再試行 (`retryNow()`) は「自動を諦めた後の最後の手段」ではなく「今すぐ試したいときの近道」という位置づけに変わる。

## 切断中のイベントを `since` で埋めない理由

`REQ` を単純に張り直すと、切断中に流れたイベントはその REQ には含まれない。ここで `since` を切断時刻に設定して埋める案もあったが、採用しなかった。ノート PC が 4 時間スリープして復帰した場合、`since` 埋めは 4 時間分のイベントを一度に流し込む。これは [ADR-0011](./0011-performance-budget.md) が定める 500 件上限を即座に食いつぶし、ユーザーが実際に見ていた新しい方のイベントを古い方へ押し出してしまう — 復帰直後に画面が入れ替わるという、ユーザーにとって「壊れた」としか見えない挙動になる。

元のフィルタは大抵 `limit` を持つ（`planQuery` / `SectionReader` が組む REQ は常にそう）。`since` を足さずそのまま張り直せば、単に「今の時点での最新 N 件」を取り直すだけになり、上限を壊さない。切断中に流れて取りこぼした「間」を埋めるのはページネーション（別計画）の役目であり、`EventStore` が id で重複排除するため、後からページネーションで同じイベントが再度届いても二重表示にはならない。

## 実装

`src/core/read/connection-pool.ts` の `ConnectionPool`:

- `Pooled` に `attempts`（連続失敗回数）と `timer`（保留中の再接続タイマー）を持たせる。
- 接続が自然死したとき (`#onConnectionDied`) の末尾で `#scheduleReconnect(url)` を呼ぶ。誰も待っていない (`entries.size === 0`) URL には積まない。
- `#scheduleReconnect` は `base = min(1000 * 2^attempts, 60000)`、`delay = base * (0.5 + random())` でタイマーを積む。
- `#reconnect` は予算が埋まっていれば奪わずに `#scheduleReconnect` へ戻る。`connect()` の失敗と `connection.subscribe()` の失敗は区別する — 前者はソケットそのものが使えないので丸ごと再試行、後者は「ソケットは生きているが特定の REQ だけ失敗した」なので接続は保持したままそのエントリだけ `onClosed` で報告する（`subscribe()` の新規購読パスと同じ区別）。
- `#drop(url)`（購読ゼロで登録を消すとき）と `dispose()` は必ず保留タイマーを `clearTimeout` する。消し忘れると、閉じたはずのリレーへ永遠に再接続を試み続けるゾンビタイマーになる。
- `retryNow()` は保留中の全 URL についてタイマーを消し、`attempts` を 0 にリセットしてから即座に `#reconnect` を試みる。
- タイマー・ジッタは `ConnectionPoolOptions.scheduler` / `random` で注入可能（既定は実タイマー / `Math.random`）。読み取り層が DOM も実タイマーも直接掴んでいないことを構造で示すためで、テストは `vi.useFakeTimers()` ではなく手で進める偽スケジューラを注入する。
- `SubscriptionManager.retryNow()` はプールへそのまま委譲する。

死亡・復帰そのものではセクションの計画を選び直さない（別途 [ADR-0025](./0025-greedy-relay-selection-under-a-global-budget.md) 系の議論を参照）。死んだリレーは「計画は正しいが今は届いていない」であって「計画が間違っている」ではないため、報告先は `unreachableRelays` のままで、選び直しの契機はセクションの追加・削除と `kind:10002` の到着に限る。

### 「諦めない」と「再選択の候補から外す」は別の問い（Task 4 追記）

上の「永久に諦めない」は**この ADR が答える問いに対する答え** —— 「購読者が居るリレーへの再接続をいつ止めるか」という問いであり、答えは「止めない」である。しかし `replan()`（[ADR-0025](./0025-greedy-relay-selection-under-a-global-budget.md)）が次に開くリレーを**選び直す**ときにも同じ URL を選び続けるべきか、は別の問いである。実地（2026-08-05 の実鍵での確認）では `.onion` アドレス（Tor 無しのブラウザからは構造的に到達不能）が最も分かりやすくこれを実演した —— `replan()` のたびに同じ死んだ URL を何度でも選び直し、その枠は誰にも使われないまま失われていた。

この 2 問を混同すると、どちらの答えも歪む。「諦めない」を再選択にまで広げると、到達不能なリレーが永久に枠を握り続ける（上の欠陥そのもの）。逆に「再選択から外す」を再接続の停止にまで広げると、一時的な不調（ネットワーク瞬断など）から自然に復帰するはずのリレーを、二度と試さないまま切り捨ててしまう。

したがって: **再接続 (`#scheduleReconnect`) は購読者が居る限り止めない。再選択 (`selectRelays` の `degraded` 入力、[ADR-0025](./0025-greedy-relay-selection-under-a-global-budget.md)) はリレー自身に起因する連続失敗が `DEGRADED_AFTER_FAILURES`（既定 4 回、正しい指数バックオフの下でおよそ 15 秒ぶんの試行）に達した URL を候補から完全に外す。** 予算超過によるバウンス（`ReconnectReason` の `"budget"`）はこの回数に含めない —— 健全なリレーが他の接続に枠を奪われて再接続を待たされているだけなのに degraded 判定されては、健康シグナルとして意味を成さない。

**除外は `replan()` が実際に走って初めて起こる。** `degradedRelays` に URL が載るだけでは何も変わらない —— 誰かが `selectRelays({ degraded })` を呼び直さない限り、その URL は前回の選択結果のまま生き続ける。

Task 4 の実装直後 (2026-08-05) はここに配線漏れがあった: `SubscriptionManager.#runReplan()` の内部呼び出し元は `subscribe()` と `#close()` の 2 つだけで、接続が死んで degraded に積み上がっても、アプリのどの経路も `replan()` を呼び返していなかった。実地では「`.onion` が 4 回失敗して `degradedRelays` に入る → それでもセクション追加・削除が起きるまで誰も選び直さない → 枠を握ったまま著者が暗転し続ける」という、この節が最初に書かれた時点で「除外された URL は誰にも購読されなくなり…」と書いていた文がそのまま嘘になる欠陥として現れた（最終レビュー、2026-08-06、Important 1）。

**修正: degraded への遷移そのものを、正当な replan の契機として追加した。** `ConnectionPool.onDegraded(listener)` は `hard` が `DEGRADED_AFTER_FAILURES` に**到達した瞬間**だけ通知する（以後さらに失敗が積み上がっても再発火しない）。`SubscriptionManager` はコンストラクタでこれを購読し、通知が来るたびに `#scheduleDegradedReplan()` でバッチタイマー（`DEGRADED_REPLAN_BATCH_MS`、既定 200ms、`profile-requests.ts` の `PROFILE_BATCH_MS` と同じ値・同じ理由）を張る（既に張ってあれば何もしない）。窓が閉じると 1 回だけ `#runReplan()` を呼ぶ —— ネットワーク断で 30 本が同時に死んでも、ジッタでずれた個々の遷移が 1 本の replan にまとまる。`dispose()` はこの購読とタイマーの両方を必ず後始末する。

これは上の「諦めない」規則と矛盾しない。ADR が禁じているのは「死亡・復帰そのもの」を再選択の契機にすることであり、それは単発のブリップ（一時的な瞬断など）でも起こるので、契機にすると健全なリレーまで選び直しのチャーンに巻き込む。degraded への遷移はブリップでは起こり得ない —— `DEGRADED_AFTER_FAILURES`（既定 4 回）連続の *リレー起因* の失敗（予算超過のバウンスは含めない）が要り、しかも 1 URL につき `DEGRADED_COOLDOWN_MS` ごとに高々 1 回しか遷移しない（失敗履歴のレコードは open / `retryNow()` / クールダウンのどれかで消えるまで生き続け、次に degraded になるときは必ずゼロから数え直しになるため）。「死亡・復帰」と「degraded への遷移」は問いとして別物であり、後者だけを契機にする限りこの ADR の方針を変えていない。

除外された URL は誰にも購読されなくなり、その結果 `#scheduleReconnect` 自体も止まる（購読者がいなければ再接続を試みる理由が無い）。したがって「除外 → 再接続停止 → 二度と回復しない」という一方通行にならないよう、`DEGRADED_COOLDOWN_MS`（既定 300 秒）というクールダウンを用意した —— 最後の失敗からこの時間だけ何も起きなければ失敗履歴を消し、次の `replan()`（上の自動配線を含む）で再び候補に戻す。サーキットブレーカの half-open にあたる。失敗履歴は実際に開いた瞬間 (`onOpen`) と手動再試行 (`retryNow()`) でも即座に消える。これが「購読者ゼロで再接続が止まっているリレー」が候補へ戻る唯一の経路である。

## Consequences

- リレー側から見ると再接続は新規接続であり、NIP-42 (AUTH) を要求するリレーでは認証もやり直しになる。AUTH は現時点でどの計画にも入っていない — 今後 AUTH 対応を追加する際は、この再接続フローの中に組み込む必要がある。
- 手動再試行の UI（ボタンなど）と `online` / `visibilitychange` イベントへの `retryNow()` 配線は、この ADR のスコープ外（後続タスク）。
