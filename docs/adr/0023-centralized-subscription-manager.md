# リレー接続と購読を単一の管理システムに集約する

すべてのリレー接続と購読を **1 つの購読管理システム**が所有する。セクションは自分でリレーに接続しない。セクションは「この `Source` の中身が欲しい」と要求し、どのリレーに何本の購読を張るかは管理システムが決める。

## これは選択ではなく強制である

[ADR-0011](./0011-performance-budget.md) で**同時 WebSocket 接続数を 30 に制限**すると決めた時点で、この集約は不可避になった。

各セクションが独立して接続を開く形では、**グローバルな上限を物理的に強制できない**。誰も全体を見ていないからである。10 カラム × 複数セクション × Outbox によるリレー分割（[ADR-0005](./0005-outbox-model-from-v1.md)）が同時に走るとき、上限を守れるのは全体を知っている 1 箇所だけである。

第 1 スライスの `SectionReader` は `openRelay` を受け取って自分で接続を開く。これは単一リレー・単一セクションでは正しかったが、**上限制御を入れる時点で必ず置き換わる**。

## マージは構造ではなく方針である

同一リレーへ向かう複数セクションのフィルタは、1 つの `REQ` にまとめられる（NIP-01 `01.md:118,147` — 1 つの REQ は複数フィルタを持て、複数フィルタは OR 条件）。`limit` はフィルタごとに効く（`01.md:149`）ので、セクションごとの件数指定も保たれる。

**ただしマージは管理システム内部の適応的な方針であって、構造上の約束ではない。**

- 枠に余裕があるときはまとめない（実測では大半のリレーが `max_subscriptions` 20 以上）
- 枠が足りないときにまとめる
- **まとめたグループの中で特定のセクションが待たされすぎたら、そのセクションだけ切り出して単独の購読を張る**

これが成立するのは、マージが `createSection` の外から見えないためである（[ADR-0014](./0014-thin-relay-connection-deep-read-layer.md) の seam）。呼び出し側インターフェース `{ items, status, loadMore }` は、マージの有無によって変わらない。

**したがってマージ無しで動くものを先に出し、必要になった時点で管理システムの内側に足せる。**

## 完了判定 — 失われるのは情報ではなく時間である

EOSE は購読単位であってフィルタ単位ではない（`01.md:157`）。マージすると EOSE は 1 回しか来ず、どのセクションが読み終わったかをリレーは教えてくれない。

**しかし管理システムは自分でまとめたのだから、グループの構成を知っている。**

```
リレーの完了     = そのリレー向けマージグループの EOSE が届いたとき
セクションの完了 = そのセクションが待っている全リレーが完了と記録されたとき
```

情報は失われない。失われるのは**時間解像度**だけである — 速いセクションが同じグループの遅いセクションを待つ。そしてその損失も、上記の「切り出し」で消せる。

これにより [ADR-0015](./0015-section-status-excludes-renderer-fetches.md) の `phase` はマージ下でもセクションごとに解決できる。

## Consequences

- **ローカル再マッチが必要になる。** マージした購読でイベントが届いても、`EVENT` メッセージは `subscription_id` しか持たず、どのフィルタにマッチしたかを教えてくれない。管理システムが NIP-01 のフィルタ意味論（`since ≤ created_at ≤ until`、タグは共通要素が 1 つ以上、複数フィルタは OR）を**自前で実装して突き合わせる**必要がある。テスト対象が 1 つ増える。

  **これをマージの帰結として書いたのは誤りだった（2026-08-01 訂正）。** ローカル再マッチが要るのは、マージするからではなく **リレーの配信を信用しているから**である。マージがなくても、購読に届いたものをそのままセクションに載せる限り、リレーは要求していないイベント（フォローしていない著者の正当な署名付きイベント、別 kind のイベント）をそのカラムへ押し込める。署名検証は**偽造**を止めるが**混入**は止めない。

  そして [ADR-0005](./0005-outbox-model-from-v1.md) の Outbox がこの面積を実質的に広げた。**セクションが話しかけるリレー集合を決めるのが、ユーザー自身ではなくフォローしている著者になった**ためである。したがって再マッチは後続 #3 でマージと同時に入れる「マージの付随作業」ではなく、**それ自体が独立した信頼境界の作業**として扱うこと。

  **解消済み（2026-08-02、後続 #4）。** 照合器を依存ゼロの純粋関数 `matchesFilter` / `matchesAnyFilter`（`src/core/read/filter-match.ts`）として実装した。`SubscriptionManager.#handlersFor` が組み立てる `onEvent` は、フィルタをハンドラ生成時点でクロージャに捕捉したうえで `store.put` の**前**にこれを通す — schnorr 検証より安い照合を先に払うことで、要求していないイベントの洪水を浴びても文字列比較で弾ける。`bootstrap.ts` の `collect()` にも同じ判定を入れ、専用経路のブートストラップ取得も同じ信頼境界に揃えた。設計の詳細は [local-filter-matching 仕様](../superpowers/specs/2026-08-02-local-filter-matching-design.md)、解消の記録は [read-layer-followups.md](../design/read-layer-followups.md) を参照。
- **グループの再編成にはデバウンスが要る。** 同じ `subscription_id` への `REQ` は置換である（`01.md:137`）。1 セクションを閉じるとグループ全体が張り直しになり、他のセクションは初回クエリを再配信され `phase` が巻き戻る。[ADR-0024](./0024-shared-bodies-per-section-membership.md) により表示は壊れないが、カラムの追加・削除が連続するたびに張り直すのは無駄である。
- **`max_subscriptions` はリレーの除外基準ではなくスケジューリングの入力になる。** 実測で 8 〜 300 と開きがある（[調査](../research/2026-08-01-nip65-relay-selection.md) 3.1 節）。
- `SectionReader` の `openRelay` / `releaseRelay` オプションは、管理システムが入る時点で内部化される。第 1 スライスで所有権を明示的にしておいた（`releaseRelay`）のは、そこに参照カウントを差し込めるようにするため。

## 実装の段階

- **後続 #1（Outbox ルーティング）** — 管理システムの器を作る。接続とルーティングの一元化まで。マージはしない。
- **後続 #3（接続プール）** — 30 接続上限、`max_subscriptions` の尊重、再接続（[ADR-0021](./0021-reconnection-policy.md)）。マージは当初ここに含める想定だったが、実際には入れなかった（下記 #5 を参照）。
- **後続 #4（ローカルフィルタ照合）** — 上記「ローカル再マッチが必要になる」を解消したスライス。**マージと同時に入れる付随作業ではなく、独立させた** — マージした購読へ届いたイベントをどのセクションへ配るかを決める手段が照合しかなく、**再マッチはマージの帰結ではなくマージの前提条件である**ため（2026-08-01 訂正、上記）。詳細は [local-filter-matching 仕様](../superpowers/specs/2026-08-02-local-filter-matching-design.md) 0 節。
- **後続 #5（REQ マージ・`max_subscriptions`）** — 後続 #4 の照合器の上に構築する。当初 #3 に含める想定だったものが、再マッチを切り出した結果ここへ回った。
- **後続 #6（セクションの保持と通知）** — **#5 より先に着手した。** 理由は3つ（詳細は[仕様 0 節](../superpowers/specs/2026-08-02-section-reader-performance-design.md)）。(1) REQ マージは今日、観測可能な効果を持たない — セクションを作っているのは `/debug/v1-section` の1つだけで、マージ対象が1本では恒等変換にしかならない。効果が出るのはデッキとカラムのスライスが載って以降である。(2) 本 ADR 自身が上記「マージは構造ではなく方針である」節で「マージ無しで動くものを先に出し、必要になった時点で管理システムの内側に足せる」と先送りを認めている。(3) 性能側は待つと高くつく — [followups](../design/read-layer-followups.md) が「上に3層積む前が最も安く直せる」と書いている以上、時間プロファイルが逆で順序を入れ替えるのが正しい。`SortedEvents`（`src/core/read/sorted-events.ts`）による保持順の全順序化（`created_at` 降順、同値は `id` 昇順、二分探索挿入）と、`Scheduler` 経由の通知バッチ（`NOTIFY_BATCH_MS = 16`、`src/core/read/section-reader.ts`）を実装した。**この追記が無いと、本ADRの採番系列で「#6」がどれを指すか読者が確かめられない**（[read-layer-followups.md](../design/read-layer-followups.md) には別系列の古い採番が残っており、そちらの「#4」は永続化を指す）。
