# リレー接続と購読を単一の管理システムに集約する

すべてのリレー接続と購読を **1 つの購読管理システム**が所有する。セクションは自分でリレーに接続しない。セクションは「この `Source` の中身が欲しい」と要求し、どのリレーに何本の購読を張るかは管理システムが決める。

## これは選択ではなく強制である

[ADR-0011](./0011-performance-budget.md) で**同時 WebSocket 接続数を 30 に制限**すると決めた時点で、この集約は不可避になった。

各セクションが独立して接続を開く形では、**グローバルな上限を物理的に強制できない**。誰も全体を見ていないからである。10 カラム × 複数セクション × Outbox によるリレー分割（[ADR-0005](./0005-outbox-model-from-v1.md)）が同時に走るとき、上限を守れるのは全体を知っている 1 箇所だけである。

第 1 スライスの `SectionReader` は `openRelay` を受け取って自分で接続を開く。これは単一リレー・単一セクションでは正しかったが、**上限制御を入れる時点で必ず置き換わる**。

## マージは構造ではなく方針である

同一リレーへ向かう複数セクションのフィルタは、1 つの `REQ` にまとめられる（NIP-01 `01.md:118,147` — 1 つの REQ は複数フィルタを持て、複数フィルタは OR 条件）。`limit` はフィルタごとに効く（`01.md:149`）ので、セクションごとの件数指定も保たれる。

**ただしマージは管理システム内部の適応的な方針であって、構造上の約束ではない。**

- 枠に余裕があるときはまとめない（実測では大半のリレーが `max_subscriptions` 20 以上）
- 枠が足りないときにまとめる
- **まとめたグループの中で特定のセクションが待たされすぎたら、そのセクションだけ切り出して単独の購読を張る**

これが成立するのは、マージが `createSection` の外から見えないためである（[ADR-0014](./0014-thin-relay-connection-deep-read-layer.md) の seam）。呼び出し側インターフェース `{ items, status, loadMore }` は、マージの有無によって変わらない。

**したがってマージ無しで動くものを先に出し、必要になった時点で管理システムの内側に足せる。**

## 完了判定 — 失われるのは情報ではなく時間である

EOSE は購読単位であってフィルタ単位ではない（`01.md:157`）。マージすると EOSE は 1 回しか来ず、どのセクションが読み終わったかをリレーは教えてくれない。

**しかし管理システムは自分でまとめたのだから、グループの構成を知っている。**

```
リレーの完了     = そのリレー向けマージグループの EOSE が届いたとき
セクションの完了 = そのセクションが待っている全リレーが完了と記録されたとき
```

情報は失われない。失われるのは**時間解像度**だけである — 速いセクションが同じグループの遅いセクションを待つ。そしてその損失も、上記の「切り出し」で消せる。

これにより [ADR-0015](./0015-section-status-excludes-renderer-fetches.md) の `phase` はマージ下でもセクションごとに解決できる。

## Consequences

- **ローカル再マッチが必要になる。** マージした購読でイベントが届いても、`EVENT` メッセージは `subscription_id` しか持たず、どのフィルタにマッチしたかを教えてくれない。管理システムが NIP-01 のフィルタ意味論（`since ≤ created_at ≤ until`、タグは共通要素が 1 つ以上、複数フィルタは OR）を**自前で実装して突き合わせる**必要がある。テスト対象が 1 つ増える。
- **グループの再編成にはデバウンスが要る。** 同じ `subscription_id` への `REQ` は置換である（`01.md:137`）。1 セクションを閉じるとグループ全体が張り直しになり、他のセクションは初回クエリを再配信され `phase` が巻き戻る。[ADR-0024](./0024-shared-bodies-per-section-membership.md) により表示は壊れないが、カラムの追加・削除が連続するたびに張り直すのは無駄である。
- **`max_subscriptions` はリレーの除外基準ではなくスケジューリングの入力になる。** 実測で 8 〜 300 と開きがある（[調査](../research/2026-08-01-nip65-relay-selection.md) 3.1 節）。
- `SectionReader` の `openRelay` / `releaseRelay` オプションは、管理システムが入る時点で内部化される。第 1 スライスで所有権を明示的にしておいた（`releaseRelay`）のは、そこに参照カウントを差し込めるようにするため。

## 実装の段階

- **後続 #1（Outbox ルーティング）** — 管理システムの器を作る。接続とルーティングの一元化まで。マージはしない。
- **後続 #3（接続プール）** — マージ、30 接続上限、`max_subscriptions` の尊重、再接続（[ADR-0021](./0021-reconnection-policy.md)）。
