# kind 固有の知識は kind 側に置き、共有層は kind を知らない

## 判定基準

**置こうとしているものが「この kind のこのタグ（またはフィールド）は何を意味するか」を含むなら、その kind を扱う kind 側のコードに置く。含まないなら、置き場所は素直さと正しさで決めてよい。**

「kind 側のコード」とは、その kind を扱うことを前提にしてよいコード —— レンダラ（[ADR-0003](./0003-open-column-abstraction.md)）、書き込みのビルダ（`src/core/nostr/build/`）などを指す。「共有層」とは、`EventStore` や取得層・書き込み層の合流点のように、複数の kind をまたいで動くコードを指す。

冒頭の例（「kind 7 の `e` タグはリアクション先を指す」）は**タグの意味の解釈**を指しており、**汎用のフィルタ機構や、タグ名・値だけで動く差分適用はこれに当たらない**。「この kind の一部として書かれた」「元は特定の NIP のために書かれた」は判定基準ではない —— 由来ではなく、今そのコード自身が kind の意味を知っているかどうかで判定する。

> **この ADR は同じ形で 2 回誤読された。** 判定基準を当てずに、タイトルや冒頭の一文だけを読んで「置き場所」を決めるとこうなる。
>
> - **2026-08-14、リアクション一覧の設計**: 「`EventStore` にタグの索引を足すと本 ADR を破る」と判断し、取得層のコアレッサに索引を持たせる案を立てた。索引はタグ値でイベントを引くだけで kind の意味を一切含んでいないのに、「共有層に何か足す = 本 ADR 違反」と結論だけで判定した。**しかも誤読の結果として選んだ案は技術的にも劣っていた** —— v1 に入るイベントはカラムの購読・`fetchOnce`・水和のどれを通っても `EventStore.put` を経由するのに、コアレッサ側の索引は自分が投げた取得の結果しか見えず、カラムが直接受け取ったイベントを取りこぼす。
> - **2026-08-22、書き込み層のタグ差分ヘルパー統合**: `follow.ts` (NIP-02) の `removeFollow` と `list.ts` (NIP-51) の `removeFromList` が同じアルゴリズムだったが、「`follow.ts` が `list.ts` に依存すると本 ADR に反する」と判断し、別実装のまま残した。`removeFromList(kind, name, value)` は kind の意味を一切含んでおらず（`FOLLOW_KIND` もタグ名 `"p"` もどちらの実装でも `follow.ts` 側に残ったまま）、判定基準を素直に当てれば共有してよかった。本当の問題は kind 非依存のヘルパーが NIP-51 の名前 (`list.ts`) を名乗っていたことで、`draft.ts` の `replaceTags` の隣へ移し kind 非依存な名前 (`addTagValue`/`removeTagValue`) に付け替えて解決した。

## 決定

「kind 30003 の `e` タグは対象イベントを指す」「kind 7 の `e` タグはリアクション先を指す」といった kind 固有の知識は、その kind を扱う kind 側のコードが持つ。レンダラは必要な関連イベント（参照先イベント、著者のプロフィールなど）を取得層に要求できる。カラム層・共有層は kind を一切知らない。

[ADR-0003](./0003-open-column-abstraction.md) の動機（NIP 変更の影響範囲を kind に閉じる）を成立させるには、取得の意味論も kind 側に無いと成立しない。カラム定義側に写像を宣言する方式では、リスト系 kind を追加するたびにカラム層を触ることになり、動機と矛盾する。

## Considered Options

- **レンダラ側。関連イベントを要求できる** ← 採用
- **カラム定義側で写像を宣言する** — 取得が1箇所に集中し最適化しやすいが、新 kind 追加のたびにカラム層を触る。ADR-0003 と矛盾。
- **kind 定義をデータとして登録し取得層が解決する** — 両立するが、メタ記述 DSL の設計コストが高く、表現力の限界に達したとき逃げ場がない。
- **解決せず ID のまま表示** — 抽象は最も薄くなるが実用に耐えず、ADR-0001 と衝突。

## Consequences

以下は v1 の**必須要件に繰り上がる**。この決定の代償であり、後から足せない。

- **要求の合流・重複排除・バッチング。** 100 件の投稿レンダラが各々著者プロフィールを要求するため、素朴に実装すると N+1 のリクエスト爆発を起こす。
- **カラムの「読み込み完了」の再定義。** レンダラが遅延取得するため、リレーから EOSE を受け取った時点では描画は完了していない。カラムの読み込み状態は EOSE と一致しない。
- **取得回数の上限制御。** レンダラが自由に要求できる以上、無限スクロールと組み合わせると要求が青天井になる。

また、旧 v1 設計ドキュメントにあった「派生ビュー（ProfileView 等）は決してフェッチしない」という原則は **本 ADR により破棄**される。

## 実装の段階

- **A-2（レンダラと関連イベント、2026-08-07）** — 本 ADR が必須要件に繰り上げていた「取得回数の上限制御」は、[ADR-0017](./0017-declarative-renderer-needs.md) が当初想定していた**深さ上限のカウンタではなく**、**`compact` が自分の関連イベントを一切要求しないという表示規則**で満たされた（[仕様](../superpowers/archive/specs/2026-08-07-renderers-and-related-events-design.md) 3 節）。すべてのレンダラは `full`/`compact` の 2 表示を持ち、引用先・返信の親・リポストの対象は必ず `compact` で描かれ、`compact` は自分の関連イベントを一切要求しない。`full` → `compact` で必ず打ち止めになるため、引用の引用のような入れ子は構造的に深さ 1 で止まる。取得回数の上界は「登録されているレンダラの種類や数」ではなく「`full` 1 段 + その関連の `compact` 1 段」という表示の形だけで決まる。詳細は [ADR-0017](./0017-declarative-renderer-needs.md)「実装の段階」の A-2 の項を参照。
