# Outbox Model (NIP-65) を v1 の最初から実装する

イベントの取得先リレーは、ユーザーが設定した固定リレー群ではなく、**NIP-65 (`kind:10002`) に基づいて著者ごとに選択する**（Outbox Model）。ある著者の投稿はその著者の write relay から取得し、ある著者宛のイベントはその著者の read relay へ送る。

## なぜ最初からか

Outbox Model は取得層の形そのものを変える。固定リレー方式が「1つのフィルタを全リレーへ同報する」のに対し、Outbox Model は「1つの論理クエリを著者ごとに分割し、リレーごとに異なるフィルタを送り、結果を合成する」。**後から入れることは取得層の全面書き換えを意味する**ため、段階導入は書き換えを2回行うことになる。

また [ADR-0001](./0001-others-first-self-via-settings.md) で「他人が使えること」を優先すると決めた以上、**作者のリレー構成を知らないユーザー**が主要な想定利用者になる。その人のフォロー先の投稿が欠落するクライアントは要件を満たさない。

## Considered Options

- **Outbox Model を v1 から実装** ← 採用
- **ハイブリッド（既定リレー + リレーヒント + 部分的 NIP-65）** — 段階的に実装できるが「どこまでやれば十分か」の基準がなく、中途半端な状態が固定化しやすい。
- **固定リレー方式のまま（v0 方式）** — 取得層は単純だが、リレーを共有しない相手の投稿が欠落する。ADR-0001 と衝突。
- **v1 は固定、Outbox は v2** — [ADR-0002](./0002-v0-parity-before-cutover.md)（パリティ後に一括切替）と組み合わせると、切替直後に再び大工事が発生する。

## Consequences

- **EOSE の合成が非自明になる。** リレーごとに担当する著者集合が異なるため、「カラムの読み込みが完了した」の定義を設計する必要がある。[ADR-0004](./0004-kind-knowledge-lives-in-renderers.md) が既にこの定義を難しくしており、影響が重なる。
- **ページネーションが一様でなくなる。** リレーごとに保持期間や応答が異なり、進み方が揃わない。
- **N+1 が二重になる。** ADR-0004 によりレンダラが関連イベントを要求し、そこに「遭遇した著者の `kind:10002` を引く」が加わる。著者→リレーのルーティング表のキャッシュ戦略が必須要件になる。
- `kind:10002` を公開していない著者へのフォールバック（リレーヒント、既定リレー）が必要。
